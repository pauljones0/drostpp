## 2. Core architecture and end-to-end control and data flow

### Hosting, naming, and execution ownership

The public facade exposes `DurableAgent`, `AgentRunner`, model adapters, `AgentExecutorBase`, and agent/tool helpers. `AgentBase` assembles collaborators: profile and prompts, a Dapr client factory, the infrastructure facade, optional registry and state, memory, tools, model or executor, and observability. Construction makes a synchronous Dapr metadata request even with an explicit model. Named components can fill omitted state, registry, memory, and pub/sub configuration. It resolves execution configuration from defaults, environment, explicit arguments, and runtime state in increasing precedence. Config Store callbacks can update selected fields later. The constructor rejects using both a chat client and a stateful executor. [Exports][exports], [bootstrap][bootstrap], [config resolution][config-resolve], [config application][config-apply], [model/executor choice][model-exclusive].

Starting an agent registers its primary and optional orchestration/broadcast workflows under canonical agent-scoped names, with a named `v1` registration. It also scopes each activity name to the agent so one runtime can hold multiple agents' activities. The runner discovers one `@workflow_entry`, uses the registered name for scheduling, and owns the default workflow client. A caller may supply a runtime or client. Shutdown is designed to preserve a borrowed runtime and close owned resources. Initial attachment normally connects MCP tools, starts the agent, and fires registered activation callbacks before scheduling. [Start/stop][agent-start], [registration][registration], [entry discovery][discover], [runner run][runner-run], [ownership][runner-shutdown], [activation][attach].

At the Python boundary, `WorkflowRuntime` registers and executes generators and activities, and `DaprWorkflowClient` schedules, queries, raises events, and terminates. Dapr Workflow supplies the durable history, logical clock, event and timer scheduling, and child-workflow machinery. Dapr's workflow implementation uses actors underneath, as the repository describes. This checkout's agent class is a Python host and workflow definition. The actor lifecycle, placement, turn serialization, reminders, and workflow-history replication are infrastructure responsibilities. The agent state facade uses separate Dapr state keys. Workflow completion in the sidecar and successful persistence of the application's timeline are distinct outcomes. [Actor boundary][actor-doc], [SDK pin][sdk-pin], [workflow registration][registration], [status source][initial-entry], [timeline definition][entry-model].

### Ingress and scheduling

- **Direct invocation.** `AgentRunner.run` connects/attaches, selects the named entry, and delegates to `WorkflowRunner.run_workflow_async`. Scheduling and optional blocking completion wait are thread-offloaded. The scheduler picks an instance ID once and retries selected transient gRPC statuses with 1/2/4-second backoff. Detach returns the instance ID. A waiting caller receives serialized output, and full workflow state remains accessible through the client. The synchronous API enters an event loop or a separate loop thread. HTTP run, status, terminate, and purge call into the same primitives. [Direct runner][runner-run], [schedule retry][schedule], [async wait][runner-wait], [sync wrapper][runner-sync], [service operations][service-ops], [status][status-route].
- **Pub/sub.** Route specs and decorator metadata become bindings grouped by component/topic. A blocking Dapr subscription thread extracts CloudEvent data and metadata, prioritizes a matching event type, applies pre-validation and typed filters, validates a Pydantic/dataclass/dict shape, and maps or skips before scheduling the first accepted route. The scheduler receives a serialized input with message metadata attached. Default sync delivery waits for scheduling success. Optional synchronous completion waiting yields SUCCESS for completed, DROP for failed, and RETRY for unresolved state. Async delivery applies backpressure to the enqueue and acknowledges that enqueue. The TTL cache marks SUCCESS/DROP only. [Binding collection][binding-collect], [CloudEvent decoding][cloud-event], [routing][route], [serialization][serialize-route], [ack policies][schedule-route], [ack dispatch][broker-ack].
- **Workflow composition.** `call_agent` yields a Dapr child call with agent workflow name, app ID, and optional instance ID. `trigger_agent` supplies a temporary wrapper workflow that waits for a cross-app child from a caller without an existing workflow context. `AgentWorkflowTool` packages the child app and canonical name with task and parent stream context, then returns the Dapr task to the orchestration generator. Pub/sub broadcasting lets peers receive context asynchronously. [Child helper][call-agent], [trigger helper][trigger-agent], [agent tool][child-tool], [broadcast workflow][broadcast], [broadcast memory][record-broadcast].

### Standard chat and tool loop

Entry records source, parent, trace, and stream context in a state activity and optionally discovers registry tools. The generator chooses a delegated orchestration workflow, an executor activity loop, or standard chat/tool turns. A standard turn calls the model activity with logical time, turn, task, and instance ID. The activity loads the entry, checks for a previously saved response for the activity execution, reconstructs chat history, renders the prompt, saves the user message in the entry, and invokes a `ChatClientBase` adapter. It records system messages separately and adds up to three recent peer broadcasts. Built-in LLM hooks execute within the activity. The first decisive before-hook can skip, deny, or mutate a call. The after-hook can replace the assistant message before persistence. Structured calls use known response models and avoid offering tools on a fresh structured turn. [Entry and dispatch][flow-entry], [prompt and history][llm-entry], [broadcast history][history], [LLM hooks][llm-hooks], [response commit][llm-commit].

Provider adapters normalize messages and functions, translate requests into provider shapes, and normalize responses to `LLMChatResponse`, validated models, or candidate chunks. The Dapr adapter checks sidecar capability/component metadata, calls Conversation Alpha2, translates its result, and tags the non-streaming fallback when streaming was requested. It currently takes that fallback unconditionally. Direct adapters can provide provider deltas. The Dapr adapter reduces function-specific choice to `required`. These are explicit limitations at this pin. [Chat contract][chat-base], [Dapr adapter][dapr-chat], [Alpha2 client][dapr-converse], [direct adapter][openai-chat], [stream normalizer][provider-stream].

An assistant tool batch first passes tool hooks by call position. Deny and skip create corresponding tool replies. Mutate replaces arguments, and approval suspends before normal dispatch. A regular tool is an activity that validates JSON and dispatches through `AgentToolExecutor`. A workflow-injected tool is invoked with hidden context so it can return a Dapr task or a generator. In parallel mode ordinary activities and task-returning tools are submitted before a group join. Workflow generators are driven afterward, inline. In sequential mode the generator invokes a closure only after the preceding item returns. That distinction makes scheduling sequential, including for mixed regular/child tools. Results return to the model in its original call order regardless of the execution grouping. [Tool hook pass][tool-hooks], [dispatch setup][tool-dispatch], [sequential and parallel join][tool-join], [tool activity][tool-activity], [argument contract][tool-context], [result commit][tool-save].

`save_tool_results` writes the batch into the instance timeline and into the operator-facing tool history. To avoid corrupting the provider message sequence, a regular tool result is appended only when the last non-tool message is an assistant with calls. The count of replies following that assistant lets the save be repeated without duplicates, including repeated IDs in a batch. Direct orchestration dispatches have no matching model call and use history-only mode. On an ordinary reply the loop finishes, and on exhaustion it creates a user-facing notice. The workflow then optionally broadcasts or summarizes, finalizes state, and returns or raises. A failure in preparation or finalization follows a different path from a failure inside the loop. [Batch invariant][tool-save], [history-only dispatch][orch-tool-history], [finalization path][flow-finish].

### Orchestration and stateful executor branches

The orchestration child gets one activity-recorded registry snapshot of team members. Round-robin uses sorted names and rotates modulo team size. Random selects in an activity, avoiding the previous responder where possible. Both seed the next peer with the previous response and proceed to the configured turn limit. The model-planned strategy requests a typed plan, routes each step/substep, validates the choice against the plan, calls the selected peer workflow, records the result in the parent entry, checks progress, updates the plan, and summarizes. It prefers the target's published workflow name and routes by app ID. Thus model planning, peer execution, progress, and optional broadcasts are visible as separate workflow work. The orchestration workflow handles one selected peer at a time. Fan-out is available via the regular tool batch. [Orchestration entry][orch-entry], [selection][orch-select], [child dispatch][orch-dispatch], [progress and finalization][orch-progress], [round-robin][roundrobin], [random selection][random], [strategy interface][strategy].

A stateful executor owns its own reasoning loop. The host binds the current prompt, tools, hooks, and session store, then consumes its async stream within `run_executor`. The common event contract distinguishes deltas, messages, tool calls and results, session checkpoints, and the terminal `complete`, `paused`, or `error`. A recorder updates the agent entry and exposes an observer/stream path. A paused activity returns serializable data to its workflow, which waits for an approval and schedules a new activity on the same session with decision and arguments digest. Missing terminal events and retryable errors raise. A terminal non-retryable result is returned across the activity boundary and then converted to a workflow failure, bypassing that activity's retries. [Executor contract][executor-contract], [events][executor-events], [binding][executor-bind], [executor workflow][executor-workflow], [consume/cleanup][executor-activity], [recorder][recorder], [resume payload][executor-resume].

The Claude adapter's durable session path derives a stable UUID for a caller alias, detects a pending or unfinished turn from a transcript, and waits for client exit before emitting the terminal event so transcript appends can complete. `DaprSessionStore` writes immutable chunks before an ETag-guarded manifest, checks if a lost commit reply actually committed, disposes of unreferenced chunks on the recoverable path, and reloads when a folding append races with a reader. It applies bounded UUID dedupe and optional TTL. The executor bridge records local workflow-backed tool requests, gives them deterministic call-occurrence IDs, schedules via the client, and reattaches on retried attempts. It excludes cross-app agent calls and interactive generator tools from that bridge. The standard workflow-context path supports those capabilities separately. ## 3. Why it works and its governing invariants

1. **Replay records decisions.** A workflow must issue the same durable commands for a given history. Context time, recorded activity results, named versions, and durable events make it possible to resume without repeating completed model/router work. Random peer choice is inside an activity, and user waits derive stable event names. Tool policy executed in the generator is explicitly required to be deterministic. A topology, policy, or code change that affects scheduling must be captured per run or versioned. The source violates parts of this invariant, discussed below. [Workflow change guidance][versioning-guide], [time and activities][flow-entry], [random strategy call][orch-select], [hooks contract][hooks], [interactive ID][ask-user].
2. **Durability is layered.** The workflow engine records completed tasks and can redeliver an activity whose completion was lost. The Python state/output boundary still needs its own idempotency. A saved assistant response can be found by workflow/execution ID plus input, with a task-ID fallback that covers redelivery but loses cross-retry identity on older sidecars. A saved tool-result batch can be detected from its matching assistant boundary. Neither mechanism establishes exactly-once execution of model calls or arbitrary side effects before the application write. [LLM redelivery check][llm-entry], [attempt identity][llm-id], [tool batch replay][tool-save], [session dedupe][session-layout].
3. **The conversation has causal pairing.** One assistant request with calls is followed by replies for those calls before another model turn. Call-position ordering is independent of completion order. Orchestrator results update history without inventing assistant calls. Error text and denials are usable tool replies, allowing the model to continue when a tool fails ordinarily. An unexpected exception from a workflow-backed child can still fail the enclosing join. [Ordered dispatch][tool-join], [tool failure conversion][tool-activity], [conversation pairing][tool-save], [history-only dispatch][orch-tool-history].
4. **Identity crosses boundaries explicitly.** Names select installed workflow/activity bindings. Instance IDs link workflow state, timeline, and stream lineage. Provider tool IDs connect replies to the right assistant. Call positions distinguish decisions for repeated IDs. A named external event links a human decision to its waiting workflow. Dapr supplies durable execution identity and app routing. Progress, output, and trace consumers need an unambiguous identity at each boundary. [Registration naming][registration], [child input][child-tool], [tool decisions][tool-hooks], [approval identity][approval-wait], [stream envelope][stream-types].
5. **Acknowledge only the boundary reached.** Sync pub/sub accepts a scheduled workflow, or optionally a terminal outcome. Async accepts volatile queue admission. The TTL cache is scoped to a local subscriber and records a completed routing disposition. It cannot prove one job per business event across replicas or process loss. The broker, scheduling policy, and idempotent handler each own part of delivery. [Boundary semantics][route-setup], [sync scheduling][schedule-route], [async scheduling][enqueue], [dedupe][dedupe].
6. **A published state pointer must refer to durable data.** The executor session store ensures chunks precede the manifest, resolves ambiguous commit replies, and refuses a transcript with holes. The team index recomputes the mutation over freshly loaded state after ETag conflict. These are stronger invariants than retrying a pre-serialized stale workflow entry with a fresh ETag. [Session chunk read][session-read], [session commit][session-commit], [index CAS][index-cas], [timeline CAS][state-save].

## 4. Strengths

- **Meaningful durability granularity.** A typical agent turn has separately identifiable model, tool, result-save, and finalization checkpoints. The parent waits on a recorded child call and can resume without re-planning completed steps. Context time and separate activities place side effects at useful retry boundaries. Scoped activity names and named workflow versions make the worker registry understandable for co-located agents and rolling changes. [Entry loop][flow-entry], [activity grouping][registration], [versioning guide][versioning-guide].
- **Correctly separates dispatch order from result order.** The pinned sequential change delays activity and child creation, so later tools cannot start simply because their tasks were constructed early. The repository covers regular and context-injected sequential dispatch. My mixed batch paired a local tool, child, and local tool and observed the next operation appear only after its predecessor returned. Parallel control scheduled all three before joining and still saved replies in model order. This verifies generator-level scheduling, including cross-app request construction. [Dispatch][tool-dispatch], [result join][tool-join], [repository sequential tests][seq-tests], [focused probes][probes].
- **Purposeful recovery in the newer state components.** The registry writes one record per agent and protects only the shared index with a fresh read and CAS, reducing the contention surface. Its attempt and jitter budgets are explicit. The executor transcript store models an ambiguous commit separately from a failed write. Its tests exercise lost replies, first-commit behavior, dedupe, TTL, and chunk folding against a store that deep-copies data and rejects stale ETags. Those tests cover useful conditions that a simple state mock misses. [Registry index][index-cas], [transcript commit][session-commit], [CAS fake][fake-etag], [registry tests][index-tests], [transcript tests][session-tests].
- **Useful extension seams.** Typed model, tool, hook, and executor contracts allow local verification without providers. Trigger activation has an explicit payload and cleanup callback. Route specs let extensions filter/map data before creating durable work. The code separates executor event recording and transcript analysis from the primary workflow. State and provider specifics have identifiable boundaries. [Activation type][activation], [route registration][route-setup], [hook decisions][hooks], [executor binding][executor-bind], [executor recorder][recorder], [transcript parsing][claude-transcript].
- **Streaming is subordinate to agent execution.** The consumer starts before workflow scheduling. Transport exceptions are generally logged independently of workflow or model progress. Parent/child lineage and control events can describe a run with multiple agents. The Alpha2 fallback and structured-output branch retain a consistent start/complete envelope shape. The consumer respects root depth, so a child turn does not end its parent's session. [Run ordering][run-stream], [stream envelope][stream-types], [transport errors][emit-id], [fallback][dapr-chat], [root termination][stream-consumers].
- **Observability includes both runtime and model work.** Debug context, instance IDs, registration names, tool records, provider usage, and executor phases give operators distinct inspection points. Activity registration is wrapped for tracing. The executor observer produces run and tool spans from the normalized event stream. State and tool errors can carry causes to the activity/workflow boundary. The concerns in §5 limit how authoritative those signals are in failure cases. [Log context][log-replay], [instrumentor][instrument], [activity spans][activity-span], [executor spans][executor-span], [result failure][tool-activity].

### Replay divergence observed at the generator boundary

- **Policy is read from the live object.** A standard run with an already-recorded first tool turn would schedule its second model call with budget 2. Re-entry with identical inputs and activity outputs after applying the supported `MAX_ITERATIONS=1` config update scheduled finalization instead. Restoring 2 restored the original request. The same source reads live tool-execution mode and hooks in the schedule-building loop. A per-run replay configuration snapshot would preserve the documented hot-reload feature for new runs. [Mutable config][config-mutable], [body loop][flow-entry], [hook decisions][tool-hooks], [finalization request][flow-finish].
- **Registry-loaded tools are worker-local.** `load_tools` updates the in-process tool map and returns only names. Retrying with a cold worker and the same history value `["Helper"]` made an assistant's agent-tool call schedule `run_tool`, while a worker with the registration issued a child-workflow request. The probe reproduced the dispatch difference. It did not run a broker, evict a real workflow worker, or verify the SDK's replay-error response. ### Tradeoffs and unresolved boundaries

- Arbitrary model/tool activity side effects can repeat before a durable application commit. The SDK can redeliver a task even where the tool's own retry policy is conservative. The standard tool loop folds ordinary errors into result data, which keeps the conversation viable but precludes workflow retry for those tool failures. Retryable executor errors have an explicit event distinction. The lifecycle would benefit from stable step-level operation IDs and tool-specific retryability. [Tool execution][tool-activity], [tool executor][tool-error], [executor error event][recorder], [LLM delivery guard][llm-id].
- Timeline writes replace the whole Pydantic document. Tool fan-out is joined and normally serialized into one batch save. This simplifies ordering and dedupe, while growing transcript reads/writes and model context with run length. The session manifest store gives large executor transcripts a different scaling path. No throughput, state size limit, or resource usage claim follows from the probes. [Timeline write][state-save], [batch write][tool-save], [session layout][session-layout].
- TTL dedupe is local and its check and mark surround scheduling. It offers duplicate suppression for a short window within that process. A crash, separate replica, ambiguous scheduling reply, or broker redelivery after expiry can fall outside it. In sync completion-wait mode a timeout also returns RETRY after the first schedule has succeeded, using a fresh workflow ID if the message is scheduled again. Broker exact behavior remains unverified. [Cache implementation][dedupe-type], [completion and scheduling][schedule-route], [marking][dedupe].
- Stream transport is best-effort. The bounded publisher drops on saturation, including control chunks if enqueued while full. The in-process and receiving async queues have no bounded item limit at this pin. Root cleanup owns the root agent's cached listeners. An independently hosted child, cancelled workflow, or failed finalizer can leave a transport lifetime that no active root cleanup reaches. Late reattach currently assumes the configured per-session topic and reads pending inputs from the root entry. This review did not measure retention, backpressure across a real broker, or listener leak rates. [Publisher queue][pub-listener], [in-process registry][local-listener], [pub/sub receive][stream-consumers], [listener cache][listener-cache], [finalization][finalize], [reattach][reattach].
- The pending approval index is one in-memory dictionary per agent, written as a whole document. Its state-store persistence has no ETag mutation loop and restore is best-effort. Two replicas can therefore overwrite each other's pending approvals under competing updates. The separate Dapr event wait remains the authority for whether a workflow can advance. The concurrency risk is source-supported. [Approval persistence and restore][approval-store], [Dapr wait][approval-wait].
- Trace continuity depends on process-local TTL storage in the wrapper path. The agent entry has a persisted trace field if supplied, but the activity wrapper's selected restoration path reads the local cache and a fallback key. The reviewed scheduler wrapper stores context after scheduling and doesn't write that field into its input. Distributed gRPC instrumentation may still provide parent context from the runtime. Context reconstruction after worker replacement and multi-agent provider hot reload need actual sidecar and exporter tests. [Scheduling span][trace-run], [activity restore][activity-context], [context cache][trace-storage], [entry context][initial-entry], [provider reload][otel-reload].

## 9. Post-mortem and prioritized improvements

The runtime is under three simultaneous pressures. Dapr must own replay and worker placement. Agent authors need familiar Python functions and provider flexibility. Operators need seen-at-a-glance answers about a live conversation, even across asynchronous brokers and state stores. The code gets much of the first two by recording the orchestration at activity boundaries. Its hardest failures come from treating a locally convenient value as evidence of a durable transition. A returned assistant message can outlive a failed timeline save. A queued trigger can outlive a failed schedule. A terminal stream message can precede a failed workflow. Consolidating each of those boundaries would improve correctness more than adding another orchestration pattern. [Workflow boundary][flow-entry], [timeline commit][llm-commit], [async routing][enqueue], [stream terminal][terminal-event].

1. **P0 — Give the application timeline an explicit commit contract.** Bind the ETag to the snapshot returned to each mutation. Recompute a typed, small mutation against the latest snapshot on conflict, with an idempotency key and a defined resolution for ambiguous commits. Propagate exhausted store errors to a workflow-visible boundary. A durable model result and replay-safe message commit may need to be separate activities so a retry of persistence does not re-run inference. Reuse the registry mutation and session manifest patterns. Add the controlled read-after-write failure, same-key conflict, lost reply, and transcript pairing cases to the ordinary suite. Make the no-store mode maintain separate transient entries or require an explicit application store for isolated agent runs. [Current write path][state-save], [model result][llm-commit], [working registry CAS][index-cas], [manifest recovery][session-commit].
2. **P0 — Acknowledge ingress after an acceptance point that survives process loss.** Await the durable schedule result before acknowledging or put the job into a durable inbox first. Include CloudEvent identity and route scope in a stable schedule key with a defined duplicate/ambiguous-reply outcome. An async queue can provide backpressure and concurrency while consumers retain the ability to send RETRY. Completion waiting needs a separate retry rule so a timeout does not create another run. Preserve route schema unions and hook metadata through canonical-name adaptation. Add a deterministic worker failure after enqueue plus a broker-redelivery test in a local SDK/sidecar harness. [Delivery boundary][schedule-route], [async enqueue][enqueue], [dedupe][dedupe].
3. **P1 — Record the execution plan that the workflow body will replay.** Freeze iteration limit, strategy, dispatch policies, versioned tool descriptors, and route choices in input or initialization activities. Have model replies refer to a recorded tool binding or an activity-produced dispatch plan. Generate stable child identities from workflow instance and a durable dispatch ordinal, or the SDK's replay-safe ID primitive when available. Govern shape changes with SDK patches and named versions, including the sequential scheduling change. Test earlier and current versions under a fresh worker with active approvals and tool calls. [Hot reload][config-mutable], [catalog mutation][load-tools], [dispatch code][tool-dispatch], [SDK replay guidance][versioning-guide].
4. **P1 — Give streaming a well-defined terminal and identity contract.** Include a stable workflow operation identity plus per-emission offset so a retry maintains identity while unrelated phases and controls are distinct. Share status with the workflow result model and support terminal failed/terminated states. Monitor terminal workflow status, honor the caller's deadline, and close the consumer if setup is cancelled or readiness fails. Distinguish explicit termination of a workflow from closing a stream. Persist authoritative control state when an event must survive a dropped chunk. [Current identity][emit-id], [terminal marker][terminal-event], [run stream][run-stream], [consumer startup][pubsub-readiness].
5. **P1 — Publish readiness and clean up human waits explicitly.** Use a single-flight attach result shared by concurrent callers. Propagate registration and actual runtime start errors, and give the already-started case a narrowly typed outcome. Persist approval state per workflow/request with a terminal transition for expiry, answer and workflow termination. Keep generic event handling within the workflow engine, and treat the listing as a recoverable view over those requests. [Attach guard][attach], [workflow lifecycle][agent-start], [approval store][approval-store], [timer race][approval-wait].
6. **P2 — Reduce ambiguity and strengthen real-boundary tests.** Introduce typed terminal outcomes and tool result records that carry error kind, retryability, ordinal, and child identity. Separate selection from application of hot config, preserve explicit memory and state adapter choices, and own gRPC/OTel setup at a scope that matches the SDK. Reject canonical binding collisions when sharing a runtime. Keep the fast Python suite. Add a locked, credential-free local SDK/sidecar suite with scripted model/provider outputs, deterministic clocks/fixture operations where applicable, and staged worker restart. Verify actor-backed progress, external-event/timer races, actual state-store conflict behavior, trace adoption across replicas, and cross-app workflow registration names before claiming production durability. [Status logic][flow-finish], [tool result writes][tool-record-status], [memory wiring][memory-binding], [private SDK gRPC patch][workflow-grpc], [telemetry reload][otel-reload], [current unit seams][conftest].
