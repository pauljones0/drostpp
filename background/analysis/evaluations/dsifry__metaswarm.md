**Assessment.** Metaswarm is a detailed development workflow for a host agent, with a narrow deterministic review-rule helper and several executable integration boundaries. It has a strong specification for accountable, independently reviewed work and a weak implementation contract for applying that specification reliably across interrupted, parallel, or externally delegated runs. The most serious measured problems occur where the shell adapters translate worker completion into Git and JSON outcomes. Provider exit zero can accompany a rejected Git commit, a successful commit can be reported with zero changed files, and a later review can receive an incomplete diff. The shell and Node suites give useful regression evidence on their fixtures. They exercise a smaller surface than the orchestration vocabulary suggests.

## 3. Why the design works and its governing invariants

- **Written acceptance precedes delegated changes.** A plan can be checked against original scope, allowed paths, dependencies, and a verifiable definition of done. The design and plan gate order preserves the artifact under review in each entry path. The assumption ledger separates an agent proposal from a user-confirmed requirement. This reduces the chance that a later agent treats an inference as an established constraint. [Pipeline and revisions](repos/dsifry__metaswarm/guides/workflow-enforcement.md:5) [Ledger and confirmation](repos/dsifry__metaswarm/skills/brainstorming-extension/SKILL.md:22) [Work-unit fields](repos/dsifry__metaswarm/skills/orchestrated-execution/SKILL.md:127)
- **Workers propose, coordinators verify, reviewers attest.** The coder reports an implementation, the orchestrator reruns tests and scope checks, and a fresh reviewer checks DoD evidence against the spec and diff. Freshness limits anchoring and self-certification. The orchestrator may supply earlier theme names and confirmed requirements while withholding previous findings. Work remains isolated in an assigned Git worktree where the workflow requires it, and the coordinator integrates after validation. [Independent validation](repos/dsifry__metaswarm/skills/orchestrated-execution/SKILL.md:235) [Reviewer inputs](repos/dsifry__metaswarm/skills/orchestrated-execution/SKILL.md:273) [Theme and acknowledgement identities](repos/dsifry__metaswarm/guides/delivery-scope.md:121) [Worktree ownership](repos/dsifry__metaswarm/guides/worktree-development.md:215)
- **The decision function is ordered and reproducible for normalized history.** Blockers require a material consequence plus evidence. One completed round without blockers passes. Remaining blockers can require Clarification (C1 user input or unconfirmed assumption, C2 nonconvergence or reviewer divergence, C3 fix-induced blockers, C4 recurring themes), then cap or recurring/disputed escalation, then an overengineering check or iteration. C1 includes merged duplicates, C2–C4 count distinct defects or themes, and prior judgments enter as explicit flags. Closed and clarify-pending histories give distinct outcomes. A specific user acknowledgement can update the window, theme set or question IDs, with the blocker set and round cap preserved. Revised or narrowed scope needs a fresh review. ## 4. What it does well and poorly, with source evidence

### Strengths

- **Review is tied to a concrete risk and to evidence.** The six-field finding contract requires title, description, severity, protected scenario, evidence, and an explicit blocker flag. The separation between fixable defects, requirement clarification, and discretionary cleanups is unusually actionable. The ordered rule keeps recurrence and nonconvergence visible, even as fresh reviewers avoid seeing previous findings. In bounded tests, the C2 logic matched an independent model in 16,384 histories. The round-10 controls re-asked a pending question, kept a `needs_user` stop after confirming only its assumption, and escalated after acknowledgement of that specific question. - **The project recognizes limits of model-only checks.** It gives each reviewer explicit rubric criteria, prompts for a receipt, regression-tests copies and dispatch sites, and keeps a rubric evaluation suite with separate judge calibration. Coverage checks, Git history, worktree state, and the explicit handoff can independently corroborate some workflow claims. The Go gate's fresh temp file, exact thresholds, and atomic publication supported independent concurrent decisions in the local test. - **Several choices reduce operational coupling.** The npm installer has no runtime package dependencies. The small JS rule has an injectable I/O path and differentiated bad-input exit code. The role generator refuses to overwrite edited or user-authored ordinary files without a force flag, and the sync check catches divergence between canonical and packaged copies. ### Material weaknesses

| Priority | What the evidence shows | Operational implication |
| --- | --- | --- |
| P0 | **The adapter reports process completion separately from Git reality without surfacing their disagreement.** Both implement paths suppress Git failures. ## 8. Post-mortem: design pressures, accumulated tradeoffs, likely failure modes, and the highest-leverage improvements

**Design pressure.** Metaswarm adds a software-development protocol to hosts that already own model inference, agent context, tool permissions, and repository access. Markdown and shell helpers make the workflow portable, inspectable, and cheap to customize. BEADS gives humans and agents a shared place to reason about the work graph. Git provides a familiar, inspectable change record. Lean install dependencies help the common path. The host is also responsible for interpreting the cues that act as transitions, matching work against scope, deciding an occurrence has finished, and invoking the corresponding external mutation. The project deliberately spends complexity on roles, evidence, and quality control first. The underlying changes in the changelog support this interpretation. The migration from copied npm resources to plugins, the repair of BEADS command drift, the move to phase-specific roles, and the later executable review rule each narrowed a separate failure class. [Workflow and dependency corrections](repos/dsifry__metaswarm/CHANGELOG.md:90) [Phase-specific dispatch](repos/dsifry__metaswarm/CHANGELOG.md:125) [Plugin-era diagnostics](repos/dsifry__metaswarm/CHANGELOG.md:219) [Upstream version coupling](repos/dsifry__metaswarm/guides/workflow-enforcement.md:18)

**Accumulated tradeoff.** Improving written policies and mirrored copies made successful runs easier to specify. Semantic contracts still have multiple authors and interpreters: a host reads the role, another model reads a prompt, a shell script prepares its input, a reviewer explains failures, and the coordinator writes a normalized history. The checked-in tests catch copied-text drift and the JS rule logic. They cover fewer cross-stage claims such as “this is the exact commit the reviewer saw” and “this worker has stopped.” Provider CLI evolution, plugin host differences, and separate Git/BEADS state increase the number of partial successes. The timeout and logging bugs show the same pattern at a technical boundary: Bash can launch a command and print a result, but it does not give the caller transactional Git effects, bounded descendants, or atomic publication of a large record. The actual Go gate shows the stronger design at small scale: immutable input per run, independently recorded outcomes, and atomic publication of a derived artifact. [What drift checks prove](repos/dsifry__metaswarm/lib/sync-resources.js:391) [Policy decision scope](repos/dsifry__metaswarm/lib/review-rule.js:200) [Shared append path](repos/dsifry__metaswarm/skills/external-tools/adapters/_common.sh:649) [Independent evaluation state](repos/dsifry__metaswarm/templates/go-coverage-gate.go:121)

**Likely failure chains.**

1. **A worker's success does not establish the result the next phase needs.** The worker exits cleanly, but commit may have failed or the adapter's metadata is computed against the new tip. A reviewer then sees the newest commit, dirty patch, or an unrelated same-second payload. A strong rubric cannot remedy an incomplete change snapshot. A second independent validation based on the original work-unit base and real path manifest is necessary to catch the problem at present.
2. **Interrupted work can appear ready or still active in competing records.** A kill between commit and BEADS closure or between the active plan write and execution write leaves partially advanced local state. On resume, a persisted gate may have line-1 pass with missing completion information, or a pending clarification without the question payload. Replaying a write action blindly can cause duplicates, while assuming it already happened can strand dependent work.
3. **Retry can compound resource use.** A timed-out or cancelled caller can leave a worker or descendant. A replacement may get the same worktree or a truncated previous snapshot, and new health probes can hang outside the implementation timeout. Summary log loss makes the budget study weakest when there is concurrency. PR polling can add demand after an independent fan-out, and closing a “ready” shepherd may leave later actions unowned.
4. **Setup or delivery can drift even with a matching version.** A synchronous heal can restore an incomplete or unintended coverage command while appearing successful. A stable copy hash establishes content integrity relative to its source. It cannot attest to a complete source inventory, host capability, or matching shell semantics for pre-push and CI. The local deployment test needs to exercise the same typed contract at each boundary.

**Highest leverage.** Anchor every work unit and review to one immutable baseline, result identity, and path manifest. Put cancellation, process ownership, commit status, and raw-log association behind a small executable adapter contract. Then make restart reconciliation and idempotent side effects explicit across Git, BEADS, and host dispatch. Preserve the current prompt-level strengths where they add judgment, such as task sizing, requirement clarification, rubric-based review, and classification of credible consequences. A small executable layer can enforce what depends on identity and ordering while leaving those judgments to the host.
