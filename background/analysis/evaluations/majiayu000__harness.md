## 2. Core architecture and end-to-end control/data flow

### Control plane and identities

Harness is a Rust application server and a collection of Rust libraries. The important boundary is between `harness-server`, which translates requests and performs effects, and `harness-workflow`, which owns definitions, the transition validator, the PostgreSQL store, the command dispatcher, and the runtime worker contract. `harness-core` holds configuration, policy shapes, and interfaces. `harness-agents` implements the model and process adapters. `harness-sandbox` supplies isolation primitives. `harness-protocol` defines RPC and notification shapes, and `harness-observe` owns application events and export. The README's general architecture diagram predates some of the workflow-first migration. The HTTP submission route and workflow store establish current authority, while the older task store still supports startup and compatibility surfaces. [Workspace manifest](repos/majiayu000__harness/Cargo.toml:1) · [Workflow execution overview](repos/majiayu000__harness/README.md:765) · [HTTP submission route](repos/majiayu000__harness/crates/harness-server/src/http/http_router.rs:93) · [Compatibility task authority](repos/majiayu000__harness/AGENTS.md:84)

One accepted submission derives identities at different scopes. The project root resolves through the project registry and canonical path. A stable workflow ID identifies the subject in that project, for example an issue or a prompt submission. A submission handle is projected for clients, with a request ID retained separately. Each transition decision has event provenance. Each outbox command has its own deduplication key and dispatch generation. A runtime job has its own ID, kind, lease generation, and owner. Live thread and turn IDs identify interactive agent state. The workspace acquisition ID identifies one use of a worktree slot. These scopes allow one workflow to span several jobs and several retries without letting old cleanup target a later acquisition. Some operational stores can degrade with explicit status. HTTP starts dispatch, workers, recovery, reconciliation, cleanup, and watchdog loops. Different transports and intake sources converge on the execution service. 4. **Scheduling and dispatch.** The server acquires command claims from the durable outbox in bounded batches using PostgreSQL `SKIP LOCKED`. It applies per-project workflow policy, selects the runtime profile from the applicable default and activity overrides, resolves trust and isolation tier, and checks agent contract, fact-readiness, and budget barriers. The worker queue is a second claim boundary with its own TTL and priorities. Implementation and PR repair activities precede ordinary work, then periodic review, ordered by creation time within a band. Recent commands and jobs survive process restart. 5. **Local execution, workspace, and session.** A Tokio supervisor refills a bounded `JoinSet` of one-job ticks. Ordinary agent activities load project policy, take a worktree or source strategy, and acquire the repository lease as required. The server constructs a role-specific prompt packet with provenance and trusted parameters, resolves a backend, and opens a transient thread/turn. The turn loop normalizes messages, tool activity, approvals, failures, and usage. Lease loss feeds a watch signal into the executor. Workspace finalization waits for process cleanup and runs configured hooks before releasing or removing the acquisition. ### Persistence, observability, and extension surfaces

The workflow database combines append-only evidence with transactionally maintained state. A fresh server opens the materialized instance, command, job, and definition tables and resumes from durable rows. Reducer replay from recorded evidence is an audit/control path. Live ThreadManager maps, approval request routing, per-process permits, and in-flight adapter processes have different lifetimes. Durable transcript and proof reads are available independently of the live turn. ## 4. What it does well and poorly, with source evidence

### Strengths

- **The transactional outbox contains the hardest state changes.** The service can recover after losing an HTTP response or worker without relying on an in-memory task to reconstruct the next action. A reducer rejection, absent evidence, and an outdated command remain distinguishable. Reopened PostgreSQL tests carried decisions, follow-ups, transcript checksums, and workflow snapshots through new store instances. The terminal fence and provenance tests exercised refusal of stale writes. [Outbox transaction](repos/majiayu000__harness/crates/harness-workflow/src/runtime/store/submission_commit.rs:236) · [Immutable decision insert](repos/majiayu000__harness/crates/harness-workflow/src/runtime/store/decision_provenance.rs:58) · [Durable cases](repos/majiayu000__harness/crates/harness-workflow/src/runtime/tests/durable_store.rs:1)

- **Lease and cancellation requirements are explicit.** Remote workers get a strong generation-bound lease proof and a receipt for a lost renewal response. The server distinguishes a stopped workflow from an eval process that still owes physical cleanup. ## 8. Post-mortem: design pressures, accumulated tradeoffs, likely failure modes, and the highest-leverage improvements

The project's historical architecture moved from per-task execution controls and per-path stores toward one durable workflow authority. The storage RFC records catalog pressure from the old per-path schema model. That earlier observation belongs to the project maintainers' report, with no new production measurement here. The pinned code routes major service stores to shared namespaces, retains compatibility migrations, and runs a schema reaper. This explains both the clean workflow core and the number of branches needed to bring older observations, worktrees, task handles, and snapshots into the current control plane. [Storage history](repos/majiayu000__harness/docs/rfc-storage-layer-redesign.md:87) · [Fixed workflow namespace](repos/majiayu000__harness/crates/harness-server/src/http/builders/registry.rs:261) · [Orphan schema reaper](repos/majiayu000__harness/crates/harness-server/src/http/orphan_reaper.rs:24)

Lock ordering was another consequence of growth. Early dispatch and completion separately claimed their obvious nearest row, which formed an ABBA cycle when both reached the same workflow or its event sequence. The pinned design establishes one parent-first order and has a small retry policy for aborted SQL transactions. Foreign keys and shared sequence advisory locks make correct order part of the write contract. The two-actor tests show the cost of maintaining this system: even with a correct database wait graph, a stale monitoring snapshot can make the regression test say the actor never arrived. The right test oracle is a live connection or a refreshed snapshot with observed backend IDs. [Historical lock interleaving](repos/majiayu000__harness/crates/harness-workflow/src/runtime/store/lock_order.rs:43) · [Current event write path](repos/majiayu000__harness/crates/harness-workflow/src/runtime/store/transaction_helpers.rs:87) · [Lock-chain measurement](.majiayu-harness-review.Lv5TAtbZ/logs/lock-chain-live-observer.log)

The local renewal race is a consequence of solving a real earlier problem. Renewal must stay concurrent with execution and its wall-clock deadline because a blocked SQL renewal should never stop the executor from observing cancellation. The worker selects over the **entire** renewal future, including the database response, to preserve that property. But it also uses the most recently *acknowledged* expiry as an identity field for completion. The acknowledgement boundary is weaker than database commit. With a delayed reply, both behaviours compose badly:

1. The worker starts generation 1 with old expiry A and the model effect starts.
2. The database updates the generation-1 row to expiry B and commits. Its reply remains pending.
3. The executor returns success. The select drops the renewal future and returns expiry A from its local variable.
4. The store correctly refuses the A fence given live B. The worker categorizes the result as expired and persists a dead letter. The caller and scheduler see a job that is still running.
5. If no intervention occurs, the later lease expiry makes the work claimable again. A new attempt can duplicate external work whose first attempt succeeded.

The durable log preserves the result and the completion fence keeps a different owner's result from being applied. The unresolved case is uncertainty *inside the same valid epoch*. The local completion fence needs a stable claim token carried across renewals, or an explicit bounded reconciliation of an in-flight renewal outcome. The remote renewal protocol already illustrates the value of distinguishing same-request transport replay from new ownership. [Worker select](repos/majiayu000__harness/crates/harness-workflow/src/runtime/worker.rs:289) · [Atomic completion condition](repos/majiayu000__harness/crates/harness-workflow/src/runtime/store/activity_completion.rs:341) · [Remote renewal receipts](repos/majiayu000__harness/docs/runtime-host-model-spec.md:145) · [Observed event sequence](.majiayu-harness-review.Lv5TAtbZ/logs/fresh-workflow-controls.log)

Workspace safety introduces a similar distinction. The store owns whether a result may mutate workflow state. The workspace owner controls whether a specific local slot may be used, and the process supervisor controls whether a subprocess can keep writing. The system prefers waiting for process cleanup over refunding a permit to an unsafe workspace. That is the right fallback for a still-live process, but indefinite waiting, lease expiry, or hard process exit leave different parts of the system with different evidence of progress. Persisting an explicit cleanup obligation helps restart only if the new controller can map the old acquisition to the exact execution epoch and establish disappearance or isolation of the previous writer. A reviewed, durable disposition for stale results would close the gap left by preserving them without a regular consumer. A rollback-only database control verified the examined dead letter survived deleting its synthetic job and the catalog had zero dead-letter foreign keys. [Workspace cleanup claim](repos/majiayu000__harness/crates/harness-server/src/workspace_lease_store/cleanup_store.rs:213) · [Terminal cleanup worker](repos/majiayu000__harness/crates/harness-server/src/workflow_runtime_worker/workspace_terminal_cleanup.rs:99) · [DLQ retention control](.majiayu-harness-review.Lv5TAtbZ/logs/dead-letter-retention-control.log)

The product also favors high-priority interactive work and live visibility. That is useful at modest load. Under pressure, strict durable priorities can hide an increasingly old lower-band job inside a healthy-looking loop, while long-lived streams reread complete status history on the same control-plane database. Bounded batch claims, version-aware readiness, and tier/turn limits are appropriate levers. Their metrics should expose *work age by band, renewal acknowledgements, and cost per refresh*. A simple age-aware scheduler and seek query address the measured causes without replacing the PostgreSQL outbox or adding a separate broker. ## 10. Prioritized improvements and acceptance criteria

| Order | Change | Acceptance criteria |
| --- | --- | --- |
| 1 | Give each local claim a stable ownership token for normal completion and workspace transfer. Reject expired or replaced generations using the live persisted lease. Resolve ambiguous renewal outcomes without letting a delayed response block cancellation. | The COMMIT-reply hold scenario settles once with the same live owner/generation. An expired lease, reclaimed generation, and terminal cancellation still reject. A blocked SQL renewal remains interruptible and its transaction lock is bounded. |
| 2 | Validate a supported local TTL range and compute a renewal deadline with margin. Include preparation and database headroom. | Invalid TTL fails before a claim or supervisor spawn, including values beyond the clock library's supported range. Tests at the smallest supported TTL include preparation, two renewals, clock/driver jitter, and true expiry. A stable activity longer than one lease interval completes under the valid setting. |
| 3 | Fix portable binary freshness checks and validate that a successful probe emits one numeric timestamp. | Stock Linux and macOS runs distinguish fresh, stale, and unverifiable. Include a probe that emits output before failing, and confirm the live-server status and default-binary startup paths agree. |
| 4 | Make cancellation and shutdown part of the worker ownership lifecycle. Stop new claims, signal active owners, and account for completed, transferred, or durably quarantined work before service exit. Provide an operator-visible dead-letter disposition and a retention policy. | Fake process-group workers survive interruption tests correctly, and the shutdown receipt states whether cleanup was confirmed. A stale result can be inspected and either reconciled against current durable/external state or discarded with audit. Prune after the disposition window without losing evidence still needed for recovery. |
| 5 | Bound control-plane cost using seek-based SSE cursors and age-aware durable scheduling. Surface per-band oldest-ready age, queue residence, and live-versus-confirmed renewal state. | Caught-up refresh reads zero old events. Reconnect uses a bounded replay cursor. Periodic jobs receive a bounded share under an ongoing interactive stream. Capacity and starvation dashboards distinguish DB, executor, workspace, and provider waits. |
| 6 | Strengthen maintainability with standard offline test slices and measured fault injection. Pin the intended per-attempt behavior or make the live reload policy explicit. | An ordinary package build works with cached pinned dependencies and a disposable PostgreSQL endpoint.
