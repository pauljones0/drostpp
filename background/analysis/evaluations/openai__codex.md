## 2. Core architecture and end-to-end control and data flow

### Thread ownership, scheduling, and input

ThreadManager owns loaded threads and shared facilities and fronts a ThreadStore. StartThreadOptions carries config, lineage, history, environment choices, tools and extension inputs. CodexThread is the public command/event handle for a living Session. Startup resolves model and environment policy, acquires or creates storage when applicable, reconstructs or seeds history, constructs services and launches the submission loop. A new rollout may defer file creation until there is work to persist. An initialization guard owns provisional persistence until startup commits. A matching live resume reuses the current runtime and writer. A different rollout path for the same live ID is rejected. [Thread manager and options](repos/openai__codex/codex-rs/core/src/thread_manager.rs:327), [live resume](repos/openai__codex/codex-rs/core/src/thread_manager.rs:2700), [session startup](repos/openai__codex/codex-rs/core/src/session/mod.rs:714), [startup commit](repos/openai__codex/codex-rs/core/src/session/mod.rs:1157), [persistence guard](repos/openai__codex/codex-rs/thread-store/src/live_thread.rs:57).

Typed Submission/Op input enters a channel of capacity 512. The session actor serializes submission handling and reacts to tree shutdown, model catalog and mailbox updates. Regular, compact and review tasks run separately. This lets the actor deliver steering, approvals, elicitation responses and dynamic tool replies while a task awaits them. A one-shot returns typed admission results. Event/EventMsg output uses an unbounded channel with one logical reader per runtime. CodexThread documents the finite-drain boundary needed when changing readers. Start-or-steer, start-if-idle, and steer-only express different admission intents. An idle start reserves a slot before async preparation. A steer validates the regular task and expected turn ID and checks any requested output schema against the current turn. Steering appends input under the turn's lock and can cancel a per-step preemption token. The finalizer's last check for queued input and removal of the task share the same lock. Work admitted near the finish boundary can extend the same turn if it wins that check. An accepted submission acknowledges admission, with recording and inference following later. ### The turn and request loop

RegularTask opens the turn lifecycle and enters run_turn. The task can compact the existing window first. It captures the first step, records initial context, resolves relevant skills/plugins and required MCP dependencies, inspects input hooks and records accepted prompts and extension injections. The main loop drains permissible steering and mail, records world-state and preference updates, clones context, and opens a model request. The first explicit prompt gets priority over already queued input. Following compaction, the turn tracks whether an existing continuation should run before pending input. Stop and after-agent hooks can introduce follow-up work. TurnContext carries turn identity, constraints and preferences. Capture reads step settings and environments under active_turn then state and awaits readiness after releasing both. Speculative capture can prepare a fallback without replacing the active snapshot. The call is recorded before dispatch. RespondToModel errors get a shaped model-facing result. Fatal dispatch and join errors have a separate typed path. ## 5. Weaknesses and evidence status

Priorities reflect impact on ordinary operation, recoverability, evidence confidence and the breadth of affected paths. A reproduced component defect is backed by execution of the cited production code in a bounded control. A source-supported risk has a reachable or plausible call path but lacks a full-workspace reproduction. The audit in §8 tests alternative interpretations.

### W1. P1, fatal direct-tool errors disappear at the result drain

**Reproduced component defect.** ToolCallRuntime turns FunctionCallError::Fatal into CodexErr::Fatal. A dispatch-task panic/join failure can take the same route. The direct sampling drain accepts Result values but returns unit. On an error, it invokes error_or_panic. Debug assertions cause a panic, and the release branch logs and discards the error. The code then returns the sampling outcome it computed before draining. In the source-extracted control, the same error between two normal outputs raised a Tokio JoinError panic in debug after saving the first output. In release the drain saved both normal outputs, returned to its caller and supplied no fatal outcome. This is a mismatch between the producer's typed result and the consumer's lifecycle. [Fatal conversion](repos/openai__codex/codex-rs/core/src/tools/parallel.rs:173), [dispatch join failure](repos/openai__codex/codex-rs/core/src/tools/parallel.rs:500), [drain](repos/openai__codex/codex-rs/core/src/session/turn.rs:2976), [build-mode branch](repos/openai__codex/codex-rs/core/src/util.rs:81), [outcome after drain](repos/openai__codex/codex-rs/core/src/session/turn.rs:3928).

**Production impact by trace.** A registered tool can produce a fatal error after successful input decoding. For example the valid clock tool call can propagate a host clock read failure in its fatal mode. A separately injected extension or tool task has ordinary failure modes at the same boundary. If upstream completed and accounting succeeds, a release turn may resample after the failed call rather than enter the explicit fatal path. The function-output normalizer can repair an unmatched call with synthetic aborted output, but that repair loses cause and does not restore the intended terminal status. The sample path consumes fatal errors explicitly if it ever receives them. In debug the owning task can panic before its finalizer. The task wrapper has no join supervisor on the success/ordinary completion path, while explicit abort handles a join failure. A stuck active slot or missing terminal event is consequently a source-supported symptom. [Valid handler failure](repos/openai__codex/codex-rs/core/src/tools/handlers/current_time.rs:101), [explicit fatal handling](repos/openai__codex/codex-rs/core/src/session/turn.rs:2158), [missing output normalization](repos/openai__codex/codex-rs/core/src/context_manager/normalize.rs:63), [turn task wrapper](repos/openai__codex/codex-rs/core/src/tasks/mod.rs:457), [abort observes join](repos/openai__codex/codex-rs/core/src/tasks/mod.rs:1232).

### W2. P1, MCP elicitation time has two inconsistent publications

**Reproduced accounting defect and source-supported publication race.** The active-time timeout checks the latest bool from Tokio watch. When enter and exit coalesce before the consumer polls, the changed branch sees false, fails to deduct the elapsed active interval, and begins a fresh timer with the previous remaining duration. A 50 ms timer that had already spent 45 ms active was still pending at 52 ms in a paused-clock control. It expired by 97 ms. A no-elicitation control and a pause observed at both boundaries expired on their original active budgets. Independently, the atomic guard count and the bool publication are separate operations. A last-exit can decrement to zero, a first-enter can increment to one and publish true, and the old exit can publish false afterwards. A forced interleaving executed the destructor’s two operations around a normal enter with pinned Tokio and observed the stale false state with one live guard. That case establishes the allowed ordering using the exact atomics and watch sender. It deliberately splits the destructor to avoid depending on an OS scheduling coincidence. A stall during an outstanding approval or form can then spend the operation timeout while the guard is active. The coalescing bug can instead extend it. [Counter, guard and publication](repos/openai__codex/codex-rs/rmcp-client/src/rmcp_client.rs:211), [timeout loop](repos/openai__codex/codex-rs/rmcp-client/src/rmcp_client.rs:252), [caller](repos/openai__codex/codex-rs/rmcp-client/src/rmcp_client.rs:1878).

**Production impact by trace.** Legacy elicitation handlers can share connection-level pause state. Modern call-specific callbacks use a separate pause state, which narrows the scope but still uses the same helper. Short overlapping callbacks may coalesce before the timeout loop runs. Both bugs need the relevant scheduling order and an operation timeout. The deterministic operation sequence and concurrent stress bound the conclusion to reachability. Field frequency is unknown. The durable effect depends on whether the server call and its host callback are still outstanding. [Per-call and connection-local scope](repos/openai__codex/codex-rs/rmcp-client/src/rmcp_client.rs:1094), [pause guard around callback](repos/openai__codex/codex-rs/rmcp-client/src/elicitation_client_service.rs:183).

### W3. P1, terminal lifecycle and writer closure can disagree

**Source-supported recovery risk.** RolloutRecorder deliberately stays alive after a failed shutdown drain so its owner can retry without losing queued items. LocalThreadStore removes its live writer only after successful recorder shutdown and subsequent work. The ordinary session shutdown handler logs and emits an error after LiveThread shutdown fails, then still publishes ShutdownComplete and exits its submission loop. SessionIo::shutdown_and_wait waits for loop termination, whose shared future drops the JoinHandle result, and returns success. The manager can consequently remove a thread as completed while the LocalThreadStore still owns the writer. Later create/resume using that same store checks that no live recorder exists. The relevant failure is a persistence fault surviving the recorder's own reopen/retry cycle, such as a temporary storage interruption around the final drain. The lifecycle leaves a writer capable of retrying while dropping its normal session owner. The stricter suspend/handoff path propagates failure and requires writer closure. Tree shutdown has its own detailed failure collector. An application may observe the separate error, and a host retaining the store has explicit operations to retry or dispose the writer. ### W4. P2, writer-lock contention can block an async executor worker

**Reproduced scheduling mechanism with a source-traced call path.** Local create and resume enter synchronous acquire_writer_lock from async code after taking a per-thread async guard. The lock helper retries shared coordination with a 50 ms blocking thread sleep and a 30 s bound. Taking a per-thread writer lock already owned by another writer fails promptly. The blocking path is contention on the home-wide coordination lock, for example while publishing an encoded compressed rollout. The code performs encoding/verification before the publication lock, which limits typical hold time. In a local exact-helper control a peer task on a current-thread Tokio executor made no progress until the contended call returned. It did progress when the same helper ran on the blocking pool. Both paths used real kernel locks and the same holder handoff. [Async create/resume calls](repos/openai__codex/codex-rs/thread-store/src/local/live_writer.rs:65), [synchronous mapper](repos/openai__codex/codex-rs/thread-store/src/local/mod.rs:402), [coordination acquisition](repos/openai__codex/codex-rs/rollout/src/writer_lock.rs:46), [blocking loop](repos/openai__codex/codex-rs/rollout/src/writer_lock.rs:137), [compression publication](repos/openai__codex/codex-rs/rollout/src/compression.rs:962).

The effect on a multithread runtime depends on simultaneous contention and worker availability. A single short hold is usually a modest delay. A suspended holder, slow filesystem or burst of concurrent resumes can consume workers that would otherwise process independent work. The control isolates scheduler behavior. It supplies neither a production latency estimate nor evidence of continuous cross-process lock contention.

### W5. P2, streaming preserves partial accepted work but lacks an exact-once side-effect boundary

**Design tradeoff and source-supported operational risk.** The default streaming mode can dispatch an approved call before response.completed, with work persisting into the outer retry or abort history. Retry uses current accepted history and tools are ordered when collected. This avoids blindly replaying a fixed request. It still cannot know if a downstream process or service completed an operation whose result failed to return. Call reservation limits concurrent duplication, while the seen-ID filter records provenance and bounded freshness evidence. Those mechanisms are not a persistent effect ledger across retries/resume. A legitimate fresh ID for the same operation may be proposed again when the previous outcome is unknown. Buffered mode moves initial tool admission after settlement and avoids early effects from failed/unsettled responses, while an already launched tool still has its own uncertainty. A sandbox-denial retry also begins a separate attempt with no general rollback. ### W6. P2, the downstream event queue has an unbounded backlog for a live slow consumer

**Design tradeoff.** The bounded submission and SSE event channels protect their immediate producers, but the public per-thread event channel is unbounded. Delivery sends the complete event after calling persistence and trace where applicable. Dropping the receiver makes sends fail cleanly, and a healthy dedicated event reader drains common workloads. A slow reader that is still attached allows a growing backlog of deltas, raw response items and lifecycle events. Legacy compatibility emissions and concurrent tools add producers. The core handle assumes a single logical reader, which makes clear ownership possible but gives a host no pressure/drop/coalescing contract at this boundary. A channel-only control held the reader open and queued 4,096 items without pending on send. The production-sized submission channel blocked at 512. ## 9. Post-mortem and prioritized improvements

The main design pressure is combining an interactive session, low-latency streaming, real side effects, provider variations and replayable history. One logical turn may contain multiple in-flight protocol views, journal writes, preserved process sessions and message queues. The implementation keeps authority snapshot-based at admission and relocates expensive or durable work into separate owners. Over time, configuration variants, scoped captures, admission modes, explicit model routing, post-request hooks and retention rules have made the central turn a coordination point for almost everything. The places with explicit provisional ownership and single commit points tend to be the clearest. Errors that cross independently cancellable futures are the least predictable.

1. **P1, preserve one typed outcome through direct dispatch and turn supervision.** Make the output drain collect fatal errors while finishing cancellation or collection for siblings. Define a precedence among user abort, transport/accounting and tool-fatal errors. Feed the result into the actual terminal decision and supervise abandoned/panicked turn tasks so active slots and waiters get released. A credential-free regression should run a valid direct tool whose registered adapter fails fatally, assert terminal error and matched persisted facts in both debug and release, then successfully start a second turn. Exercise a concurrently completing sibling and a simultaneous cancellation. [Drain](repos/openai__codex/codex-rs/core/src/session/turn.rs:2976), [finalization](repos/openai__codex/codex-rs/core/src/tasks/mod.rs:788).
2. **P1, publish MCP pause accounting atomically with timing evidence.** Serialize active-count changes and their published pause state. Include accumulated pause duration or transition times with each state publication so consumers can compute remaining active time even after coalescing. Validate simultaneous first-enter/last-exit, nested guards, early cancellation, closed receivers, and multiple coalesced pauses. Keep the positive control where a long observed form uses no active timeout budget. [Active-time implementation](repos/openai__codex/codex-rs/rmcp-client/src/rmcp_client.rs:211).
3. **P1, distinguish actor termination from durable writer ownership transfer.** Return a typed outcome covering loop termination, writer drain/close, and retained recovery responsibility. Where the writer deliberately remains live after a failed drain, transfer it to an explicit retryable owner and report that outcome to the manager and eviction caller. Cover a storage outage that survives both recorder attempts, then repair and resume in the same process. Check both root and v2 eviction, without requiring blind discard. [Shutdown path](repos/openai__codex/codex-rs/core/src/session/handlers.rs:435), [bounded shutdown report](repos/openai__codex/codex-rs/core/src/thread_manager.rs:1751), [v2 eviction](repos/openai__codex/codex-rs/core/src/agent/control/residency.rs:56).
4. **P2, remove blocking coordination from async workers.** Use a cancellable async lock wait or a bounded blocking owner that retains writer/cleanup responsibility across caller cancellation. Keep the same ordering rules for publication and create/resume. Measure responsiveness of unrelated turns during forced coordination contention instead of inferring it from the 30 s maximum. [Blocking acquisition](repos/openai__codex/codex-rs/rollout/src/writer_lock.rs:137).
5. **P2, make accepted/unknown/settled operations explicit.** Preserve the low-latency streaming choice with clearly typed outcomes for already accepted effects, uncertain outcomes and replay repair. Give side-effecting tool implementations a request identity/idempotency option and prevent automatic resubmission of an explicitly uncertain, irreversible operation. Use a loopback fake and benign local file counter for failure after a completed tool item, after result publication, and between checkpoint/close. Buffered mode should continue to gate dispatch on settlement. [Streaming mode](repos/openai__codex/codex-rs/config/src/config_toml.rs:750), [result release](repos/openai__codex/codex-rs/core/src/client/response_delivery.rs:117).
6. **P2, bound live observer buffering and reduce large-history preparation.** Document receiver lag and durable resynchronization. Coalesce suitable progress deltas, preserve required reply and terminal events, and expose buffer depth/high-water metrics. Add a preflight estimate for the new prompt and context before compaction and measure request latency/memory across large retained history for SSE and WebSocket reuse. Keep input accepted/rejected facts so a failed fit check has a clear recovery path. [Output queue](repos/openai__codex/codex-rs/core/src/session/mod.rs:771), [pre-turn compaction](repos/openai__codex/codex-rs/core/src/session/turn.rs:256).
7. **P3, reduce the number of transitions that only a full runtime build can verify.** Extract a request reducer with typed lifecycle phases and effect intents, preserve the single Session owner, and expose narrow conformance targets for retries, pending input, tool failure, interrupted compaction and shutdown. Keep deterministic offline scenarios near their owners. Make capability/configuration snapshots discoverable in service-specific fields while retaining a defined extension publication order. Resolve or document probe/commit normalization semantics. [Main turn loop](repos/openai__codex/codex-rs/core/src/session/turn.rs:218), [extension registry](repos/openai__codex/codex-rs/ext/extension-api/src/registry.rs:22), [constraint operations](repos/openai__codex/codex-rs/config/src/constraint.rs:149).

The strongest reason to keep the current architecture is that changes can be scoped to these transition contracts. A wholesale rewrite would risk changing the meanings of replay, tool admission and parent/child delivery simultaneously. Focused ownership and error-handling changes can improve reliability while preserving the production request/snapshot model and storage format.
