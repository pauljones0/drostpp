# Pi core runtime evaluation

The coding CLI and SDK are built around an injectable agent loop and a replayable JSONL history. The separate Durable runtime adds transactional admission, persisted phases, and cancellation ownership for p2's background and one-shot agents. p3 at this revision supplies session facts and worker routing. The highest-priority changes are to serialize session control operations and separate observer failures from persistence. The controlled probes reproduce four defects and one tool declaration contract inconsistency. ## 2. Core architecture and end-to-end control/data flow

### Coding CLI and SDK

1. **Bind the workspace and rehydrate history.** Startup services resolve cwd, user configuration, resources, and `ModelRuntime`. The SDK builds the manager's active session context before selecting a model and thinking level. A supplied model wins. Otherwise session metadata, configured availability, and defaults govern fallback. The selected virtual model's identity is explicit session metadata because assistant entries record the physical model that answered. The SDK gives the core `Agent` a model stream backed by `ModelRuntime`, an extension context transform, queue settings, and a session ID. `AgentSession` subscribes to the agent immediately, installs tool and request hooks, then builds the current prompt and loadout. [SDK construction][sdk-create] · [SDK model binding][sdk-agent] · [Session construction][session-init].
2. **Admit input and assemble the starting messages.** An extension slash command may consume input directly. The general input hook can transform or handle the message before skills and prompt templates expand. An active run needs a steer/follow-up decision. `prompt()` counts async preflights to guard tree navigation. Once a trigger reaches `_startRun`, the session marks the run busy before compaction and `before_agent_start`. It picks the active system sections and tools, normalizes images against model limits, and appends the user, queued next-turn context, and extension messages. Resource discovery contributes inherited project instructions, skills, and normalized tool guidelines. The prompt builder keeps structured sections whose updates can be stored as positional system messages. [Prompt admission][session-prompt] · [Run admission][session-start] · [Run preparation][session-prepare] · [Project context discovery][resource-context] · [Prompt sections][system-prompt] · [Extension prompt contract][extension-prompt].
3. **Separate working state, persisted context, and on-wire messages.** The in-process `Agent` takes a shallow run snapshot and owns the run's abort controller. `runAgentLoop` emits starting messages and computes executable tool declaration changes. In the coding harness, `prepareRequest` rebuilds from the manager before every model call. Virtual routing chooses a model and thinking level per request and can persist branch-local routing state. Long virtual contexts are checked against the routed model. Ephemeral context handlers, conversion of custom messages and summaries into user-role context, image policy, and transcript normalization happen before provider dispatch. `Models.streamSimple` resolves provider/auth and merges options before returning normalized deltas. Adapters get explicit support for replaying ordered system instructions, declaration lifetimes and tool-result pairing. [Agent snapshots][agent-snapshot] · [Core declaration and stream mapping][core-declarations] · [Canonical request projection][session-projection] · [Message conversion][message-conversion] · [Transcript utility][ai-transcript] · [Tool declaration modes][ai-tool-state] · [Model dispatch][ai-dispatch].
4. **Publish deltas and execute completed calls.** Model events include a starting partial, text/thinking/tool-call updates, and a terminal result. Pi updates its working message as these arrive and reduces finalized messages to state before notifying awaited core listeners. A complete response's tool calls flow through name resolution, prepare-arguments normalization, schema validation, a preflight hook, execution, and a post-result hook. Unknown, invalid, blocked, and aborted calls still get typed error results. A truncated assistant response fails the whole apparent tool batch before executing any call. Parallel tool mode reserves preflight in source order, runs prepared calls concurrently, and emits completion as each finishes. Final tool-result messages are emitted in call order. Any tool marked sequential makes its batch sequential. `runToolCall` lets nested callers reuse the same validation and hooks. [Stream reduction][core-stream] · [Tool loop and truncation][core-turn] · [Parallel batch][core-parallel] · [Preflight][core-preflight] · [Nested call entry][core-nested] · [Agent event reducer][agent-reducer].
5. **Commit the conversation boundary and decide what comes next.** The coding session applies extension `message_end` replacement and notifies SDK subscribers before appending records. The turn-end boundary then has entry IDs to refer to and can propose structural changes. Pending custom context is flushed at a complete turn boundary to avoid interleaving a tool call and its result. Steering drains at the next request boundary, and follow-ups drain when the loop otherwise finishes. The host may continue after a low-level `agent_end` for a retry, overflow recovery, or queued work. The extension-facing `agent_before_settle` can append entries and request continuation. `agent_settled` is the notification after that policy loop, and actions requested from inside it are deferred until listeners finish. [Event and persistence path][session-events] · [Boundary drafts][session-boundary] · [Queue scheduling][core-queue] · [Post-run path][session-post-run] · [Settled dispatch][session-settled] · [Extension lifecycle contract][extension-order].
6. **Resume at the transcript boundary.** The CLI opens the JSONL file, validates the header, migrates old formats, normalizes incomplete lines when appropriate and rebuilds its index and active branch. Raw entries have stable IDs and parent IDs. Recovery edits and compactions affect the projection and leave the raw history available. Session replacement first settles the old activity, runs shutdown handlers, invalidates old contexts, then rebuilds cwd-bound services and rebinds the host. The CLI can reconstruct context and start a new request. It does not checkpoint an arbitrary running tool body or an in-flight provider stream. [Session format][session-format] · [Path and projection][session-index] · [Streaming JSONL reader][session-read] · [Session lifecycle owner][runtime-teardown] · [SDK session contract][sdk-docs].

The stdio RPC boundary attaches a JSONL line reader. Command IDs correlate responses and allow independent commands to overlap. A prompt reports accepted/queued/handled after preflight and emits the model events separately. The startup and shutdown path does not run in the model loop. This is an actual embedding entry point where lifecycle races can be exposed, independent of UI ordering. [RPC prompt][rpc-prompt] · [RPC input and concurrency][rpc-dispatch].

### Durable and p2

1. **Admission is itself a durable mutation.** `HarnessImpl` owns a `SessionImpl`, one storage failure guard, a scheduler, submissions, views, and a registry. `Conversation.submit` takes an input, standalone write, or explicit continue. A conversation-scoped request ID deduplicates admission and catches reuse across submission types. For idle runnable input, a commit records the input, marks the run, and creates a generation task. A busy conversation durably queues steering or follow-up with its delivery policy. A common mutation line orders these changes and protects state from concurrent external callers. `Submission.wait` checks status and registers on that line to avoid missing a completion. [Harness assembly][durable-assembly] · [Submission wait][durable-wait] · [Admission rules][durable-admit] · [Run creation][durable-start].
2. **The task phases carry the restartable boundary.** Generation prepares context through an entry cutoff, replays system sections, resolves current model/tools, and records options and thinking level in the request checkpoint. A blocking compaction is an owned child phase. A background compaction may run while the request proceeds. Request and poll work outside the mutation transaction. The stream writes throttled live-document changes with a bounded persistence delay. Terminal classification writes usage, assistant artifacts, and the next phase or settled state together. If tool work follows, stable task IDs connect the generation to each call and its result. A killed process can recover from committed intent and durable handles, or charge an interrupted attempt and follow policy. The scheduler distinguishes pending, claimed/running, waiting, sleeping, blocked, completing, and terminal work using records rather than process-local promises alone. [Checkpoint shape][durable-phases] · [Request preparation and cutoff][durable-request] · [Partial delivery][durable-partials] · [Classification][durable-classify] · [Recovery][durable-interrupted] · [Durable design invariants][durable-invariants].
3. **Separate storage order, provider order, and ownership.** Tools may finish out of order. Context derivation restores results to their issuing call order and separates tool-round sequencing from commit order. Transaction-scoped documents are draft state that is revoked at the transaction boundary. `beforeRequest` and other hooks run against a scheduler phase and a registry snapshot. Terminal child outcomes drive parent continuation. Scheduling, abort marks, and recovery all use the same ownership tree across tasks and conversations. [Context result ordering][durable-order] · [Task ownership rules][durable-structured] · [Registry composition][durable-registry] · [Session commit path][durable-commit].
4. **The p2 worker owns a real session runtime.** Server-side session metadata controls worker placement. The worker opens its own Chord store, starts a Durable harness after model configuration is available, contributes extensions, checks location, validates the root's selected model, and resumes scheduling after plugins have loaded. Native handles close with the host. Its model/settings proxy reads updated plugin contributions, and extensions can appear or disappear through a Chord registry snapshot. The worker publishes transcript and live state to consumers through watches and reports server-facing facts without a second writer to its store. [p2 store binding][p2-store] · [p2 model and harness setup][p2-harness] · [p2 start and close][p2-worker-start] · [p2 extension snapshots][p2-ext-registry] · [Single-writer guidance][p2-practices].
5. **Delegation is a p2 application policy over Durable.** `subagent spawn` creates a named conversation under a background anchor and separately schedules a durable reporter. The child has a model, instructions, cwd/environment, thread, and tool selection constrained by the caller's capabilities. The reporter submits the child input under a stable request ID and reports back to the originating branch under another. The child entry and report are independently deduplicated. Queued child input after failure is withdrawn if the child is idle and it still cannot be placed. One-shot `agent` uses a child owned by the calling task, persists the child ID, deduplicates submissions, validates the JSON answer, and makes up to three attempts. The two ownership choices explain why a normal parent stop can leave a named child running and cancels a foreground one-shot. [Background anchor][p2-anchor] · [Durable reporter][p2-reporter] · [Child creation][p2-spawn] · [One-shot agent][p2-one-shot] · [Structured ownership][durable-structured].

The p3 route starts a session worker through Chord when a known session's worker object is needed. The sessions plugin has a server facet for stored facts and a worker facet that follows them. The worker component associates exit publication with the server store, preserving the order of queued writes from the worker and its exit. The supervisor holds one lock per data directory, restarts a process that had successfully listened and then crashed, and uses capped exponential backoff. Pi-ai and Durable appear as development dependencies. The checked-in runtime facet provides no generation, tool-call or compaction entry point. [p3 route][p3-route] · [p3 worker manager][p3-workers] · [p3 sessions worker][p3-worker] · [p3 manifest][p3-pkg] · [p3 supervisor][p3-supervisor] · [Current p3 slices][p3-slices].

## 3. Why the design works and governing invariants

- **Canonical state is an entry projection.** A CLI request can be reconstructed from the committed branch plus explicitly transient provider transformations. Replaying tool declarations and prompt sections through history preserves provenance and lets adapters exploit common prefixes. Working status, partial messages, and original attempts remain separate from the model-visible view. On the Durable path, the checkpoint cutoff identifies which entry prefix was prepared, and phases tie the request to a documented, persisted intent. [CLI projection][session-projector] · [CLI canonical context][session-projection] · [Transcript normalization][ai-transcript] · [Durable request checkpoint][durable-request].
- **A result must answer its call.** Tool-call IDs link artifacts. Parallel completion order is useful to observers, and source order is useful to the model. Blocking and validation errors get model-visible result records, and ordinary cancellation still produces artifacts for unstarted calls. Retry omission takes away the failed call and matching results together. Recovery from an interrupted write may need a synthetic result. The declared and executable sets normally have a common source at the tool-delta boundary. [Core preflight and outcomes][core-preflight] · [Parallel result ordering][core-parallel] · [Recovery omission][session-omit] · [Provider-side pairing][ai-orphan-repair] · [Durable abort][durable-abort] · [Durable tool order][durable-order].
- **Lifecycle phases are fences with different strengths.** A core `agent_end` terminates the low-level run, and `Agent.waitForIdle()` includes awaited listeners. Session settlement includes recovery and the pre-settle boundary. The consumer of a raw loop instead observes asynchronous records and supplies its own completion work. Durable distinguishes the answer's committed acceptance from all owned tasks draining, so `Submission.wait()` and `Conversation.waitForIdle()` also have different meanings. [Agent lifecycle][agent-lifecycle] · [Raw API contract][agent-readme-low] · [SDK settle contract][sdk-events] · [Durable handle wait][durable-wait] · [Owned work completion][durable-structured].
- **The durable effect boundary is explicit.** Record intent, make the external call, then record its outcome. A provider may already have charged for an interrupted unacknowledged request. Reopen has enough information to retry, poll a known deferred handle, or mark interruption. The runtime guarantees its own commit ordering, while adapter semantics determine whether effects beyond storage can be idempotent. Tool definitions declare replay policy, and unsafe effects need external idempotency or recovery-specific handling. [Effect sandwich][durable-effect] · [Generation interruption][durable-interrupted] · [Tool replay path][durable-tool] · [Durable commit invariants][durable-invariants].
- **Extensions have deliberate execution points.** CLI input, before-run, model-context, payload/response, tool, turn-boundary and shutdown hooks operate on different state. Ordered result folds and per-hook validation allow composition. In Durable the registry snapshot and per-phase `Runtime` bind extensions to a task version and invocation. At p2 the server owns placement, each worker owns its content, and selective reports cross that boundary. [CLI hooks][extension-order] · [Boundary contract][extension-boundaries] · [Durable registry][durable-registry] · [p2 ownership guide][p2-practices].

## 4. Strengths

**The smallest layer has a useful job.** Agent-core owns loop scheduling, stable message/result ordering and optional lifecycle state. Tests exercise the pure loop independently of any provider registry or disk. Its typed injectable stream and provider-neutral transcript let both coding-agent and Durable share provider work without forcing Durable through coding-agent's mutable session object. Pi-ai deliberately keeps its root independent of bundled model catalogs and concrete provider implementations. This matters for embedding and for the offline recovery in this evaluation. [Agent-core entrypoint][agent-entry] · [Agent-loop tests][agent-tests] · [AI root][ai-index] · [Durable request path][durable-request].

**Parallel tools preserve context semantics.** Sequential validation and preflight make prompts and policy checks predictable. Allowed tool bodies can overlap. A completed batch produces stable report order, including error artifacts for blocked or truncated calls. Code mode and other nested callers can route through the same pipeline and record parent IDs, per-call timing and aggregate usage. Same-path file mutations have a separate in-process queue that uses canonical paths where present. [Tool execution types][agent-types] · [Truncation][core-truncation] · [Parallel commit order][core-parallel] · [Nested records][nested-tools] · [File mutation queue][file-queue].

**The CLI exposes a small, understandable durable transcript.** A user sees history survive the first request failing because the first user input triggers the initial disk write. An unusual partial tail doesn't prevent reopening valid earlier records. Existing formats are migrated. Projection preserves original provenance for edits, forks, summaries, and retries, and context usage discounts measurements invalidated by later edits. Saving failure artifacts in raw history while omitting them from retry context makes diagnosis possible after the fact. [JSONL append][session-writes] · [JSONL read][session-read] · [Session versions][session-format] · [Projected token accounting][compact-estimate] · [Recovery omission][session-omit].

**Compaction preserves structural context.** The CLI selects boundaries from the effective projection, keeps a recent tail, handles cutting inside a long turn with a prefix summary, and snapshots system state so future requests get a coherent loadout. It rejects broken summary results and accounts for summary usage. Durable expresses compaction as a task that can finish immediately, queue behind a run, be marked stale after a reset, or block generation at the configured threshold. These choices avoid putting a long model call under a storage transaction. [CLI compaction preparation][compact-prepare] · [CLI compaction commit][session-compact] · [Durable compaction task][durable-compact] · [Durable stale and concurrent compaction tests][durable-compaction-tests].

**Durable makes recovery and delegated ownership first-class.** The input admission, live view, run checkpoint, and child ownership show how the conversation got into its current state. SQLite close/reopen tests exercise streaming interruption, waiting tasks, deferred polls, and settings snapshots. The scheduler can park a tool on a signal or a wait condition and resume from persisted state. Background ownership and request-ID deduplication give p2 a reusable basis for named subagents instead of requiring every plugin to reinvent worker supervision. [Durable checkpoints][durable-phases] · [Durable recovery tests][durable-recovery-tests] · [Durable task scheduler][durable-scheduler] · [p2 background tasks][p2-reporter].

**Durable Code mode preserves the script's effect boundary.** The VM restarts from recorded initialization and receives results from a journal in original delivery order. Nested calls reattach to stable task keys. A journal entry precedes delivery, and the script's acknowledged call count guards what a later replay may launch. A module version, VM fingerprint, deadline or call divergence can stop replay. This costs extra commits per sequential result and makes the restart guarantee concrete. [Runtime journal and replay contract][durable-codemode] · [Worker lifetime][codemode-host].

## 5. Weaknesses and evidence status

| ID | Classification | Finding and reachable scope |
| --- | --- | --- |
| F1 | Reproduced defect | Exported `agentLoop` and `agentLoopContinue` leave their returned iterators and result promises pending when `prepareRequest` rejects. Their internal discarded promise only has a fulfillment handler, so the rejection reaches the process as unhandled. The same callback through `Agent` is translated into an error assistant and reaches idle. |
| F2 | Reproduced defect | A synchronous SDK `AgentSession.subscribe` callback that throws during a successful assistant's `message_end` prevents that answer from being recorded. The agent catches the observer error and may persist a synthetic error at the same logical point. A real in-process provider already completed the request. |
| F3 | Reproduced defect | Two concurrent `AgentSession.compact()` calls on an idle, compactable session overwrite one shared controller. When the first finishes, the session reports idle while the second is still pending and cannot cancel it. The second fails dereferencing `signal`. RPC dispatch has a parallel path to the same method. |
| F4 | Reproduced contract inconsistency | An embedding caller can replace `context.tools` from the typed `prepareRequest` hook. The next request still declares the previous set because declarations were written before the replacement. Model calls to a removed tool return `Tool … not found`; the next boundary reconciles the declaration. The normal coding-agent loadout path has its own update hooks and is outside this repro. |
| F5 | Reproduced defect | Two overlapping SDK `AgentSessionRuntime.newSession()` calls can both succeed and bind. An earlier-started factory that completes last overwrites the already bound session without shutting it down or invalidating its context. |
| R1 | Source-supported risk and stated tradeoff | CLI turn artifacts and boundary draft entries use sequential JSONL appends. A crash between assistant and results can leave a complete-looking assistant before its external effects and results have been recorded. Recovery has no atomic tool-run checkpoint across that boundary. Multiple successful writes also incur synchronous I/O. |
| R2 | Measured structural cost, operational impact unmeasured | CLI projection walks the entire active branch twice even when a recent compaction limits the resulting messages to three. `declareToolChanges` independently replays tool deltas. A longer retained branch raises work per projection. The experiment counts index reads and leaves latency and production throughput open. |
| T1 | Tradeoff | Extensibility keeps CLI features out of the loop, while many mutable hooks operate at tightly ordered boundaries. Awaited callbacks support useful barriers but a slow extension or observer can delay forward progress. The raw EventStream is a queue without producer backpressure, unlike the awaited sink. |
| T2 | Tradeoff | Durable commits across records give stronger local recovery and cancellation ownership. The scheduler, phase transitions, observers, storage adapters and migrations introduce more places to reason about progress. Context/device behavior is still application-dependent and an external effect can be uncertain across a crash. |
| U1 | Unresolved | Deployed provider wire semantics, live credential lifecycle, cross-device p2 behavior, file-system power-loss, and workerd store conformance were outside the exercised profile. The offline package bootstrap had missing exact artifacts. |

F1 is reachable using typed, documented preparation alone. `StreamFn` and several other callbacks explicitly require normalizing failure into a returned value. `PrepareRequest` has no such restriction, and the product itself installs a request preparation hook whose virtual routing can reject. The fail-to-settle is specific to the raw convenience wrappers. The test held all provider activity out of the failing path. [Raw start][core-raw] · [Raw continuation][core-raw-cont] · [PrepareRequest type][prepare-contract] · [Provider callback contract][agent-types] · [Stateful failure handler][agent-lifecycle] · [Virtual route preparation][session-projection].

F2 crosses a material ownership boundary. Public subscribers observe the completion after the agent's state reducer and before the session manager append. The test saw the successful assistant in the event, then reopened a file containing the user's request and a synthetic error. The no-throw run produced a persisted success and valid turn-boundary ID. Message history is a stronger product invariant than the success of an event consumer. Intentional extension modification through the `message_end` hook is an earlier, documented step and is preserved by moving public publication after the append. [Reducer and listeners][agent-reducer] · [Session public event before persistence][session-events] · [SDK event contract][sdk-events] · [Normal message replacement test][coding-runtime-tests].

F3 arises before any provider dependency. Both calls await the initial abort before taking ownership, then store their controller in the same field. They can both reach a supported compaction hook with separate signals. Finishing either call clears the shared state. The auto-compaction path already uses a captured controller and ownership-sensitive cleanup, which is a good local precedent. The single-call control established real cancellation followed by a clean non-commit. [Manual compaction][session-compact] · [Manual cleanup][session-compact-clear] · [Manual catch/finally][session-compact-end] · [Auto-compaction cleanup][session-auto-compact] · [RPC compact entry][rpc-compact] · [RPC dispatch][rpc-dispatch].

F4 reflects two distinct representations. Declarations live in transcript entries while executables live in a tool array. The first declaration pass occurs before the request hook, so a caller needs to update both values itself today. The raw loop's own contract says it declares changes before each request and that replay yields the runtime tool set. The same property cannot be assumed after arbitrary transcript rewriting by an extension, which is a deliberate override. [Tool delta contract][core-declarations] · [Request hook sequence][core-prepare] · [PrepareRequest type][prepare-contract].

F5 follows from teardown and publication being separate awaits on the runtime owner, with no single reservation spanning them. Both calls can tear down the original before either creates its replacement. The late completion assigns into the same owning fields. The serial control observes the ordinary shutdown callback before switching to the second replacement. The overlap leaves the first bound replacement's captured extension context callable after it loses the owner. That is an ownership violation with a concrete teardown consequence. Specific leaked provider or plugin handles were outside the probe. [Runtime ownership contract][runtime-owner] · [Teardown and binding][runtime-teardown] · [New-session path][runtime-new] · [Context invalidation][session-dispose].

R1 concerns recovery of real effects and result records. The shared AI message transformer has a defensive second pass that closes orphaned calls with a synthetic error result. This can satisfy a provider's call/result pairing while the original tool outcome remains unknown. It supplies neither recovery of the tool's effect nor proof that the effect never ran. [Sequential CLI persistence][session-events] · [Append implementation][session-writes] · [Provider message repair][ai-orphan-repair] · [Durable effect contracts][durable-effect].

Two further limits matter when interpreting the table. The CLI intentionally allows unbounded continuation under appropriate extension behavior, and its documentation tells extension authors to guard a continually asserted `continue`. There is no finding that ordinary follow-up automatically loops. Durable has per-conversation `maxTurns` and restart policy, but those are separate from provider timeouts, tool policy, and a model's quality. Also, the runtime replacement class explicitly documents teardown-first and error propagation. That choice can leave the caller with a disposed session if the replacement fails and merits lifecycle policy work. It is documented behavior rather than a failed test. ## 6. Core-code quality

### Decomposition and state

The cleaner split is `agent-loop.ts` as effects plus an awaited sink, `Agent` as reducer and run owner, pi-ai as transcript and provider interface, and `SessionManager` as a branch projection. The same split makes the repo's faux model useful in several packages. The seam between low-level and host policy is detailed enough for stable tests. `AgentSession` couples considerably more responsibilities. Its queue bookkeeping, branch changes, compaction, extension state, retry classification, tool lookup, and refresh hooks share mutable instance state. Reading an incoming model turn eventually requires following three transcripts or copies and several duplicated boundary guards. A refactor can extract each control operation without relocating domain policy into generic agent-core. [Agent core entrypoint][agent-entry] · [Agent run ownership][agent-lifecycle] · [Session field inventory][session-init] · [Request projection][session-projection] · [Session event handler][session-events].

Durable's decomposition is stronger at the persistence boundary. Typed committed records, transaction scope, a guarded storage façade, a separate task scheduler, and scoped registries make ownership explicit. Its complexity is higher in the scheduler and generation phases. `TaskRecord` state, `pi.live`, cached graph indexes, and transaction membership have to stay in step. Code comments and the specification document the fences. ### Concurrency, cancellation, and resource ownership

Agent-core synchronously acquires one active run, rejects a second direct prompt, and passes an abort signal to provider/tool hooks. Finished events are awaited before clearing state. Each tool batch can operate with controlled parallelism. The signal requires cooperation from tools and observers. A resource created outside the signal's scope can keep running. Code mode makes this difference explicit by distinguishing script settlement from actual worker exit, disarming the worker's own reference on termination, and tying an optional admission slot to exit. CLI session replacement waits for the outgoing agent run, invokes registered shutdown handlers, invalidates API contexts, and cleans provider session resources. SDK `dispose()` itself is synchronous and detaches after requesting abort. The host wrapper is the stronger settlement API. MCP's extension uses a per-session startup/shutdown boundary and closes its registered and late connections. Durable schedules phases outside the write transaction and commits the action's transition or outcome on the mutation line. A stored claim, abort mark and phase binding matter more than a live promise. Abort traversal finds ordinary descendants and drains their handles before finalizing the owner. Background work has separate handling, as do persistent conversations. Watchers can read immutable state without blocking transaction callbacks, while publications maintain commit order. A callback can ignore its signal, a tool may perform effects before an abort arrives, and a host reaching a failure boundary still needs to reopen its store. ### Errors, retry, and compaction

Pi distinguishes pre-request transport retries, model/turn retry, and context recovery. A retryable provider failure and a context overflow take distinct paths. Overflow receives one compact-and-repeat recovery per relevant attempt. A completed successful assistant can trigger threshold compaction without another conversational reply. Manual and branch summaries use their own retry callbacks and operation signals. Durable remembers attempts and clocks in tasks, preserves the committed partial on interruption, and can poll a deferred response without reissuing its underlying request. ## 9. Post-mortem and prioritized improvements

Pi has two plausible answers to session ownership because it serves two different applications. The CLI favors a quick startup, a legible transcript, lightweight in-process injection, and extension flexibility. Durable was free to require transactional storage and distinguish the current answer, unresolved work, per-phase claims, and durable recovery. P2 needed those distinctions when a child or reporter had to outlive a parent turn or a worker process. P3 presently supplies a process/plugin substrate, so its progress cannot be used to judge execution guarantees for features it has yet to ship. The higher-order pressure on the CLI is reliable state transitions as successive features add hooks and background work. Durable's pressure is keeping its storage and scheduler contracts tractable for extension developers. [Contribution philosophy][contributing] · [CLI project boundaries][repo-readme] · [Durable invariants][durable-invariants] · [p2 worker design][p2-worker-entry] · [p3 slice scope][p3-slices].

1. **Highest priority. Give host control operations one lifecycle owner.** Reserve the operation before any await that can admit another manual compaction, new session, fork, switch or import. Decide explicitly whether each overlapping operation queues, cancels the current operation, or rejects as busy. Store controllers and outgoing/candidate session references on that operation and release them by identity. Keep abort able to reach the operation without waiting on its own reservation. Tests should schedule crossed completions, assert the until-idle condition, and check exactly one teardown per superseded runtime. F3 and F5 already reproduce the lost ownership with public calls. The auto-compaction path and Durable commit ownership provide patterns at different scales. [CLI manual path][session-compact] · [Auto-compaction ownership][session-auto-compact] · [Runtime lifecycle][runtime-new] · [RPC input concurrency][rpc-dispatch] · [Durable writer][durable-commit].
2. **High priority. Make completion and persistence independent of ordinary observers.** Give the raw loop adapters an exceptional terminal outcome that releases both iterator and result consumers. Keep the configured provider-error representation. In the CLI publish authoritative message completion after successful append, and report public subscriber exceptions as observer diagnostics. Retain awaited internal/extension barriers where they intentionally control the run. Add an explicit notification ordering test, an iterator abandonment test, and a report-only observer failure test with disk reopen. The current stateful failure handler and Durable's distinction between publication and watch delivery are relevant patterns. [Core adapters][core-raw] · [Stateful failure handling][agent-lifecycle] · [CLI persistence boundary][session-events] · [Durable publication rules][durable-invariants].
3. **High priority for embedders. Make tool declarations and executor bindings converge at a named boundary.** Define whether request preparation may change the executable roster. An interface that changes executable tools should either regenerate the intended provider declarations with the appropriate transcript delta or require an explicit declaration projection in the same return value. Keep deliberate model/extension filtering possible. Test with unknown, renamed, hidden and removed declarations and preserve ID ordering after a tool result. F4 is a compatibility failure even without touching provider integrations. [Tool delta rules][core-declarations] · [PrepareRequest type][prepare-contract] · [Adapter tool replay][ai-tool-state].
4. **Medium priority. Reduce repeated branch work where it matters.** Calculate the active path once per projection and reuse provenance/index data. Consider caching a live projection using a revision and the effective cutoff while protecting branch navigation, summary boundaries, and edits. Preserve raw entries and file format. The counted Map reads demonstrate the baseline; add order-of-growth tests for compacted histories and avoid optimistic production latency claims until measured. In p2, track growth in reported-answer deduplication state alongside persisted task and view caches. [CLI projection][session-projector] · [p2 report deduplication][p2-reporter] · [Durable range reuse][durable-context].
5. **Medium priority. Make offline verification and failure budgets easier to interpret.** A pinned offline test artifact with matching generated model shards and minimal dependencies would make faux and runtime checks reproducible without registry access. Keep deterministic core suite targets separate from provider/transport integrations and generated-input checks. Expose structured errors from adapters where provider semantics permit and include transport-attempt counts beside session-attempt counts. Retain existing text matching as a compatibility fallback. Add workload tests to document restart and offline artifact coverage before claiming hosted portability. [Build and test instructions][repo-rules-tests] · [Catalog data manifest check][catalog-check] · [Transport retry][ai-transport-retry] · [Outer retry][session-retry] · [Typed AI telemetry][ai-telemetry].

Preserve the architectural choice between transcript resume and effect recovery. For CLI embedders, surface incomplete tool rounds explicitly on reopen, and keep automatic recovery of an external effect opt-in with a safe replay contract. For workflows that require restartable tool bodies and owned child work, Durable already exposes the requisite checkpoints and tests both replay policies. [CLI file boundary][session-writes] · [Wire-level repair][ai-orphan-repair] · [Durable effect contracts][durable-effect] · [Durable tool replay tests][durable-tool-tests].
