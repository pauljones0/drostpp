### Execution modes and their lifecycle

| Mode | Execution ownership | Important boundary |
| --- | --- | --- |
| Blocking | Proxy performs assembly, first inference and a synchronous tool loop on the caller's path. Configured concurrent tools can fan out, then the caller joins. | Caller observes a synchronous value or exception. |
| Future | Proxy returns an outer future. Async augmentation, input validation, memory, native model calls and tool stages compose into it. | `TokenStream` | Proxy performs prompt/memory prologue. `start()` builds the request and installs the callback handler. Partial events can forward early, and another handler can be installed for the next model round. | A streaming handle represents provider cancellation. Eager calls are scheduled when a completed tool call arrives if concurrent tools are configured. |
| `Flow.Publisher` | Subscription opens a fresh run for a stateless service. With memory, the same publisher admits one subscription. A deferred subscription buffers demand until async setup installs the real subscription. Mutiny tubes relay model and AI Service events. | The finite source is drained eagerly into bounded buffers. Downstream cancellation suppresses later delivery. Upstream cancellation still depends on branches wiring their work to the subscription. |

The callback path can buffer partial text while output guardrails operate. The reactive event path suppresses raw partial text when output guardrails can rewrite the answer. The text adapter drains rich events with unbounded upstream demand and filters them into a bounded text buffer, so a non-text terminal marker can be consumed even after the last requested text item. The provider path separates HTTP SSE frames from model events with a parser and a model-specific sink. This is a practical low-latency policy for finite inference streams. It makes buffer overflow, terminal ordering and cancellation first-class parts of the contract. ## 8. Post-mortem and prioritized improvements

The source suggests three pressures. Declarative interfaces and multiple providers require a stable request abstraction. Compatibility with a legacy synchronous and callback API makes conversion to future and reactive execution incremental. Stateful tool and workflow features then add retries, compensation, checkpointing, and observability to more than one lifecycle. The API succeeds at reuse and composition. It becomes hardest to reason about when a mode needs to answer whether work is still allowed, what can be persisted, and which transition has already won.

1. **Apply one tool-round state machine across the four turn modes.** Reserve the budget on the first tool-bearing response event before any executor submission, let a text-only response finish even with zero tool rounds left, and commit the result messages as one unit. Treat eagerly started tools as tracked work from submission through the last result. Add identical boundary tests for zero, one and multiple allowed rounds, a tool-plus-text response, multiple tools in one response, and a failed or cancelled eager round. This addresses findings 1 and 2 with a common invariant and protects side-effect accounting.
2. **Give all future and subscription stages one invocation owner.** Attach retrieval reads and leaves, memory assembly, output guardrail futures, reprompts and next-round model calls to the same lifecycle. Put cancellation checks before new dispatch and writes, with a defined policy for mandatory cleanup. Make terminal event ordering part of the behavior tests, and validate initial demand before dependency setup can delay the upstream subscription. Preserve the established distinction between cancellation, planned compensation and ordinary failure. The current cancellation chain is a useful primitive for this change.
3. **Keep active tool exchanges protocol-valid independently of retention.** Build the next model request from an explicit transaction-like turn transcript or fail clearly before dispatch when even the current round cannot fit. Use group-wise eviction and persist message bundles coherently. When normalization or guardrails replace a draft, document the difference between conversation record and accepted output. Cover shrinking window settings and long tool results in both message and token policies.
4. **Make the workflow attempt and checkpoint explicit.** Atomically acquire/create a scope for an ID and establish whether concurrent roots are serialized or rejected. Guard delayed value publication with the same identity-based replacement on reader and worker completion. Define a single root lifecycle that protects prelude, run, output and terminal persistence. Save every supported suspension transition and honor the store's acknowledgement. For mapper recovery, carry completed item results and reducer progress in one checkpoint, or derive reduction from validated retained slots. Test in-memory resume, reloading into a fresh proxy, save refusal and mid-batch restart separately.
5. **Specify budgets, guarantees and supported extension behavior more tightly.** Document when side effects and validation may repeat, bound any general recovery policy at the layer that owns it, and distinguish user-visible success from acknowledged checkpointing or successful compensation. Give blocking discovery an explicit execution policy and expose actionable diagnostics when extension code runs on the caller or model delivery thread. Add focused parity tests to targeted credential-free CI before expanding provider integrations.

Simple fixes can address the individual branches, but the larger leverage is removing the need to reconstruct lifecycle rules from several independent callbacks. Keeping independent model and tool adapters while making turn and workflow lifetimes explicit would preserve the strongest parts of the design.

## 10. Disposition

The pinned snapshot has a capable and testable Java runtime for typed turns, tool use, message management, and local and model-guided workflows. The recovered suite and ordinary positive controls support confidence in the tested paths. The reproduced defects reduce confidence at specific boundaries where side effects, cancellation, concurrent scope access, or resume correctness are essential. A production integration can benefit from the strong model and tool interfaces while still needing explicit policy for serialized session access, bounded tool rounds, durable checkpoint acknowledgement, and idempotent side effects.

The findings on tool limits, cancellation wiring, reactive setup, memory coherence, mapper reduction and workflow persistence are addressable in the core independently of vendor behavior. Source inspections add concerns around executor liveness, distributed ownership, and real reactive cancellation. Their frequency and external behavior remain open. The reactive code checks cancellation before dispatching each event, but emits the completed-tool event immediately before starting that tool. Whether cancelling from the subscriber’s callback prevents submission at that boundary needs a real tube-backed test, including the handoff to the in-flight result tracker. Native Maven, provider conformance, live transport, and end-to-end Mutiny demand and overflow are separate verification gaps. This report's evidence supports prioritizing fixes and regression cases at the runtime lifecycle boundaries.
