# OpenHands Automation architecture and reliability review

## 1. Snapshot, scope, and elapsed-time evidence

The service has a useful division of responsibility. It records when work should start, admits runs through a database queue, and delegates execution to the software-agent SDK and agent server. The ordinary local path worked end to end. The most consequential weaknesses arise when a database transition and a remote effect happen in different orders. Independent transactions reproduced a cancelled or completed run being overwritten, a cancelled queued run being launched on SQLite, and an acknowledged terminal run retaining an unscheduled sandbox cleanup.

## 2. Core architecture and end-to-end control/data flow

### Process and authority

One FastAPI lifespan supplies storage access and runs the scheduler, dispatcher, watchdog, Git sync and optional stream supervisor. Every service replica can host these tasks. PostgreSQL supports coordination across replicas. Local mode is selected by a configured agent-server URL and typically runs one automation process beside an agent server with SQLite. App-server profile resolution, conversation state, tool lookup, LLM calls, and command execution belong to OpenHands and the SDK side of the boundary. The service uses declarative configuration to decide when or why to run, what artifact and profile to use, and whether to start a new conversation or send a turn to an existing one. Model planning and tool-use loops run inside the conversation runtime. [lifespan](repos/OpenHands__automation/openhands/automation/app.py:98), [background actors](repos/OpenHands__automation/openhands/automation/app.py:140), [mode selection](repos/OpenHands__automation/openhands/automation/config.py:776), [cross-repository ownership](repos/OpenHands__automation/AGENTS.md:5), [SDK tool composition](repos/OpenHands__software-agent-sdk/openhands-tools/openhands/tools/preset/default.py:48).

An `Automation` is an organization-scoped definition with owner, creator, trigger, active state, executable spec, timeout, profile, and optional factory. A factory is an independent named grouping. It carries no worker, scheduler, pipeline, or execution engine. `AutomationRun` is both queue entry and history. It records reason for admission, triggering user or event, runtime identifiers, deadlines, subject, phase, and eventual status and outcome metadata. `AutomationDraft` stores a draft body and can materialize a disabled DRAFT automation for a manual test through the same queue. The regular API checks the draft boundary and event/cron selection requires active state. Authentication, authorization to manage a definition, the identity executing a run, and the callback owner are separate decisions. A service-account assignment checks real org membership at the service boundary. Changing run-as checks for live work, disables the definition and releases old subjects before a subsequent enable. [factory and definition models](repos/OpenHands__automation/openhands/automation/models.py:78), [run row and queue contract](repos/OpenHands__automation/openhands/automation/models.py:262), [draft model](repos/OpenHands__automation/openhands/automation/models.py:467), [draft materialization](repos/OpenHands__automation/openhands/automation/draft_router.py:569), [manual draft dispatch](repos/OpenHands__automation/openhands/automation/draft_router.py:756), [definition authorization](repos/OpenHands__automation/openhands/automation/router.py:172), [run-as transfer](repos/OpenHands__automation/openhands/automation/router.py:1375), [service-account membership](repos/OpenHands__automation/openhands/automation/utils/run_as.py:109).

### Admission

| Entry point | Selection and durable effect |
| --- | --- |
| Manual | The dispatcher route checks org, definition-level permissions and draft state. It adds a PENDING run with manual provenance and triggering user. Manual admission is intentionally available for disabled definitions, and the dispatch query still excludes soft-deleted definitions. |
| Cron | The scheduler scans least-recently-polled enabled ACTIVE definitions in batches. It stamps every selected row for rotation, computes the latest previous fire in the configured timezone, compares it with the last trigger or creation time, and writes the run and bookkeeping in the same transaction. After downtime it emits one due run per selected automation, coalescing missed slots. |
| Webhook | The route verifies the configured signature against raw bytes, interprets provider and custom envelopes, applies admission and delivery-ID metadata, and hands an `AcceptedEvent` to transport-neutral ingest. It matches source, glob and JMESPath against the raw payload, stores parsed data for the runner when present, and inserts integration event plus new runs atomically. |
| Stream | A configured provider owns a long-lived connection and calls the same ingest with a provider-scoped org and a fresh session per event. Slack Socket Mode accepts a limited mention envelope, acknowledges promptly, and uses the envelope's stable event ID. |

### Worker, backend and SDK handoff

1. The dispatcher expires old deferred work, computes optional global RUNNING capacity, and selects oldest eligible PENDING rows. PostgreSQL uses transaction-scoped advisory admission locking when a cap is enabled and `FOR UPDATE SKIP LOCKED` for selection. It commits RUNNING and a provisioning deadline before spawning one asyncio task per claimed run. The tasks share the polling loop's HTTP client. Ordinary processing is asynchronous in one service process, with independent database sessions for later writes. ### Outcome and recovery

The SDK workspace sends completion on context exit, optionally registering the conversation and cost first. The callback checks the run's automation principal and org, updates a RUNNING row conditionally, records phase and error classification or semantic finish metadata, and arranges cleanup for a visible non-retained sandbox. A success can reconcile watchdog-authored timeout based on the persisted error prefix. User cancellation conditionally updates PENDING or RUNNING, then stops the local BashCommand or asks the cloud runtime to remove the sandbox. The verifier can recover a lost callback from command-specific BashOutput and classify a real failure separately from uncertain infrastructure. The watchdog handles deadlines and retained-workspace, integration-event and deferred-sandbox sweeps. PENDING runs survive app restart and are picked up by new pollers. Claimed runs are resolved through timeout or callback. There is no stored dispatch owner or retry lease that hands an unfinished claim to another worker. [SDK completion callback contract](repos/OpenHands__software-agent-sdk/openhands-sdk/openhands/sdk/workspace/base.py:83), [cloud callback](repos/OpenHands__software-agent-sdk/openhands-workspace/openhands/workspace/cloud/workspace.py:857), [completion lifecycle](repos/OpenHands__automation/openhands/automation/router.py:1744), [cancellation lifecycle](repos/OpenHands__automation/openhands/automation/router.py:2050), [command verification](repos/OpenHands__automation/openhands/automation/utils/agent_server.py:206), [watchdog scan](repos/OpenHands__automation/openhands/automation/watchdog.py:573), [sandbox cleanup sweep](repos/OpenHands__automation/openhands/automation/watchdog.py:925).

Two persistence extensions are operationally relevant. The per-automation KV API supports encrypted per-key values, a version anchor, optimistic version checks, and ordered atomic batches. Writers serialize on the per-automation metadata and then touched keys in PostgreSQL. Git sync mirrors definitions and optional artifacts to an org-selected repository. It uses a DB-backed org lease, a replaceable local checkout, pull/import/export/push, and a dirty-state conflict rule. This mirrors definitions, while in-flight run decisions and external operation ownership continue to live in the service database and execution environment. ## 3. Why the design works and its governing invariants

- **Persist work before launch.** A committed PENDING row is sufficient to make work eligible after a restart. The dispatcher commits its RUNNING claim before launching external effects, so PostgreSQL pollers cannot each acquire the same row through the normal selection path. Counting RUNNING under the optional advisory lock also avoids two replicas claiming distinct rows past the same global cap. The row status is the admission gate, which means recoverable exceptions at the runtime handoff need explicit treatment. [pending creation](repos/OpenHands__automation/openhands/automation/utils/run.py:196), [count and claim transaction](repos/OpenHands__automation/openhands/automation/dispatcher.py:1744), [commit before task creation](repos/OpenHands__automation/openhands/automation/dispatcher.py:1799).
- **Put admission and dedupe in one transaction.** The uniqueness invariant is `(org_id, source, provider_event_id)` for non-null IDs. A targeted insert conflict handles real replays, while unrelated DB failures still propagate. An event and any new run rows commit together, with telemetry running afterward. Dedupe applies to the retention window and source-supplied identity. Subject locking addresses a different consistency problem, deciding which conversation owns an external work item. [partial unique index](repos/OpenHands__automation/openhands/automation/models.py:813), [dialect-specific conflict target](repos/OpenHands__automation/openhands/automation/ingest.py:166), [commit and telemetry](repos/OpenHands__automation/openhands/automation/ingest.py:401), [different subject invariant](repos/OpenHands__automation/openhands/automation/conversations.py:152), [dedupe retention sweep](repos/OpenHands__automation/openhands/automation/watchdog.py:902).
- **Distinguish launching, evaluating and finalizing.** Cloud context acquisition can be retried at a provisioning failure boundary before work starts. Resource limits can move the same RUNNING row back to PENDING under a conditional update, with deferred time and attempt count. Once the entrypoint may have executed, the system verifies its ID or waits for callback, avoiding generic replay of code with side effects. Failures in unpacking, setup, or absence of a callback still have a secondary evidence path through BashOutput. [pre-execution retries](repos/OpenHands__automation/openhands/automation/dispatcher.py:721), [defer or skip](repos/OpenHands__automation/openhands/automation/dispatcher.py:782), [guarded requeue](repos/OpenHands__automation/openhands/automation/utils/run.py:486), [command-specific fallback](repos/OpenHands__automation/openhands/automation/utils/agent_server.py:56).
- **Keep execution context separate from outcome.** The backend owns resource semantics, the run owns status, and the SDK supplies evidence. Callback and explicit cancel use status predicates, and most watchdog writes do too. The callback can preserve a semantic FinishTool response independently of infrastructure success, so an agent's task outcome need not disable otherwise healthy automation machinery. [context release](repos/OpenHands__automation/openhands/automation/backends/base.py:99), [completion and teardown policy](repos/OpenHands__automation/openhands/automation/router.py:1793), [semantic outcome handling](repos/OpenHands__automation/openhands/automation/router.py:1824), [cancel compare-and-set](repos/OpenHands__automation/openhands/automation/router.py:2088), [watchdog outcome handling](repos/OpenHands__automation/openhands/automation/watchdog.py:299).
- **Declare meaningful differences between DB modes.** PostgreSQL row and advisory locks serialize competing service instances. SQLite config enables WAL, foreign keys and a busy timeout. SQLite migrations explicitly take an immediate transaction. Some app paths use real no-op writes or SQL conflict clauses to get SQLite serialization, such as factory assignment and event intake. Others assume a single process. Multiple asynchronous actors inside that process can still interleave across a read and subsequent write. [SQLite connection settings](repos/OpenHands__automation/openhands/automation/db.py:189), [SQLite migration transaction](repos/OpenHands__automation/migrations/env.py:81), [cross-dialect assignment lock](repos/OpenHands__automation/openhands/automation/factory_router.py:142), [dispatch dialect split](repos/OpenHands__automation/openhands/automation/dispatcher.py:638).

## 5. Weaknesses and evidence status

### Highest-impact lifecycle failures

**A terminal write can overwrite a winning completion or cancellation. Reproduced on SQLite and PostgreSQL.** `mark_run_terminal` reads the row in a new session and checks RUNNING in Python. It calls `mark_run_status`, which updates by ID alone. I stopped the production helper between those two statements with an asyncio event, completed or cancelled through the actual ASGI endpoint in another session, verified 200 and the committed terminal value from a third session, then released the helper. Both pre-existing terminal values became FAILED. Callback cost `0.25` remained on the FAILED row. A terminal row present before the helper's initial read was preserved, and the API's own late cancellation correctly gave 409. This is a stale-read overwrite. The guarded write in one actor cannot enforce a global state machine while another actor writes without the predicate. The dispatch failure helper also emits failure and can consider auto-disable after the attempted write, without learning whether it won. [terminal helper](repos/OpenHands__automation/openhands/automation/utils/run.py:740), [ID-only update](repos/OpenHands__automation/openhands/automation/utils/run.py:320), [callback condition](repos/OpenHands__automation/openhands/automation/router.py:1838), [cancel condition](repos/OpenHands__automation/openhands/automation/router.py:2088), [subsequent failure effects](repos/OpenHands__automation/openhands/automation/dispatcher.py:951).

**SQLite can launch cancelled PENDING work within one process. Reproduced.** I held the dispatcher after the real PENDING poll and before its status update. The cancel route replied 200 and a new session read CANCELLED. On release, the dispatcher committed RUNNING and the task hook recorded a launch. The resulting row still had `completed_at`. Cancel before polling correctly excluded the row. SQLite's WAL, single writer, and single-process topology do not serialize an application read and a later write against a sibling endpoint. The PostgreSQL claim takes row locks and has a different race contract. [selection predicate](repos/OpenHands__automation/openhands/automation/dispatcher.py:615), [SQLite lock omission](repos/OpenHands__automation/openhands/automation/dispatcher.py:638), [claim loop](repos/OpenHands__automation/openhands/automation/dispatcher.py:1759), [transition values](repos/OpenHands__automation/openhands/automation/utils/run.py:283), [per-connection pragmas](repos/OpenHands__automation/openhands/automation/db.py:213).

**A fast callback or late cloud cancellation misses sandbox cleanup. Reproduced on both databases with a scripted cloud boundary.** A command can report completion while the start call is returning or while dispatcher ID writes are pending. The callback decides teardown from the sandbox ID visible in its initial read. Cancellation also bases its teardown on IDs already on the row. In the two early orders, terminal status was accepted successfully, then a sandbox and command ID appeared without a cleanup deadline or release. The normal order booked cleanup once the ID was already registered. The dispatcher's post-start check calls `stop_command` on a non-RUNNING row. Cloud inherits a no-op because its cancellation contract expects the entire sandbox to be deleted by the route. The result establishes a missing service-side teardown action in this ordering. Runtime TTL and actual cloud retention were outside the measurement. ## 9. Post-mortem

The service grew around a deliberate split. SQL provides durable automation definitions and a compact run queue, while existing OpenHands servers provision resources and run agents. Adding the scheduler to the API lifespan provides a convenient local deployment without a second service. The architecture then absorbed multi-replica admission, an optional persistent local runtime, user and service identities, external event acknowledgements, resumed conversations, delayed cleanup, and compatibility for installed artifacts. Each change addresses a specific operational need. Most of the severe gaps are at handoffs between these mechanisms. An enum alone cannot express whether execution was merely claimed, a sandbox exists, a command started, a callback won, or cleanup still needs to be done. [queue as history](repos/OpenHands__automation/openhands/automation/models.py:262), [embedded workers](repos/OpenHands__automation/openhands/automation/app.py:140), [admission and task launch](repos/OpenHands__automation/openhands/automation/dispatcher.py:1700), [callback cleanup decision](repos/OpenHands__automation/openhands/automation/router.py:1793), [durable cleanup date](repos/OpenHands__automation/openhands/automation/watchdog.py:925).

Concurrent actors already have several correct local patterns. Compare-and-set in callback, cancellation, requeue and lease release should become the shared lifecycle contract. The service can preserve the existing SQL queue and SDK data plane. The changes with the highest return are explicit ownership, durable intent for effects that outlive transactions, and tests that require conflicting actors to publish exactly one durable decision.

| Priority | Change | Acceptance evidence |
| --- | --- | --- |
| P0 | Route all claims and terminal transitions through a small transition store. Use the expected source state and, for in-flight operations, the expected attempt or epoch in the SQL predicate. Return the actual winner; only the winner writes failure counters, disable decisions, audit and cleanup intents. Use a single transaction for the decision and its local DB consequences. | Both database variants preserve a callback or cancel committed after the dispatcher's read. SQLite concurrent cancel can never yield RUNNING with `completed_at` or cause a launch. A stale watchdog result cannot win against a newer deadline. |
| P0 | Persist dispatch progress and runtime identifiers immediately at the boundary where they are known. Give workers an attempt identity, lease and heartbeat, with a durable handoff to a cleanup worker. Add idempotency to allocate and start when supported. Without server-side idempotency, reconcile by a durable correlation ID and retry only before any potentially effectful step. Keep a service-owned task group and drain it before closing the shared client. | Exit a child after claim, after sandbox allocation, during startup and after command start. Restart can distinguish retryable provisioning from ambiguous execution, preserve the committed command, and eventually delete the right sandbox. Fast callback and cancellation still produce correct cleanup. |
| P1 | Model subject delivery independently of `started_at`. Use one fenced subject owner, a durable ordered inbox for turns received before readiness, and an idempotent dispatch/append consumer. Specify queue overflow explicitly. Durable intake before acknowledgement can preserve receipt without holding locks during sandbox resume. | A follow-up on each side of PENDING, claim, context readiness, conversation creation and callback goes to a single logical conversation. Provider delivery ID replay and crash/retry preserve the same result. A deadline-constrained response stays bounded under DB contention. |
| P1 | Bound transient verification using explicit `next_verify_at`, attempt/backoff and a policy for unresolved outcomes. Separate loss of confirmation from execution failure, keep capacity reporting honest, and record retryable cleanup jobs. Preserve configured grace and retained subjects through reconciliation. | With prolonged 429, timeout or transport failure, old work does not hold all capacity forever. A later SDK result is reconciled with a structured cause and does not cause a contradictory auto-disable or first-run outcome. A genuine remote delete failure remains visible and retryable. |
| P1 | Store a cron-specific occurrence cursor and UTC `next_fire_at`, indexed over cron definitions. Define whether fold occurrences both fire and whether nonexistent local times skip or move. Define catch-up and overlap policy per automation. Pass the configured batch size and keep manual provenance independent of the cron cursor. | Timezone gap/fold and exact-boundary tests, time advances across downtime, and many unrelated event definitions all preserve the documented occurrence policy. Self-overlap works only when explicitly allowed. |
| P1 | Make Git publication acknowledgement versioned. Keep the normalized export generation or an outbox in the DB and acknowledge specific generations after a successful push. Retain individual import failures for retry when a commit contains both healthy and transiently blocked definitions. | Push refusal followed by a replacement checkout recreates and publishes the pending generation. A simultaneous API edit cannot be cleared by an older export. Network I/O still holds no SQLite write transaction. |
| P2 | Version the execution contract and separate a typed requested plan, resolved runtime snapshot and status transition cause. Derive health from last successful polls, age and counts by stage, retries, unknown outcomes and cleanup backlog. Keep product capture off claim transactions and use explicit worker readiness. Test the server and runner releases together offline in CI. | Historical bundles and both runtime modes pass the same supported-contract tests, and operators can account for accepted events, committed runs, launched commands and pending cleanup with stable identifiers. |

This ordering prioritizes state corruption and unreconciled execution over policy and performance improvements. It also preserves the valuable design decisions already demonstrated: local/cloud backends, event acceptance with DB dedupe, SQL orchestration, command-specific fallback, real migration history, and a stable SDK handoff.
