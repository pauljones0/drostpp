## 2. Architecture and end-to-end control and data flow

### The runtime owner and three useful lifetimes

`Mastra` registers definitions and injects dependencies such as logger, storage, PubSub, observability, and memory. Workflow registration binds the executable definition and engine to that host. Internal workflows are registered separately, sometimes by run ID. Their event routing can stay local even when the application uses remote workers. A run-scoped registration retains a typed `RunScope` with reference-counted lifecycle and expiry. Registration is how an event carrying IDs and data reconnects to executable code and runtime facilities. [Mastra constructor](repos/mastra-ai__mastra/packages/core/src/mastra/index.ts:1816) [agent registration](repos/mastra-ai__mastra/packages/core/src/mastra/index.ts:3069) [internal workflow registration](repos/mastra-ai__mastra/packages/core/src/mastra/index.ts:4219) [workflow registration](repos/mastra-ai__mastra/packages/core/src/mastra/index.ts:6435)

A **definition** owns schemas, executable steps, and the graph. A **logical run** owns run ID, input, result/state, an execution position, and any persisted suspension. A **live execution** owns a cancellation controller, process handles, model/tools, transient processors, stream writers, and sometimes a lease or fence generation. A run can have several live executions over time. A worker or model stream can disappear while a stored run remains recoverable. An output subscriber can come and go without owning either the workflow or its tools. That distinction explains several otherwise confusing API choices, including restart versus resume and durable stream reconnect versus starting another agent turn. [Run](repos/mastra-ai__mastra/packages/core/src/workflows/workflow.ts:4173) [run-scope design](repos/mastra-ai__mastra/packages/core/src/mastra/run-scope.ts:1) [execution claim](repos/mastra-ai__mastra/packages/core/src/agent/durable/execution-fence.ts:261) [run registry](repos/mastra-ai__mastra/packages/core/src/agent/durable/run-registry.ts:1)

### From a workflow definition to execution

```text
createStep and registered agent/tool/workflow references
  -> typed builder entries plus a serialized graph projection
  -> commit and createRun
  -> start / startAsync / stream / resume / restart / timeTravel
  -> engine drives a position and dispatches entries
  -> step or adapter invokes user code
  -> step outcome, state delta, path, and trace are reconciled
  -> persist checkpoint or park, and publish observation events
  -> terminal result or resumable state
```

- The fluent workflow builder carries the previous type through `.then`, `.map`, `.parallel`, `.branch`, `.foreach`, and loop operations. The graph produced by `commit` is an ordered list of typed control-flow entries, with nested workflows and indexed blocks giving it structure. An executable definition contains functions and step references. Its serialized projection captures identities, schema/authoring metadata, and the described flow. Recovery uses the registered executable graph with persisted paths and results. The serialized projection does not supply user functions on its own. Mapping templates and predicate trees can declare referenced step IDs, which matters when journal-backed results are no longer resident. - `createRun` assigns or reopens a run ID, resolves the storage version and any run-local snapshot policy, and binds an engine, graph, and PubSub. A supplied ID can find a previously persisted run. A fresh ID for an explicitly nonpersisting workflow avoids an unnecessary existence read. On start the run validates input and initial state, validates request context when configured, and awaits `onStart` as a gate. `startAsync` tracks the dispatch boundary and returns the ID after preparation and, where applicable, durable dispatch. Its background invocation still handles completion and lifecycle callbacks. - The default engine is an async, serial driver over top-level entries. It chooses an initial index for a fresh, resumed, restarted, or time-travel drive, then dispatches each entry with the prior result, current run state, request context, paths, abort controller, and writer. The interpreter hands ordinary leaves to the step executor and agent/tool/classifier/mapping leaves to entry executors. The step gets parsed input, state accessors, `getInitData` and step-result lookup, `retryCount`, `suspend`, `bail`, and `abortSignal`. A successful entry applies its mutable context before the next entry. Parked or failed outcomes leave the loop through defined status branches. Expected user step failures become structured results. Exceptions outside step settlement, for example preflight failures or an uncaught control-flow error, can reject the promise. Branch predicates are evaluated before launching every selected arm, so overlapping conditions can run more than one arm. - Human intervention is a stored continuation. `suspend(payload, { resumeLabel })` validates the payload and records active/suspended paths. The leaf records an outcome with its timing, payload, and any available partial output. `resume` loads the same logical run, identifies the leaf by path or label, validates incoming data, and dispatches the parked entry with old suspension and new resume data. ### Event workers, persisted execution, and stream delivery

The evented workflow engine takes the same graph and continuation semantics through a message boundary. It first subscribes to the live tail of `workflows-finish`; it then publishes start/resume/restart data to the shared `workflows` topic. Live-tail placement matters on a retained broker because a historical suspend of the same run ID could otherwise finish the new caller. A worker reconstructs context, resolves the registered definition, dispatches the next occurrence by execution path, and writes state before advancing. Event type, run ID, event ID, persisted occurrence data, and adapter capability determine whether a delivery starts the leaf, continues from its completed result, or is dropped. The broker delivery budget is distinct from the user step retry budget. The worker acknowledges or asks for retry based on the processor result. Engine finish releases the caller waiting on the finish topic. Watch/output topics surface intermediate lifecycle and custom chunks. [subscribe before dispatch](repos/mastra-ai__mastra/packages/core/src/workflows/evented/execution-engine.ts:162) [live-tail finish subscription](repos/mastra-ai__mastra/packages/core/src/workflows/evented/execution-engine.ts:240) [resume publication](repos/mastra-ai__mastra/packages/core/src/workflows/evented/execution-engine.ts:267) [route a step-run event](repos/mastra-ai__mastra/packages/core/src/workflows/evented/workflow-event-processor/index.ts:1989) [finished occurrence decision](repos/mastra-ai__mastra/packages/core/src/workflows/evented/workflow-event-processor/finished-occurrence.ts:81) [delivery fence](repos/mastra-ai__mastra/packages/core/src/workflows/evented/workflow-event-processor/index.ts:5151) [delivery budget](repos/mastra-ai__mastra/packages/core/src/workflows/evented/workflow-event-processor/index.ts:5227) [orchestration worker](repos/mastra-ai__mastra/packages/core/src/worker/workers/orchestration-worker.ts:32)

Persistence has two substantially different read and write profiles. With storage v1 the engine writes a snapshot with status, original input and step outcomes, state, ordered path and active positions, suspend labels, serialized graph, timestamp, context, and trace linkage. The in-process engine serializes writes inside a run. Evented storage uses result/state updates whose atomicity needs adapter support. v2 splits the run header, current result references, evolving state, and step/foreach payloads. It writes checkpoints plus incremental journal updates and can retain successful step summaries in the driver. For example the default engine loads the current entry and predecessor at dispatch and drops eligible originals after finishing an entry. v2 gives the caller a `steps()` loader and the step asynchronous `getState()` and `getStepResultAsync()`; v1 callers can continue to use the eager object, `state`, and synchronous prior-step access. Reopening a run preserves its original version. Children inherit the parent's version. A cron schedule is another producer of work. The scheduler lists due rows, checks the target and its definition, derives a run or claim ID from schedule ID and scheduled fire time, and compare-and-sets the old and next fire times before publication. It records the publication outcome. Publication has a finite retry loop. A last-error or process failure between claim and publish can leave an advanced schedule with an uncertain or absent invocation. That is a real transaction boundary. A scheduled definition switches to the evented engine when nonempty `MASTRA_WORKERS` marks a split-worker setup, including the caller value `false` used to keep workers off a front process. The shared engine choice keeps worker and caller in agreement. ### Agent entry points and the inner loop

```text
Agent.generate / Agent.stream / resume APIs
  -> merge defaults, scopes, and dynamic RequestContext
  -> resolve run, thread, resource, model, version, and trace
  -> transient preparation workflow
       prepare tools       prepare memory and input processors
                   \       /
                    map runtime inputs
                         |
                   MastraLLMVNext / loop
                         |
       model step -> map emitted tool calls -> foreach tool
       -> fold results / background checkpoint / signals / completion checks
                         |
                continue, finish, or park

    message and usage aggregation / persistence / caller stream or FullOutput
```

- `generate` and `stream` converge on `Agent.#execute`. They merge invocation/default options, resolve dynamic scope/model and memory identity, and register thread-bound work with the thread runtime. The execution path can resolve a stored agent definition version. A resume prefers the stored exact version of the suspended agent, unless the caller explicitly picks an exact override. Reserved context identities take precedence over memory arguments. Preparation is a transient in-process workflow with parallel tool and memory setup, then a mapping step and stream creation. It avoids snapshot writes and puts live tool, message and callback objects in its run scope. `generate` awaits the aggregation of that output. The chosen model method still differs by invocation. ### Durable agents, conversation state, and readers

Durable execution wraps an agent definition in a reusable workflow. The durable stream start reserves a thread when applicable, claims the run before preparation, resolves dynamic model, memory and tools, and builds both a serializable input and a live registry entry. The input includes IDs and model/tool metadata, initial message state, durable options, and trace information. The registry and run scope hold what has executable identity, including callbacks, controllers, instances, converters and processors. The stream subscribes before the workflow starts. Durable workflow steps load or reconstruct runtime dependencies, checkpoint iteration state, and output chunks to the run topic. 1. **Definition, execution occurrence and result identity are independent.** A step ID names an addressable definition/result. ## 5. Weaknesses

### Reproduced defects and contract gaps

**D1. Default workflow retry dispatch after cancellation.** A failing step with one retry and a nonzero delay executed the second body after `await run.cancel()` in 24/24 runs on v1 and 24/24 on v2. The second invocation received an already-aborted signal. No following step ran and the final stored and returned states were both `canceled`. The otherwise equivalent evented run invoked the body once in 24/24 runs on each version. A cooperative implementation may stop an already-running function only at its own boundaries, but a fresh retry is a dispatch decision the engine controls. The default retry loop waits a plain timer and invokes the next body without checking the controller as it enters the retry. The engine's later cancellation checks still preserve the outward status. The symptom is hidden from consumers who only inspect status. An effect inside the retry body can occur after cancellation acknowledgment. ### Tradeoffs and unresolved risks

- **Transport and adapter choice change the guarantee users receive.** In-memory atomics exercise logic and single-process races. A store with guarded writes can preserve remote cancellation atomically. An older store that only reads before writing leaves a window. Durable-agent PubSub fallback can acquire a lease yet lack a storage generation. A backend with no leases has weaker guarantees again. Evented step redelivery avoids duplicate dispatch where it can prove an active/completed occurrence, but transport loss, ambiguous publication and external effects require separate handling. No evidence here establishes arbitrary exactly-once side effects. - **Scheduling has a claim-to-publish gap.** Stable occurrence IDs and the schedule CAS prevent double advancement. Once a claim advances a row, publication is a separate operation. Retries plus a failed trigger record give operational visibility. A hard crash can happen before either publication or trigger recording, and an acknowledged/unknown publish can later be delivered. Recovery code and deterministic IDs mitigate several cases but cannot make two independent writes one transaction. This is a source-grounded failure window, without a process-kill reproduction specific to the scheduler in this evaluation. ## 9. Post-mortem and prioritized improvements

Mastra has accumulated several demands on the same authored graph. The graph supplies typed composition to TypeScript callers, runnable functions to the interpreter, stable occurrence IDs to distributed workers, a compact representation to storage, and a displayable result to observers. Agent orchestration adds streamed model output that can appear before the step completes, state that must be rolled back on retry, and external tool calls that may already have taken effect. Backward compatibility adds a second storage shape and multiple provider/stream generations. The resulting code does well when it makes each transition's identity, authority, and representation explicit. The four reproduced defects show the cost when a lifecycle assumption lives in only one of the parallel paths.

The highest-risk failures occur on a boundary where the caller receives a reassuring answer while another commitment remains outstanding. A canceled result can disguise a newly dispatched retry. A successful result can close its stream before the peer receives the step frames. A cloned definition can execute correctly with ordinary values while silently changing its validation, retry, and engine policy. A suspended result can carry a reason yet lose a valid partial value. Integration tests help by examining body invocations, raw state, and actual wire traffic along with the returned envelope.

1. **Block fresh work once logical cancellation is confirmed.** Carry a cancellation contract through the retry executor. Use an abortable backoff and a final dispatch-time guard. Distinguish logical cancellation and hand-back at the same step boundary so an interrupted executor can leave a recoverable cursor. Use the shared engine test harness with a controlled first-attempt failure and an armed retry. The decisive assertion is absence of a second body invocation after acknowledgment, alongside final status and the noncancel and nonretryable controls. Include both in-memory and real-store capability cases. This protects side effects and gives cancellation a concrete cut point. [default retry boundary](repos/mastra-ai__mastra/packages/core/src/workflows/default.ts:521) [post-step cancellation](repos/mastra-ai__mastra/packages/core/src/workflows/handlers/entry.ts:969) [evented acceptance test](repos/mastra-ai__mastra/packages/core/src/workflows/evented/retry-delay.test.ts:269)
2. **Give workflow streaming an explicit producer/observer completion barrier.** Make ready-subscribe and completion/detach phases explicit for `Run.stream` and its resume path. The producer should settle only after the reader can consume preceding frames or record which ones require replay. For an in-process default run, wiring the owned stream to its local writer can avoid a peer round trip. For a shared bus, use a per-run acknowledged terminal marker or durable ordered log with a bounded failure path. Waiting for socket send or using a fixed timer cannot prove receiver delivery. Preserve the authoritative result and expose an observable delivery failure when the transport cannot honor the stream contract. Test real connected peer and broker roles plus slow and failed consumer cases. [current default stream integration](repos/mastra-ai__mastra/packages/core/src/workflows/workflow.ts:5076) [subscription barrier example](repos/mastra-ai__mastra/packages/core/src/workflows/evented/execution-engine.ts:240) [replay delivery reconciliation](repos/mastra-ai__mastra/packages/core/src/events/caching-pubsub.ts:386)
3. **Use one canonical record for workflow copy and step outcome assembly.** An engine-specific clone factory or explicit immutable definition object should retain the engine, state and context schemas, retry/wait policies and both graph projections. It should state which live services or mutable references are shared. The low-risk suspension fix is to encode output presence explicitly so schema-valid falsy data survive. A cross-engine case should compare original/copy preflight, body attempts, and graph export. A second case should check exact values in public result, watch event and reloaded snapshot. These fixes are smaller than the architectural work and high value for parity. [default clone path](repos/mastra-ai__mastra/packages/core/src/workflows/create.ts:129) [evented clone path](repos/mastra-ai__mastra/packages/core/src/workflows/evented/workflow.ts:116) [suspended leaf construction](repos/mastra-ai__mastra/packages/core/src/workflows/handlers/step.ts:747) [parallel implementation](repos/mastra-ai__mastra/packages/core/src/workflows/evented/step-executor.ts:440)
4. **Make guarantees and loss of guarantees observable by adapter capability and run.** Lease owner, generation, event ID, step path, storage version and applicable guards could form one diagnostic view across logs, status inspection, and traces. Give users a strict mode for recovery that requires store fencing and a usable run log. Provide a stable effect ID for replayable user operations. Consider a durable dispatch outbox for schedule occurrence claims, with a separate marker for publication and applicable idempotency on the receiver. Keep external side-effect semantics explicit. [fencing interface](repos/mastra-ai__mastra/packages/core/src/storage/domains/workflows/base.ts:54) [delivery guard](repos/mastra-ai__mastra/packages/core/src/workflows/evented/workflow-event-processor/index.ts:5151) [schedule claim boundary](repos/mastra-ai__mastra/packages/core/src/workflows/scheduler/scheduler.ts:448)
5. **Keep extending the shared acceptance suite around cross-representation invariants.** Exercise public operations against normal, durable, evented and adapter-managed workflows. Compare expected result, stored state, stream frames, tool effects, and next model request. Add crash points just before/after store writes and publication, plus negative support checks for adapters lacking atomic guarantees. Move public-host fixtures behind localhost test fixtures, keep elapsed-clock assertions paired with an outcome oracle, and give expected-failure cases a tracked removal plan. Define optional or versioned output validation before tightening the default schema behavior. Consolidate phase logic where these acceptance tests demonstrate agreement. [existing test design](repos/mastra-ai__mastra/packages/core/src/loop/test-utils/aimock/README.md:14) [existing overlap tests](repos/mastra-ai__mastra/packages/core/src/workflows/storage-v2-concurrent-writes.test.ts:250) [actual subprocess recovery](repos/mastra-ai__mastra/stores/libsql/src/__tests__/cross-process/resume-claim-takeover.test.ts:1)
