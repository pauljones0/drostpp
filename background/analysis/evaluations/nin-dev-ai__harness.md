## 2. Core architecture and end-to-end control/data flow

### Entry points, ownership and data stores

The headless CLI resolves a Git root, connects to a Unix socket and starts a detached daemon when needed. CLI requests have an ID and the daemon validates the envelope before dispatching to a handler. Socket clients can subscribe from an event sequence number. The daemon owns one SQLite file and a map of open projects for its home. It takes a PID-file lock before listening, reopens projects named in earlier `project.initialized` events, recovers them and attaches `EnginePlugin`. A project is identified by its configured name and a short hash of the canonical root. Each project runtime has the config and adapter cache, one engine, and one set of logical worker slots. A worker slot is a role plus ordinal. Its execution is a sequence of short-lived vendor processes. The daemon can continue after a client disconnects. [CLI startup](repos/nin-dev-ai__harness/apps/cli/src/commands/_client.ts:57) · [Daemon open and restart](repos/nin-dev-ai__harness/packages/daemon/src/daemon.ts:87) · [Socket protocol](repos/nin-dev-ai__harness/packages/daemon/src/server.ts:52) · [Project identity and adapters](repos/nin-dev-ai__harness/packages/daemon/src/project.ts:47) · [Worker slots](repos/nin-dev-ai__harness/packages/daemon/src/project.ts:102)

The daemon's journal is the authority for state transitions, assignments, approvals, route pauses, and receipts. `Store.appendMany` validates every event, writes a sequence-numbered row and applies its projection in the same SQLite transaction. Task, worker, run, result, finding, approval and usage tables are replayable. The project root holds `harness.yaml`, `.harness/checks.yaml`, task Markdown with role, acceptance and file hints, per-run prompts and event JSONL, task worktrees, and the derived `HARNESS.md` board. Git holds the actual changes and commit ancestry. Native conversation state stays in vendor-managed sessions. A journal replay restores projections. A fresh deployment also needs the corresponding task specifications, Git history and any vendor state it intends to resume. [Storage transaction and replay](repos/nin-dev-ai__harness/packages/storage/src/db.ts:29) · [Projection tables](repos/nin-dev-ai__harness/packages/storage/src/projector.ts:4) · [Task creation and mirror order](repos/nin-dev-ai__harness/packages/daemon/src/project.ts:130) · [Artifacts](repos/nin-dev-ai__harness/packages/daemon/src/supervisor.ts:83)

### Intake, planning and delegation

- **Explicit tasks and plans.** `task.add` resolves the role or chooses one using keywords, instructions, path hints and a least-loaded-writing-role tie-breaker. `plan` builds an input from the document, repo summary, writer roles and existing tasks. A readonly planner returns JSON or text from which JSON can be extracted. Harness validates shape, task keys, write roles, links and cycles, and allows one retry carrying diagnostics. It fits out-of-scope jobs to roles when possible, consolidates or orders overlapping jobs, and persists the resulting DAG in dependency order as DRAFT tasks. Approval verifies the graph and moves tasks to QUEUED. [Task RPC and approval](repos/nin-dev-ai__harness/packages/daemon/src/engine.ts:132) · [Role choice](repos/nin-dev-ai__harness/packages/daemon/src/planning.ts:69) · [Plan validation](repos/nin-dev-ai__harness/packages/planner/src/plan.ts:119) · [Retry and draft persistence](repos/nin-dev-ai__harness/packages/daemon/src/planning.ts:204) · [DAG approval](repos/nin-dev-ai__harness/packages/daemon/src/engine.ts:445)
- **Direct request and continuity.** `dispatch` records a thread and a primary writer or adds a message to the latest unfinished turn. An active implementer is stopped for a checkpoint and the message is appended on the next vendor turn. A new turn after a merge normally keeps the role, tries the prior route's native session if suitable, and otherwise builds a bounded handoff with recent request, result and changed-file data. Primary turns reuse the same directory path on successive branches to support cwd-keyed sessions. Delegated children use independent worktrees. A canceled predecessor can leave a reusable path with a historical ownership reference. [Dispatch RPC](repos/nin-dev-ai__harness/packages/daemon/src/engine.ts:321) · [Message delivery](repos/nin-dev-ai__harness/packages/daemon/src/outer-loop.ts:1087) · [Session handoff](repos/nin-dev-ai__harness/packages/daemon/src/threads.ts:25) · [Worktree path ownership](repos/nin-dev-ai__harness/packages/daemon/src/outer-loop.ts:374)
- **Delegated wave.** A successful implementer result can carry a single `DELEGATE:` JSON line. Jobs must specify file hints and acceptance. The engine rejects nested delegation and waves that exceed configured counts or overlap their siblings or the parent's current diff. It creates child tasks, records their relation and wave, approves them and pauses the parent with an explicit reason. Children pass through the ordinary scheduler, checks and merge. The parent waits for all to be merged and, on automatic landing, delivered. Failure or a blocked landing goes to a person. On resumption the engine replays parent changes on the new integration tip and adds the children's summaries. The parent does not hold its worker while the children run. - **Lead.** A settlement subscription asks an optional readonly lead to inspect the oldest settled unreported request. It uses explicit batch keys, structured findings, limited follow-up jobs and a configured round cap. It can add a few facts to the board. Task-sized model tiers and review-size configuration keep the lead from being the only mechanism for controlling spend. The lead itself calls the supervisor directly. Its per-project `busy` flag excludes another lead call during a run, and wakes arriving while busy are discarded rather than queued. Startup does not run a lead sweep on its own. ### Scheduling and worker/process handoff

The queue is a view over task rows. A project gets a 30-second clock tick and explicit kicks from commands, completion, merge and quota timers. A single `ticking` loop serializes scheduling passes, with an `again` flag to rerun after overlapping kicks. A pass prefers limit resumes, repairs and reviews ahead of queued work. It then ranks by number of transitive dependents, size S/M/L, creation time and ID. It admits only tasks whose dependencies are `MERGED`, plus `task.delivered` in auto-land mode. Per-role worker availability and the project-wide worker count include runs being finalized or gated. It also checks file hints against active work before starting an implementation, subject to the limitations in section 4. [Wake and pass](repos/nin-dev-ai__harness/packages/daemon/src/outer-loop.ts:125) · [Pass and worker count](repos/nin-dev-ai__harness/packages/daemon/src/outer-loop.ts:178) · [Work ordering and eligibility](repos/nin-dev-ai__harness/packages/daemon/src/scheduler.ts:33)

Within a role's route pool, the engine prefers an eligible previous route for the implementation/follow-up path, then ranks by the smallest known headroom and penalizes busy routes. A reviewer pool prefers a vendor independent from the implementer. Fallback routes are considered after the pool under configured policy. The engine checks CLI health, persisted route pauses, and guards. The production guard order is policy followed by quota. It tests attended/unattended policy, scope and fallback approvals, quiet hours, caps, manual limits, and estimated fit. Quota compares 5-hour and weekly estimates with each window's own headroom and estimates already in flight. It reduces the weekly reserve/pacing burden for a waiting person, and can fall back to a manual budget or an eight-run rolling limit when usage is unknown. `QuotaGuard` records measured window deltas, puts a route on a jittered reset or backoff and wakes the scheduler. All of that sits outside model reasoning. [Candidate evaluation](repos/nin-dev-ai__harness/packages/daemon/src/outer-loop.ts:217) · [Pool ranking](repos/nin-dev-ai__harness/packages/daemon/src/outer-loop.ts:283) · [Guard order](repos/nin-dev-ai__harness/packages/daemon/src/defaults.ts:5) · [Policy](repos/nin-dev-ai__harness/packages/daemon/src/policy-guard.ts:57) · [Quota admission](repos/nin-dev-ai__harness/packages/daemon/src/quota-guard.ts:168) · [Reset and backoff](repos/nin-dev-ai__harness/packages/daemon/src/quota-guard.ts:301)

Dispatch ensures `harness/integration`, syncs it toward the base before a new task, creates or reuses a task branch/worktree, and runs configured setup on creation. The prompt combines the role, task spec, checks, board and dependency handoff. Fresh resume includes a diff summary. Repair prompts refer to the specific check, review, conflict or human comment. The supervisor journals a `STARTING` run and saves the prompt, then calls the selected adapter with argv-oriented execution data, filtered environment, timeout, mode, schema and optional resume ID. `ProcessRunner` launches in a detached Unix process group, normalizes stdout and stderr, and correlates the process ID and vendor session with `started`. Supervisor appends normalized events and a terminal outcome. On ordinary cancellation it delegates TERM/KILL to the adapter's process group. [Workspace dispatch](repos/nin-dev-ai__harness/packages/daemon/src/outer-loop.ts:389) · [Prompt assembly](repos/nin-dev-ai__harness/packages/daemon/src/task-prompts.ts:25) · [Start and stream](repos/nin-dev-ai__harness/packages/daemon/src/supervisor.ts:83) · [Spawn](repos/nin-dev-ai__harness/packages/adapters/src/process.ts:85) · [Session normalization](repos/nin-dev-ai__harness/packages/adapters/src/process.ts:227)

### Verification, integration and stopping

The main task sequence is `DRAFT → QUEUED → RUNNING → GATING → REVIEWING → PR_READY → MERGED`. A separate run lifecycle records the child outcome. A usefully changed branch can still be gated after a generic agent failure. The system checkpoints write work, screens actual changed files with policy and conflict-marker checks, and runs independent configured argv checks. A failed required check moves to repair with bounded attempts. Repeated failure signatures or an unchanged tree halt repair. A reviewer reads a diff with secret paths excluded, returns structured findings and has edits reverted if the worktree hash changed. Blockers route back to repair. Review can be skipped by size while the task gate still runs. Initial and repair models can have configured S/M/L tiers. [Task state machine](repos/nin-dev-ai__harness/packages/core/src/state/task-machine.ts:4) · [After-run dispositions](repos/nin-dev-ai__harness/packages/daemon/src/outer-loop.ts:592) · [Check runner](repos/nin-dev-ai__harness/packages/verify/src/runner.ts:81) · [Gates and stall](repos/nin-dev-ai__harness/packages/daemon/src/outer-loop.ts:733) · [Review state](repos/nin-dev-ai__harness/packages/daemon/src/outer-loop.ts:833) · [Model tier](repos/nin-dev-ai__harness/packages/daemon/src/outer-loop.ts:506)

In assisted mode the human accepts the result. Approved-scope may merge automatically once approvals are satisfied. A promise chain serializes task merges per project. `mergeTask` rebases and squashes on the integration tip, independently reruns required checks, verifies tip stability and fast-forwards. A real conflict can be replayed as `git apply --3way` into the task worktree and given to the same implementer once. `MERGED` means the integration effect is recorded. Automatic landing moves the base with a fast-forward or a non-rewriting merge commit on a clean root checkout. `reconcileDelivery` issues a separate `task.delivered` receipt if the integration commit is reachable from base. Manual landing and PR actions are explicit CLI operations. The GitHub boundary builds draft evidence and refuses `gh pr merge`. [Merge serialization and landing](repos/nin-dev-ai__harness/packages/daemon/src/outer-loop.ts:874) · [Integration Git protocol](repos/nin-dev-ai__harness/packages/workspace/src/merge.ts:28) · [Conflict repair](repos/nin-dev-ai__harness/packages/daemon/src/outer-loop.ts:935) · [Base branch land](repos/nin-dev-ai__harness/packages/workspace/src/land.ts:28) · [Delivery receipts](repos/nin-dev-ai__harness/packages/daemon/src/delivery.ts:4) · [GitHub adapter](repos/nin-dev-ai__harness/packages/github/src/gh.ts:9)

Pause and takeover use an adapter stop reason and checkpoint for later continuation. Takeover returns an interactive command to the CLI, which owns that interactive process. Stop cancels supervised agent runs and closes the socket and DB. On boot, recovery tries to kill prior active groups by recorded PID, writes `run.crashed`, checkpoints, requeues `RUNNING`/`GATING`, and resets worker slots other than explicitly paused slots. `REPAIRING` and `REVIEWING` are discoverable by the resumed scheduler. A persisted merge event allows recovery to restore the task's `MERGED` projection. Active process registration, effects between journal writes and shutdown joins determine how far those guarantees extend. [Pause, cancel and takeover](repos/nin-dev-ai__harness/packages/daemon/src/outer-loop.ts:977) · [Daemon stop order](repos/nin-dev-ai__harness/packages/daemon/src/daemon.ts:133) · [Recovery](repos/nin-dev-ai__harness/packages/daemon/src/recovery.ts:17)

## 4. What it does well and poorly, with source evidence

### Strengths

**Mechanical verification has real authority.** Checks use argv, a filtered environment, and a process-group deadline. The task and run states distinguish process completion from accepted work. Gate repair prompts use actual failure tails and a diff summary, and the stall detector stops replacement runs that make no progress. The credential-free CLI demo confirmed a claimed success failed the gate, the existing fake session repaired it, and the later checks passed. Independent review, checkout-based verification and bounded conflict repair make simple autonomous workflows practical on a repository with strong checks. [Check execution](repos/nin-dev-ai__harness/packages/verify/src/runner.ts:50) · [Failure evidence in repair prompts](repos/nin-dev-ai__harness/packages/daemon/src/task-prompts.ts:46) · [Stall controls](repos/nin-dev-ai__harness/packages/daemon/src/outer-loop.ts:780) · [False-success regression test](repos/nin-dev-ai__harness/tests/e2e/outer-loop.test.ts:77)

**The system has meaningful integration tests for a local supervisor.** The fake adapter spawns a real scripted CLI, and adapter-contract tests reuse the process runner with vendor fixture replay. The test suite drives SQLite WAL persistence, Git worktrees and conflicts, Unix socket subscription, detached CLI startup and real forced daemon kills. The number of passing assertions includes exhaustively generated state-machine cases. The most consequential positive evidence is the real-process recovery test, where an acknowledged group and its child were gone after restart and one integration commit per task remained. [Fake process adapter](repos/nin-dev-ai__harness/packages/adapters/src/fake/index.ts:92) · [Reusable adapter contract](repos/nin-dev-ai__harness/packages/adapters/src/contract-suite.ts:29) · [Crash assertions](repos/nin-dev-ai__harness/tests/e2e/crash-recovery.test.ts:57)

**Handoffs preserve useful context and can be reviewed after the fact.** The board is derived and atomically rewritten, with a bounded prompt excerpt. Native sessions coexist with dependency and conversation handoffs drawn from journal evidence. The distinction between integration and base-branch delivery addresses a real failure mode described in the repository, where work was considered complete while the user's branch still lacked it. The project retains a rewritten integration history under a dated name, and exposes dirty base or Git conflicts as landing blockers. ## 8. Post-mortem: design pressures, accumulated tradeoffs, likely failure modes, and the highest-leverage improvements

**Three useful constraints shaped the software.** It targets one local Git repository at a time from a user's viewpoint, relies on already-installed agent CLIs and subscriptions, and wants rapid unattended progress with checkable results. Worktree-local writes, an append-only journal, external providers and a deterministic outer loop meet those constraints without requiring a new agent runtime or a service. The repository records practical pressures behind the current design. Codex sometimes announced the session after other output, so the parser delayed `started`. Claude needed a stable cwd for native resume, so later turns reuse a path. Integration-only work went unseen on `main`, so landing became automatic. Weekly pacing stalled an attended request, so its blocking rule changed. The adaptive decisions fixed each immediate workflow issue. Each also broadened an ownership or state contract. [Delayed `started` decision](repos/nin-dev-ai__harness/docs/DECISIONS.md:49) · [Delivery diagnosis and Phase 3](repos/nin-dev-ai__harness/docs/PROGRESS.md:50) · [Stable cwd and attended pacing decisions](repos/nin-dev-ai__harness/docs/DECISIONS.md:174)

**Process incident chain.** An adapter starts a detached process, then an output parser waits to decide what `started` should say. The supervisor's durable representation gets the PID only from that normalized event. Killing the daemon between spawn and announcement discards its only live ownership map. Recovery then accepts a null PID as lack of cleanup work and requeues the task. Without ownership evidence, the original actor can still hold an old worktree while a replacement starts. The highest-leverage change is a launcher-owned identity and launch handshake independent of provider output, captured early enough to reconcile pending starts. Use one cancellation scope for phase preparation, the child process, auxiliary commands and finalization. Record old and new phase, cancel intent and join disposition. [Detached spawn and delayed `started`](repos/nin-dev-ai__harness/packages/adapters/src/process.ts:95) · [Started projection](repos/nin-dev-ai__harness/packages/storage/src/projector.ts:67) · [Recovery ordering](repos/nin-dev-ai__harness/packages/daemon/src/recovery.ts:23)

**Delivery incident chain.** The product added automatic base landing after a safe integration workflow already existed. A design that recorded Git operation results after the fact now relies on those receipts for dependency ordering and completion. A kill after the ref update leaves no durable intent tying the verified commit to its task. A divergent base requires a new tree, while the only recheck ran on a different Git commit. Reachability then turns an ancestor relationship into a delivery status for the whole request. A versioned prepared effect with the old tip, candidate commit, check inputs and target tree can make retries reconcile actual refs. For a divergent base, compute and verify the prospective merge tree before moving the user-visible ref. [Effect boundary](repos/nin-dev-ai__harness/packages/daemon/src/outer-loop.ts:899) · [Divergent landing](repos/nin-dev-ai__harness/packages/workspace/src/land.ts:35) · [Delivery check](repos/nin-dev-ai__harness/packages/daemon/src/delivery.ts:4)

**Orchestration incident chain.** The scheduler can derive a queue from state, which keeps the implementation small. That works while every relevant transition preserves its phase and a reliable wake follows each durable change. Using `PAUSED` and prose reasons for different work kinds lost the review phase. Config reload adds rows without reconciling ownership. Child waves and lead batches have persistently identifiable inputs, but admission spans events and lead processing is triggered by a transient wake. The fix is a restartable phase model with typed scheduling scope and durable work eligibility. Use a prepared launch plus generation check at the final effect boundary, drain every settled lead batch, and make a child wave's accepted state equivalent to parent waiting. Preserve human pauses and role limits across reload and restart. [Persisted scheduler payload](repos/nin-dev-ai__harness/packages/core/src/schemas/events.ts:112) · [Live selection by phase](repos/nin-dev-ai__harness/packages/daemon/src/scheduler.ts:70) · [Delegation reconciliation condition](repos/nin-dev-ai__harness/packages/daemon/src/outer-loop.ts:708) · [Lead busy handling](repos/nin-dev-ai__harness/packages/daemon/src/lead.ts:70)

**Reliability ceiling.** The verified happy path justifies using the framework for small local runs with strong project checks and recoverable branches. Treat unattended base changes, concurrent projects, and workflows that repeatedly pause or survive daemon failure as higher-risk until the ownership and commit invariants are enforced together. Simulated pooling shows deterministic dispatch behavior. It provides no performance or quality comparison with a single agent, and historical live results in `docs/PROGRESS.md` describe different environments. [Test and metric definitions](repos/nin-dev-ai__harness/docs/PRD.md:962) · [Historical live suite claims](repos/nin-dev-ai__harness/docs/PROGRESS.md:53)
