**Assessment.** Pydantic AI's strongest design choice is the normalized, typed conversation protocol shared by a small graph loop, provider adapters and application code. The loop stays recognizable across tool dispatch, structured retries, partial results and durable replay. The largest maintenance cost sits at transitions where several representations of the same run must agree. In particular, a deadline can have been computed while the preparation work it covers is still outside the cancellation scope. A delegated tool can wait on a slot its own parent holds. Both behaviors are supported by archived local controls and source inspection. The completed test selection supports the core architecture with the scope and version limits in sections 7–8.

## 2. Core architecture and end-to-end control and data flow

### Entry points, setup, and graph

```text
agent.run / iter / run_stream / run_stream_events
  -> resolve conversation and assemble run configuration
  -> open run and resources -> UserPromptNode
  -> ModelRequestNode: record request -> prepare step -> serve attempt(s)
  -> CallToolsNode: classify response -> validate / execute / defer
       -> ModelRequestNode with tool returns, feedback or new input
       -> End(FinalResult), with the settled tail recorded
       -> End(DeferredToolRequests), with open calls resumable from history
```

1. **Public entry.** `Agent[DepsT, OutputT]` holds reusable model, tool, output and capability configuration. `AbstractAgent.run()` opens `iter()`, advances through the hook-aware `AgentRun.next()` until `End` or a replacement result, and returns the settled result after the run context closes. An event handler can make a normally buffered run stream both model and tool nodes, then drain the handler's remaining events on normal return. `iter()` resolves a supplied `Conversation` or the separate history, usage and ID inputs, awaits `_prepare_run()` and opens its returned `_PreparedAgentRun`. `run_sync()` drives the async path. The synchronous streaming path has its own bridge to preserve the loop and context of its asynchronous resources. [Run driver](repos/pydantic__pydantic-ai/pydantic_ai_slim/pydantic_ai/agent/abstract.py:634), [agent entry](repos/pydantic__pydantic-ai/pydantic_ai_slim/pydantic_ai/agent/__init__.py:1623), [sync bridge](repos/pydantic__pydantic-ai/pydantic_ai_slim/pydantic_ai/_sync_stream.py:184).

2. **Assembly.** Per-run overrides and spec contributions influence the bootstrap model, retries, instructions, settings and capabilities. A static or dynamically selected model is needed to build the first `RunContext`. Bootstrap selection can receive the intended step-one prompt, existing history, IDs, usage limits and deadline. The framework then assembles per-run capabilities and toolsets, derives output processors and output tools, and stores a model settings resolver so a later step can use a different selected model. The precedence for settings is model defaults, agent settings, capabilities and run settings, with model-specific preparation applied per attempt. An explicit run or override model can bypass capability selection. Run IDs distinguish executions. Conversation IDs correlate successive runs. [Bootstrap and precedence](repos/pydantic__pydantic-ai/pydantic_ai_slim/pydantic_ai/agent/__init__.py:1689), [step-one context](repos/pydantic__pydantic-ai/pydantic_ai_slim/pydantic_ai/agent/__init__.py:1849), [settings and tools](repos/pydantic__pydantic-ai/pydantic_ai_slim/pydantic_ai/agent/__init__.py:2133), [graph inputs](repos/pydantic__pydantic-ai/pydantic_ai_slim/pydantic_ai/agent/__init__.py:2290).

3. **Resource scope.** `_PreparedAgentRun.open()` owns the exit stack, controller attachment, deadline timer, agent limiter, selected model lifetime, graph lifetime, capability lifecycle and toolset entry. It enters the cancellation translation context early so translation occurs after history-producing teardown. A separate stack for models stays open through settlement of any accepted pending response. Toolset entry is inside the propagated capability context so lifecycle work can share the run's instrumentation. The run can retain diagnostics after resources have closed. [Exit ordering](repos/pydantic__pydantic-ai/pydantic_ai_slim/pydantic_ai/agent/__init__.py:5012), [admission and models](repos/pydantic__pydantic-ai/pydantic_ai_slim/pydantic_ai/agent/__init__.py:5078), [graph and lifecycle entry](repos/pydantic__pydantic-ai/pydantic_ai_slim/pydantic_ai/agent/__init__.py:5139).

4. **Graph.** The agent caches its fixed graph by name. The registered nodes are `UserPromptNode`, `ModelRequestNode`, `CallToolsNode` and the stream finalizer `SetFinalResult`. `BaseNode.run()` returns a concrete next node or `End`. `GraphBuilder` derives edges from return annotations, and `GraphRun` owns scheduling and task teardown. This internal graph is fixed and the builder opts out of the generic structure-validation pass. The generic graph runner tracks tasks in an AnyIO task group and aggregates forked inputs into reducers by join and fork instance. Tool concurrency is handled separately by the agent's tool scheduler. Normal agent advancement consumes one pending node at a time. It converts between the engine's task requests or terminal markers and the public node objects. `AgentRun` deliberately resynchronizes the graph after a hook replaces or recovers an outcome. Graph task errors travel through `ErrorMarker`, preserving the originating exception for recovery. `async for` yields a node before executing it and detects advancement the caller already performed so it can avoid a second execution. 5. **State and injection.** `GraphAgentState` carries the transcript, usage, retry totals, run step, IDs and pending event/message buffers. `GraphAgentDeps` carries run resources and policies, including `user_deps`, the current model, schema, tool manager, capability graph and controller. `build_run_context()` projects them to the public typed API. `RunContext[DepsT]` gives a tool, instruction factory or hook the application dependency object, plus selected model, history, per-run limits, tool IDs and retry state. Function signature inspection excludes the first typed context parameter from the model's schema and inserts it when the tool runs. Closures and a task-local current context support model wrappers without changing the basic model signature. Pydantic validation context is a separate application-supplied value or a value computed from a run context. It goes to Pydantic's validators. ### One request step

6. **Prepare history and request.** `UserPromptNode` normalizes supplied history, prepares the opening or resumed request, restores dynamic system prompts and handles exceptional tails. A suspended provider response can be continued when there is no new prompt. Provided results for a deferred call dispatch against the stored response directly. A trailing interrupted request can lead to synthesized returns for abandoned calls. An unresolved live call or suspended turn can block a new prompt until explicitly resolved. The request node appends the current request, increments the step counter, selects the model, refreshes capability and tool discovery state, prepares the tool manager, resolves instructions and settings, and builds a `ModelRequestContext` with normalized messages and `ModelRequestParameters`. [Prompt and resume](repos/pydantic__pydantic-ai/pydantic_ai_slim/pydantic_ai/_agent_graph.py:1285), [deferred resume](repos/pydantic__pydantic-ai/pydantic_ai_slim/pydantic_ai/_agent_graph.py:1435), [tail repair](repos/pydantic__pydantic-ai/pydantic_ai_slim/pydantic_ai/_agent_graph.py:1534), [request prepare](repos/pydantic__pydantic-ai/pydantic_ai_slim/pydantic_ai/_agent_graph.py:3233).

7. **Separate the step from the attempt.** `wrap_model_request` encloses the step. Its handler is single-use. `before_model_request` runs before the attempt loop. The attempt baseline captures the step's inputs so a retry can restore them and resolve the next model's preparation, native tools, settings and wrappers. Settings start from model defaults and merge agent, capability and run layers. On a model change the new model gets those layers and hook edits over its own defaults. Model-sensitive instructions resolve again, while toolset instructions remain tied to the step. That preserves the step's tool state and avoids scheduling another durable toolset discovery unit. `prepare_model_request` receives the model about to serve that attempt. It is the appropriate hook for model-dependent request changes. Normalization gives adapters a provider-valid projection. Optional token counting uses that projection and a copy of usage to check projected consumption. An accepted response enters history. A rejected, billed attempt can contribute usage and failed-attempt details independently of whether its response enters history. [Step wrapper](repos/pydantic__pydantic-ai/pydantic_ai_slim/pydantic_ai/_agent_graph.py:3034), [attempt loop](repos/pydantic__pydantic-ai/pydantic_ai_slim/pydantic_ai/_agent_graph.py:3095), [provider-response accounting](repos/pydantic__pydantic-ai/pydantic_ai_slim/pydantic_ai/_agent_graph.py:3145), [attempt preparation](repos/pydantic__pydantic-ai/pydantic_ai_slim/pydantic_ai/_agent_graph.py:3712), [Settings layers](repos/pydantic__pydantic-ai/pydantic_ai_slim/pydantic_ai/agent/__init__.py:5611), [Attempt-specific resolution](repos/pydantic__pydantic-ai/pydantic_ai_slim/pydantic_ai/_agent_graph.py:3662).

8. **Adapter boundary.** A `Model` implements `request`, with extension points for streaming, counting, suspended work, compaction and lifecycle as applicable. The graph passes model messages, settings and request parameters. A provider supplies the SDK client and provider defaults, and a model profile expresses features such as schema output, native tool support and message representation. The adapter parses provider output back to common parts and usage. For example, OpenAI Chat and Anthropic have translation functions on opposite sides of the same model contract. The common preparation resolves requested versus supported output modes, native/local tool variants, relevant schema transformations and request settings. Provider classes own client and API configuration. Profiles describe API or model-family support facts. An individual adapter renders the resulting request and maps response parts, finish state and usage back to the common protocol. `FunctionModel` gives a controlled application callback this same boundary for ordinary tests. `TestModel` generates deterministic responses and schema-derived tool arguments. 9. **Continuation and commit.** A provider can report a suspended response. The core continuation loop keeps one logical model step across multiple segments, with separate ceilings for resumed generation and polling a continuing job, and merges parts according to continuation mode. The pending-output type lets the app retain a still-running request. The accepted response is settled at run exit while the serving model is still entered. Cancellation or abandonment withdraws the live job where the model supports that operation. The accounting path subtracts any suspended seed already billed by an earlier run and checks provisional usage between segments. A compatible suspended response in history can seed a new run, with previously billed usage subtracted. `PendingModelResponse` lets a willing caller detach a still-pending job. Cancellation and abandonment have explicit cleanup paths. After a response is accepted, the commit path stamps IDs, updates the run step count and preserves the response for a later run even if its billed usage stops the current one. A usage stop before dispatch marks the committed history response interrupted. ### Tool execution, approvals, and output

10. **Discover and validate.** Toolsets own composition, discovery, instructions and execution. A `FunctionToolset` creates tool definitions from signatures and prepared metadata. Combined and wrapper toolsets preserve routing to the source tool, can filter or rename definitions, and control resource entry. `ToolManager.for_run_step()` populates one exposed-name map and carries retry state between steps. An availability change can cause re-resolution within the same step without replaying the dynamic toolset lifecycle or advancing retries twice. `validate_tool_call()` returns a `ValidatedToolCall` carrying the call, selected tool, per-call context, validated arguments or failure, and any valid deferral. Pydantic core checks JSON or Python input before the tool is executed. The validation hooks may adjust the arguments or the outcome. Async functions run on the loop. Ordinary sync functions run in a worker thread when enabled. 11. **Dispatch and settle.** `CallToolsNode` identifies actionable text, images and local tool calls from normalized response parts. It treats native tool exchanges as response data and gives actual local calls priority over a plain-text preamble. In buffered early mode, a valid structured text or image result can preempt ordinary local function calls, while co-emitted output tools and deferred calls keep their own arbitration. `process_tool_calls` chooses an end strategy. `early` favors successful output and records skips for unneeded sibling function calls. The default `graceful` completes preceding function batches before an output tool, skips later output tools after the first success, and can still run function tools. `exhaustive` runs all eligible tools, with the first successful output in model emission order winning. Explicit sequential tools split execution into barriers. A true function-tool retry can suppress a tentative graceful or exhaustive output. An unknown-tool retry, an output-tool retry alongside another valid output, and already committed streamed output have different rules. Tool result events can be delivered as tasks complete, while result parts are gathered into stable emission order. [Response routing](repos/pydantic__pydantic-ai/pydantic_ai_slim/pydantic_ai/_agent_graph.py:4320), [end strategies](repos/pydantic__pydantic-ai/pydantic_ai_slim/pydantic_ai/_tool_execution.py:387), [retry predicate](repos/pydantic__pydantic-ai/pydantic_ai_slim/pydantic_ai/_tool_execution.py:1125), [strategy implementations](repos/pydantic__pydantic-ai/pydantic_ai_slim/pydantic_ai/_tool_execution.py:1349), [result assembly](repos/pydantic__pydantic-ai/pydantic_ai_slim/pydantic_ai/_tool_execution.py:1021), [Early-mode candidate policy](repos/pydantic__pydantic-ai/pydantic_ai_slim/pydantic_ai/_agent_graph.py:4450), [Plain and structured output controls](repos/pydantic__pydantic-ai/tests/test_agent.py:5636).

12. **Pause and resume.** A definition can mark an external call or require approval. A local body or an appropriate validation phase may also defer a call. The normal graph dispatch validates before collecting pending calls, preserves the original arguments and records a JSON-compatible validated view by call ID. Approval can supply replacement arguments. Resume revalidates these or the original arguments, so a stateful validator can produce a different value from its earlier display projection. It emits `DeferredToolRequestsEvent`, permits a capability to supply results inline, emits `DeferredToolResultsEvent` for those answers, and uses the same call-processing machinery for the approved result. A remaining batch becomes `DeferredToolRequests` when the output spec permits it. `Conversation` can preserve that batch, including classification and metadata beyond the raw transcript. On resume the graph matches results to eligible call IDs and rejects ambiguous duplicate IDs or attempts to replace completed returns. It revalidates approved inputs, optionally from `ToolApproved.override_args`, and uses explicit denial or external result values to settle other calls without invoking a local body. Revalidation means intervening application state can change the arguments, even when the original model data is unchanged. ### History, streaming, limits, and cancellation

14. **History as data.** `ModelRequest` and `ModelResponse` are typed messages with discriminated parts. The Pydantic message adapter handles the persistent form, including typed tool parts and provider provenance. `all_messages()` returns the transcript and `new_messages()` returns the run delta. The framework separately resolves which messages a conversation store still needs. The store represents history as linked entries with a revisioned head. A save appends a suffix and swaps the head with compare-and-set semantics. A fork can share old entries, and a branch can preserve the prior head while changing what gets loaded. Backends own the write transaction and can override an entry-by-entry read. Normalization merges adjacent compatible requests and repairs missing or orphaned tool exchanges. Request preparation can lower typed deltas and instructions to a provider's supported representation while preserving the richer stored form. History processors and request hooks can intentionally change history. Appending instruction/tool changes where supported reduces avoidable prompt-prefix churn. [Message protocol](repos/pydantic__pydantic-ai/pydantic_ai_slim/pydantic_ai/messages.py:3781), [serialization](repos/pydantic__pydantic-ai/pydantic_ai_slim/pydantic_ai/messages.py:6033), [clean and repair](repos/pydantic__pydantic-ai/pydantic_ai_slim/pydantic_ai/messages.py:6661), [wire projection](repos/pydantic__pydantic-ai/pydantic_ai_slim/pydantic_ai/models/__init__.py:1977), [history accessors](repos/pydantic__pydantic-ai/pydantic_ai_slim/pydantic_ai/run.py:1116), [Store backend contract](repos/pydantic__pydantic-ai/pydantic_ai_slim/pydantic_ai/conversation_store.py:745).

15. **Three streaming surfaces.** The adapter supplies a `StreamedResponse`, whose parts manager tracks vendor indexes and merges deltas into snapshots. Start, delta and end events surface through the stream together with a first potential output marker. It signals that an output *can* be formed, before full validation. `AgentStream` adds event middleware, token checks, request state and partial or final validation. `run_stream()` exposes a `StreamedRunResult` at the first output candidate and settles it through `SetFinalResult`. Its committed-output policy gives different retry and node-hook behavior from ordinary graph completion. `run_stream_events()` drives `run()` behind a zero-buffer channel, yielding intermediate model and tool events and a settled result event after producer completion. `iter()` lets callers inspect the graph and stream chosen nodes explicitly. Its node streams cache their outcome to avoid executing the same turn twice. Exiting an event-stream context closes and drains the producer. `ProcessEventStream` can tap this stream with backpressure or transform the events seen by consumers. A text-delta transform can change streamed chunks while final validation reads the underlying accumulated response. Omitting an output marker changes when the early-result API can yield. The synchronous stream bridge keeps the context manager on one owner task and pumps updates, draining pumps before releasing that owner. A stream-only cancel records an interrupted response. Run cancellation owns the larger graph. 16. **Accounting and retries.** `UsageLimits.request_limit` limits committed logical steps and defaults to 50. Each response may include actual usage from several attempts or continuation segments. ## 3. Why the design works and governing invariants

| Invariant | Consequence |
| --- | --- |
| The graph topology is reusable and each execution has its own state and resources. | A typed `End` aggregates output independently of a particular provider. Tool retries, queued events and cancellation are scoped to a run. A shared agent configuration can support concurrent runs while individual resource scopes manage entry and exit. |
| A request step, serving model attempt and provider exchange have distinct identities. | The next model can rebuild parameters from the step's baseline. Billed attempts remain visible to accounting even when the transcript only carries the accepted step. A continuation can span several provider exchanges without pretending each is a new graph turn. |
| Tool result identity is grounded in call IDs, the selected tool definition and its underlying dispatch identity. | Positional completion order cannot assign results to arbitrary calls. Deferred results have to bind unambiguously to the transcript. Skipped, denied, retried and interrupted operations can leave explicit records so a later request has coherent history. |
| Output machinery performs local validation across provider modes. | The response transport and the Python output type can evolve independently. A provider schema can guide generation and Pydantic still validates what the application receives. Partial validation is identified in context, and a potential result event does not establish that a complete schema has been satisfied. |
| Transcript ordering and live event delivery are separate. | Tools can finish in any order within a segment while recorded returns preserve emission order. Ordered event mode also serializes presentation of function results. The default dispatcher chooses a propagating task failure in emission order in this mode. Exhaustive dispatch has a different error path. Replay-sensitive adapters can choose stricter policies. |
| Some context members are intentionally shared by identity within one run. | A shallow derived context can signal cancellation, enqueue work or emit an event seen by the owning graph. Replacing one of these objects would strand changes. A durable boundary explicitly snapshots data that cannot share that identity. |
| Cancellation is terminal and has a single outer translation boundary. | Nested teardown can finish writing state before a typed error is produced. An outer runtime retains its native external cancellation signal. The response-only stream cancel has a separate meaning from cancelling the whole run. |
| Persistent history, outgoing request projection and telemetry have different purposes. | The saved transcript retains typed state and origins. Each serving adapter can project it into its wire representation. Observability can project an independently configured view without rewriting the transcript. |
| Durable identity and result shape outlive Python implementation details. | A registered operation name, relative ordering and payload shape are compatibility data. Replay can reuse journaled answers while rebuilding the in-process graph and rehydrating data at the operation boundary. |

The strongest local implementation of these ideas is the explicit response-commit transition. A normalized response that reaches the acceptance boundary gets its run metadata and usage. If a post-response limit rejects further processing, the graph records it as interrupted so a caller can make an informed continuation. This reduces duplicate model work and gives callers usable diagnostics. A related tool transition saves collected returns before propagating the interruption. These guarantees depend on where teardown occurs, on the completeness of provider usage and on the caller selecting the appropriate resume policy. [Response commit](repos/pydantic__pydantic-ai/pydantic_ai_slim/pydantic_ai/_agent_graph.py:4064), [tool interruption](repos/pydantic__pydantic-ai/pydantic_ai_slim/pydantic_ai/_agent_graph.py:4624), [resume repair](repos/pydantic__pydantic-ai/pydantic_ai_slim/pydantic_ai/_agent_graph.py:1534).

### Documented behavior and maintainability costs

- **Final-output streaming commits before ordinary graph arbitration can finish.** `run_stream()` and `run_stream_sync()` reserve the first potential output event. ## 9. Post-mortem and prioritized improvements

The architecture balances three pressures. The graph must support a typed, inspectable transcript across providers with different wire protocols and continuation models. Middleware can change a turn before it runs, around the real request, after a response, or when it fails. Streaming and durable execution make portions of that work externally visible or replayable at distinct boundaries. These pressures explain the separate logical step and provider attempt, the choice to preserve raw tool arguments alongside validated values, and the durable indirection around individual operations. They also explain why a new state field or hook can require changes in several projections and lifecycles. The highest maintenance risk is a correct implementation in each subsystem with an omitted or mismatched contract at their junction. [Attempt boundary](repos/pydantic__pydantic-ai/pydantic_ai_slim/pydantic_ai/_agent_graph.py:497), [stream completion](repos/pydantic__pydantic-ai/pydantic_ai_slim/pydantic_ai/agent/abstract.py:1134), [context projection](repos/pydantic__pydantic-ai/pydantic_ai_slim/pydantic_ai/durable_exec/_run_context.py:277).

1. **P1 · Make preparation timing an explicit public lifecycle boundary.** Decide which selector, capability, and toolset setup work a deadline can interrupt and when a pre-fired token is checked. To meet the current broad guidance, bind cancellation before those callbacks using an outer owner scope, install the inherited deadline there, and preserve the existing typed cancellation and partial-conversation behavior as run state becomes available. Account for the distinction between early rejection of an already-cancelled token and cancellation initiated by a setup hook. An alternate compatibility path is a documented two-phase contract with explicit preparation timing. Use existing virtual-clock and event-blocker patterns to pin exact phase coverage and teardown, including a selector, a stateful `for_run()`, a toolset factory, and the limiter. Check durable identity and timer placement before moving the boundary across a durable operation. [Cancellation scope](repos/pydantic__pydantic-ai/pydantic_ai_slim/pydantic_ai/agent/__init__.py:5012), [deadline and selection](repos/pydantic__pydantic-ai/pydantic_ai_slim/pydantic_ai/agent/__init__.py:1849), [clock test](repos/pydantic__pydantic-ai/tests/test_run_timeout.py:649), [setup cancel policy test](repos/pydantic__pydantic-ai/tests/test_run_cancellation.py:2065), [durable time](repos/pydantic__pydantic-ai/pydantic_ai_slim/pydantic_ai/durable_exec/temporal/_durability.py:585).

2. **P1 · Define nested admission on shared pools.** The safe initial contract is to reject a descendant's queued acquisition if its ancestor still owns a permit in that pool. Preserve the existing direct same-task guard, the passing cross-task case with spare capacity, and ordinary queueing for independent runs. A conservative rejection can also reject a request that would have unblocked when a different owner finished, so document the rule and apply it at the built-in limiter's queue boundary. A check across agent and model admission needs an explicit run or lease lineage and must exclude stale context copied to a task that outlives its owner. A capacity decision needs to participate in the limiter's acquisition path, avoiding a separate preflight race. Broader saturated sharing across several owners needs a separate policy and coverage. Document separate pools or a shared model-operation pool for callers who need delegation today. Extend the existing deterministic queue tests to exercise all tool modes and the child-model wrapper. [Current task ownership check](repos/pydantic__pydantic-ai/pydantic_ai_slim/pydantic_ai/agent/__init__.py:5109), [semaphore fast path and queue](repos/pydantic__pydantic-ai/pydantic_ai_slim/pydantic_ai/concurrency.py:202), [model wrapper composition](repos/pydantic__pydantic-ai/pydantic_ai_slim/pydantic_ai/models/concurrency.py:93), [spare-capacity contract](repos/pydantic__pydantic-ai/tests/test_concurrency.py:557).

3. **P2 · Preserve conversation storage semantics when settling streams.** Give buffered and streamed settlement a shared projection for revision, unsaved/store boundary, transcript, usage and identifiers. Establish history ownership explicitly so saving the result and continuing the conversation advances the expected revision. Use a stored conversation, a window, an archived branch, and normal completed streaming as controls against the native graph result and the already-settled deferred-result branch. The source currently predicts a revision conflict for the normal case. A focused regression should establish it before shipping a change, and should check both saved content and successful reuse of the resulting revision. [Buffered settlement](repos/pydantic__pydantic-ai/pydantic_ai_slim/pydantic_ai/run.py:317), [streamed settlement](repos/pydantic__pydantic-ai/pydantic_ai_slim/pydantic_ai/result.py:690), [store update](repos/pydantic__pydantic-ai/pydantic_ai_slim/pydantic_ai/conversation_store.py:323), [saved result continuation test](repos/pydantic__pydantic-ai/tests/test_conversation_store.py:1209).

4. **P2 · Align extension and streaming contracts with tests.** Pin which hooks run at terminal stream completion, the handling of subsequent calls, and when a deferred call has validated arguments. Keep final-output streaming's early visibility and the full-run event API's graph completion semantics explicit. Specify whether a settled stream result carries the final lifecycle hook's replacement, and when that result becomes observable. Treat changes to observed candidates as compatibility work because a consumer can act before validation finishes. Clarify validation-context refresh at its actual scope, or specify an explicit per-validation refresh policy. Validate composition requirements in the one-capability case along with other ordering controls if the singleton source observation is confirmed.
