## 2. Core architecture and end-to-end control and data flow

### Reusable loop and concrete host

## 5. Weaknesses and evidence status

### F1. Release can admit overlapping direct replies for the same session

**Reproduced.** A direct `StateMachineServices::reply` with a gated provider produced one chunk and stayed open. A second direct reply with the same session ID was rejected. `release_session` then returned while the first token stayed uncancelled and the first stream remained pending. After re-pinning a local provider, a second direct reply for the same ID streamed a chunk while the first was still open. ### F4. Effect batches can become partially durable, and drops discard live partial output

**Reproduced, batch commit.** A normal `[RecordUsage, AppendMessage, AppendMessage]` batch persisted both rows and usage and emitted usage/message-usage events. **F2 — a successful operation that never advances.** The fixture uses real persisted rows with unique IDs, one request, one kickoff, an allow decision per request, and a full reload before every step. This rules out colliding IDs, a wrongly chosen kickoff, retry decisions, malformed tool arguments and mistakes from caching the session in the fixture. The 99/100 differential matches the database's reverse insertion-ID query: 99 later rows leave the request as the hundredth match. At 100 the query returns only later rows, commits zero changes and returns `Ok(())`. Dedicated `StateMachine::step` calls bound the measurement. The full Goose builder reuses that same operation and effect handler, with approval ahead of executors and turn cap. In the stable transcript shape, earlier steps pass and the repeated approval prevents later steps from getting a turn. A tiny fixture using an in-memory effect handler with an exhaustive patch search would miss the issue. The observed history is deliberately seeded, so provider-specific occurrence rates remain open. [Fixture]($HOME/.cache/goose-runtime-review.QQbFwK/probes.rs:437), [four sizes]($HOME/.cache/goose-runtime-review.QQbFwK/probes-run2.log:36), [storage search](repos/aaif-goose__goose/crates/goose/src/session/session_manager.rs:3053), [production step priority](repos/aaif-goose__goose/crates/goose/src/agents/state_machine_builder.rs:170), [stdio smoke's exhaustive in-memory patch](repos/aaif-goose__goose/crates/goose-agent/tests/mcp_extension.rs:253).

The normal confirmation flow can account for those rows without direct database seeding. Consider an ordinary turn without a recipe in which one agent-visible message contains 50 distinct valid calls to advertised tools and the host policy asks about every call. The approval batch inserts one separate confirmation row per call after its metadata patch. All of its initial patches can still find the originating row because at most 49 later rows exist at the time of the last patch. Each answer is a separate persisted row. The host waits for all 50 answers before applying a state-machine decision, at which point there are at least 100 later rows. For any allowed call still in that originating message, the approval step can now repeat its patch without advancing. Proactive compaction passes over the open calls. ## 9. Post-mortem and highest-leverage improvements

The main design pressure is to let a turn resume using the same durable material that users and providers already exchange. This keeps the generic engine small and the host extensible. It makes correctness depend on every operation agreeing on what counts as a kickoff, an open call and a completed step. The transcript simultaneously records historical events, supplies working state for operations and offers provider-specific projections. A seemingly local optimization such as a limited patch search can defeat the workflow's progress invariant. A future state index should preserve the transcript and make the active workflow view explicit. [Operation note contract](repos/aaif-goose__goose/crates/goose-agent/src/operation.rs:96), [reconstruction control](repos/aaif-goose__goose/crates/goose/src/agents/state_machine/tests/pipeline.rs:539), [tool state join](repos/aaif-goose__goose/crates/goose-agent/src/tool_call_state.rs:29), [storage patch](repos/aaif-goose__goose/crates/goose/src/session/session_manager.rs:3053).

The other pressure is responsiveness over long-running operations. Live messages publish early, pending decisions and remote processes live in memory, and tool snapshots can legitimately outlive a manager selection. As long as one owner keeps polling, the system can finish and reconcile most states.
