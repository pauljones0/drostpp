## 2. Core architecture and control flow

### 2.1 Direct agent, typed state, and event stream

`Agent` composes a `ChatModelBase`, `Toolkit`, `AgentState`, optional workspace/offloader and middleware. It exposes `reply_stream` and `reply` over the same implementation. The stream yields typed lifecycle events and optionally a final `Msg`. The convenience method consumes the stream and returns the final message. `observe` takes the input normalization path without performing inference. A new request deep-copies and validates its inputs, processes unsupported media, assigns a fresh `ReplyContext`, and emits `ReplyStartEvent`. A continuation applies a user decision or external result against the current parked calls and retains the reply ID and iteration count. An interrupt event closes a parked reply. Running work is interrupted by cancelling the owner task. [Construction](repos/agentscope-ai__agentscope/src/agentscope/agent/_agent.py:133) · [Public methods](repos/agentscope-ai__agentscope/src/agentscope/agent/_agent.py:279) · [Input dispatch and reply context](repos/agentscope-ai__agentscope/src/agentscope/agent/_agent.py:1051) · [Input normalization](repos/agentscope-ai__agentscope/src/agentscope/agent/_agent.py:2062) · [Interrupt event contract](repos/agentscope-ai__agentscope/src/agentscope/event/_event.py:495)

The central loop chooses between read-only instructions `Reasoning`, `Acting`, and `Exit` using the current reply's unfinished calls, pending interaction, structured-output state and iteration budget. It then runs the chosen action. Reasoning may compress context and add runtime hints before assembling the system prompt, summary, context and active tool schemas. The model's terminal response is committed to the context, and the model's deltas are independently translated into start, delta and end events. A round counts after each generated call has a result. On the ordinary iteration limit, the loop can make a finalization call with tools disabled. Structured output uses a temporary `GenerateStructuredOutput` tool and a bounded grace window, and returns its validated value in the final message. [Loop](repos/agentscope-ai__agentscope/src/agentscope/agent/_agent.py:1161) · [Next-action logic](repos/agentscope-ai__agentscope/src/agentscope/agent/_agent.py:3657) · [Model input](repos/agentscope-ai__agentscope/src/agentscope/agent/_agent.py:3355) · [Reasoning stream and commit](repos/agentscope-ai__agentscope/src/agentscope/agent/_agent.py:1748) · [Structured output tool](repos/agentscope-ai__agentscope/src/agentscope/agent/_structured_output_tool.py:42)

`Msg` contains role, author, identity, usage, outcome and content blocks. Text, thinking, hints, media and tools use separate block types. A reply accumulates multiple reasoning and acting rounds in one assistant message, found by reply ID and author even when later observations extend the transcript. The event representation serves incremental consumers, and `Msg.append_event` reduces those events into a transcript. The context model stores the summary and retained conversation, permission and tool context, tasks and extension state. The latter is a dictionary keyed by middleware convention. Its model validator migrates the old top-level reply fields. The service's transcript projection and the SDK's inference state have separate write paths and can carry different representations of the same turn. ### 2.2 Model and tool boundaries

Model cards describe capabilities, limits and parameter overrides. Formatters convert the shared messages into provider-specific records, including separate chat and multi-agent strategies where needed. `ChatModelBase` wraps one model's provider call, normalizes exceptions, bounds start-time retries, and wraps streams into incremental and complete `ChatResponse` values. Its accumulator keys blocks by ID and joins fragments once. Agent-level retries and fallback govern the awaited model call, with a distinct policy once it returns an iterator. The two retry counts are additional attempts. The agent layer defaults to zero additional attempts to limit multiplication with provider-level retries. Provider-aware structured generation can try strategies distinct from the SDK's temporary final-output tool. ### 2.3 Multi-agent composition and procedural control

- **GoalPipeline.** An executor submits a structured report. A verifier receives the original goal and report and produces pass, fail or impossible. Refusals feed back to the executor. Iteration and invalid-output counters live on the pipeline instance and survive an in-process human-interaction pause. No separate pipeline persistence contract appears in the constructor or stream API. Its reachable outcomes are expressed through participant events, loop completion and exceptions. - **TeamPipeline.** The leader sees an external `TeamAssign` tool. The pipeline captures those assignments, groups them by member, runs groups in parallel and calls a given member in assignment order. It feeds member results back as tool results in leader-call order. Parked member results route by reply ID. Leader and member state are separate. The member contexts can be cleared when the leader finishes. The assignment runner cancels and joins siblings after an infrastructure failure. ### 2.4 Context, memory, session runtime and realtime

Short-term memory is the typed context plus summary. The context compressor estimates input size from messages and tools, retains recent context, keeps an unfinished turn's required protocol blocks together, summarizes older material and can offload originals. It handles unsuccessful compression using the configured fallback and retains reply usage. Tool result truncation is a separate budget. Memory middleware extends this with filesystem-backed memory, retrieval-augmented hints and optional Mem0 and ReMe integrations. The long-term extensions use reply, prompt and reasoning hooks, so the core loop can continue to operate on ordinary messages and tools. In the service runtime, a normal input is enqueued into a session FIFO. A dispatcher listens for wakeup signals and drains shared triggers. One local run registry owns process task handles. The queue claims an item durably before removing its head, saves the input, and runs the agent under a session lease. `ChatService` loads the mutable record after lock acquisition and reconstructs agent, model, hooks, workspace and toolkit. It applies each event to a message projection, appends to replay storage, publishes live, and persists projected messages, agent state and a replay cursor in a checkpoint section. The stream consumer subscribes before replay and uses entry IDs to handle overlap. The shared bus offers both in-memory and Redis implementations. Durable session records live in Redis or an asynchronous SQL backend. The service's renewable Redis mutex provides serialization during healthy ownership and the in-memory bus coordinates callers within one process. ## 3. Governing invariants

| Invariant | Consequence |
| --- | --- |
| One foreground writer owns a session and its current reply context. | The reply ID, loop iteration, middleware and tool-call state all refer to a coherent run. The service lock and local registry establish this under normal operation. A direct caller must serialize use of a stateful agent. A renewable lease requires an explicit policy for ownership loss. |
| A tool-result block settles one call ID. | The next reasoning step can correlate both sides of the call in the inference transcript. Calls in ASKING or SUBMITTED can outlive the current generator and resume against saved state. A new iteration starts after the last unfinished call settles. |
| A streamed partial and a semantic result have separate roles. | Deltas allow progressive presentation. The assembled model output controls context writes and act/exit decisions. Retry and fallback must be explicit about whether any delta has reached the consumer. |
| A parked stream is a deliberate lifecycle outcome. | The direct agent stops streaming without a successful end event while waiting for outside input. The reply ID and unresolved calls remain in state. Teams and SOPs can route or persist these parked transitions. |
| A cancellation or close must end ownership or transfer it. | The owner must settle work it started, with interrupt records where the stream can still deliver them. An offloaded task needs a new owner before the original can release it. Generator closure and task cancellation arrive at different points. |
| The durable transcript and inference state need a common commit version. | Readers use the transcript plus replay cursor and the next turn loads agent state. They agree during normal commits under the checkpoint lock. A failed intermediate write, stale holder or cancellation requires recovery or an explicit failed checkpoint outcome. |

The design works because it demarcates decisions the model proposes from decisions the host executes. The host controls registration, state, permission/interaction, dispatch and finalization. Shared typed data carries identities across those transitions. The arrangement gives one core Agent room to support both normal chat and specialized loops through composition. Its main cost is that multiple adapters and middleware layers must uphold one lifetime and commit protocol. ## 5. Weaknesses and evidence status

| ID | Status | Effect |
| --- | --- | --- |
| F1 | Reproduced under injected lease-renewal loss | An older live worker can overwrite conversation state written by a newer worker after the old lease expires. |
| F2 | Reproduced under one write failure and repeated cancellation | A reply can be marked completed and saved while the next agent takes its context from an older snapshot. |
| F3 | Reproduced with default service offload | A tool can continue after foreground cancellation before it has a registered background owner. |
| F4 | Reproduced with explicit generator close | Closing an SDK reply stream can leave a provider iterator open or allow a tool worker to keep running. Direct toolkit close can raise a Python generator protocol error. |
| F5 | Reproduced with default Agent cancellation settings | GoalPipeline treats an interrupted participant as an output failure and starts more work. |
| F6 | Reproduced through the documented configuration | `stop_on_reject=True` does not stop inference after a human denies a tool call. |
| F7 | Reproduced with a mixed-capability model router | The primary model can cause an input image to be discarded before the selected model sees it. |
| F8 | Reproduced after a fault at the subscription boundary | The wakeup loop can stop indefinitely on a single-worker service even while fallback signals continue. |
| F9 | Reproduced contract limitation | Restarting a parked structured reply with a serialized schema loses Python-only validation. |

## 9. Post-mortem and prioritized improvements

The framework is carrying four useful pressures at once. Python users want one configurable Agent and simple coroutine tools. Provider adapters need different deltas, tool schemas and capability limits. Applications want a first response quickly and need to park or hand work off. The service needs restartable state and routing across worker processes. The core design handles local control flow well by making events and typed state the common exchange. Complexity accumulates at the seams between an event announcing a transition, the coroutine that still owns work and the store that makes the transition durable.

The failures are mostly interactions among valid features. A heartbeat can protect the lease entry while a stale holder still writes session state. A reply can emit a valid terminal record just before the state write fails. A developer can attach a legitimate queue-based offload middleware and introduce an extra task whose lifetime the outer cancellation path cannot see. Logical reply boundaries and iterator invocation boundaries differ during human interaction. The same distinction explains the Goal retry, structured schema roundtrip and memory write-back cases.

| Priority | Improvement | Verification target |
| --- | --- | --- |
| **P0** | Fence session commits and supervise lease loss. Give the protected writer a lease generation/version and require it in the storage commit. Watch the renew task and surface a stale-owner outcome when the lease cannot be re-established. | Repeat F1 with real Redis-compatible TTL expiry and transport failure. B's newer snapshot wins even if A resumes and tries to write. A's event stream has an attributable loss-of-ownership outcome. Release protects the current owner's key. |
| **P0** | Make the reply/state/cursor checkpoint a durable transition. Group transcript and state in one storage transaction where supported. Use a monotonic checkpoint plus reconciled publication where the bus and storage are separate. Protect the persistence task through repeated cancellation with a bounded join and clear failure reporting. | Repeat F2 while failing each write and while cancelling more than once. A new reader sees one committed version, or a visible incomplete state that recovery can reconcile. A completed event alone carries no promise beyond its defined commit boundary. |
| **P0** | Establish explicit lifetime ownership at every streaming and offload layer. A forwarding generator closes its owned child. A task owner cancels and joins untransferred work. Yield completion responses after successful stream progression and keep cleanup yield-free. | Test close, break with `aclosing`, task cancel and consumer exception across model, toolkit, Agent, middleware and pipelines. F3 only permits survival after an acknowledged transfer, with its task ID visible. F4 returns only after cleanup and never yields during `GeneratorExit`. |
| **P1** | Make reply identity and terminal states first-class inputs to orchestration policy. Validate recipient reply ID before applying all continuations and interrupts. Handle interruption before Goal retry logic. Either implement the documented rejection setting or remove it with a compatibility transition. | F5, F6 and F13 become explicit behavior tests. A delayed stop cannot close a later turn. Cancellation never starts a fresh verifier. A rejected tool follows the configured policy while retaining its result. |
| **P1** | Reconnect and drain wakeups under bounded supervision. Borrow the cancel or scheduler listener's retry pattern, and ensure recovery can reacquire an actual consumer. Clarify delivery guarantees and durable acknowledgement for result-bearing triggers. | After a real broker EOF or repeated transient failures, a single worker resumes consumption and drains existing work without restarting the application. Busy-session retries and durable FIFO recovery retain their existing ordering and side-effect protection. |
| **P2** | Tighten edge contracts. Select the model before lossy media adaptation. Make external batch acceptance atomic or return explicit accepted IDs with idempotent replay. Carry schema identity and version for registered Python validators. Carry a parked reply's write-back data until a completed terminal outcome. | F7, F9, F10 and F14 pass after a restart or multi-stage turn with a clear policy for unsupported or explicitly schema-only cases. |
| **P2** | Support Python 3.14's annotation metadata. Preserve unwrapped signatures, merge explicit hints deliberately and use forward-reference inspection when available. | F15 passes under 3.14 while the PEP 563, partial and injected-state fixtures continue to pass on 3.11. |
| **P2** | Improve runtime attribution and admission. Emit attempt IDs and selected model/phase on standard events, and explicitly document or reject overlapping direct replies. | Event-only telemetry attributes fallback and pre-output retry correctly. F11 receives a clear admission error before state mutation. Preserve optional tracing for attempt diagnostics. |

The shortest path is a regression matrix around ownership and commits, then refinements to routing and memory. Existing tests cover healthy controls for the major subsystems. Boundary tests can combine those paths and inject precise handoff failures. Recent changes in the pin such as callable-instance annotations can retain the current public schemas for ordinary extensions.
