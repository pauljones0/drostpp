## 2. Core architecture and end-to-end control/data flow

### Executable composition

The gateway binary links selected in-process driver factories. The server initializes authorization metadata, storage, extension registries, and compute capability negotiation before serving. The compute driver is a versioned gRPC contract even when the implementation is invoked in-process. It returns native resource observations and capabilities such as runtime identity binding, readiness ownership, and whether the gateway should manage running intent across restarts. The external-driver path adapts the same interface to a Unix socket. A managed subprocess has gateway shutdown ownership, while an operator-started socket endpoint has an independent lifecycle. ### Runtime control, updates, and recovery

The Linux runtime keeps the signal/reaper and workload launcher local to the boundary. The launcher assigns native enforcement before workload execution, including a dedicated launch thread for inherited syscall notification. The runtime retains descriptor/process ownership and stages network requests, while the supervisor evaluates ingress to its mediation surfaces and routes policy-governed egress. Polling supervisors retain a compatibility path. An admitted launch is distinct from an accepted runtime update and provider readiness has its own reporting surface. ## 3. Why the design works and its governing invariants

- **Identity has a lifetime.** Workspace/name resolves a stable logical sandbox ID. The runtime generation keys native boundary artifacts and is distinct from platform identity, ownership epoch and transport connection. Late events and completion replies can arrive in any order, so each effect must check the identities it was admitted under. Provisioning operation IDs are kept after settlement to prevent a late callback from adopting a later settled attempt. API-level request IDs cover caller admission and do different work from these runtime fences. [Start request](repos/NVIDIA__OpenShell/proto/compute_driver.proto:539) [Operation equality](repos/NVIDIA__OpenShell/crates/openshell-server/src/compute/provisioning_operation.rs:23) [Main-process exit fence](repos/NVIDIA__OpenShell/crates/openshell-server/src/compute/mod.rs:6119) [Client request ID](repos/NVIDIA__OpenShell/proto/openshell.proto:1363)
- **CAS is the correctness fence across replicas.** The lifecycle gate is per stable ID and local to a gateway replica. Ordinary driver observations bypass it, while ambiguous starting and terminal snapshots reacquire it and reread both stores. Reads are repeated before CAS and desired state is checked again on completion. The Postgres mutation-lock hierarchy orders global, workspace and sandbox keys, reserves a separate pool for advisory locks, and carries legacy keys for rolling upgrade compatibility. The reconciler lease reduces redundant watch work. It can expire while a previous worker is still alive, which is why the independent operation and version fences matter. [Lifecycle gate](repos/NVIDIA__OpenShell/crates/openshell-server/src/compute/mod.rs:256) [Ambiguous snapshots](repos/NVIDIA__OpenShell/crates/openshell-server/src/compute/mod.rs:5623) [Mutation lock order and capacity](repos/NVIDIA__OpenShell/crates/openshell-server/src/persistence/mutation_lock.rs:4) [Lease scope](repos/NVIDIA__OpenShell/crates/openshell-server/src/compute/lease.rs:4)
- **Deadlines and readiness survive replay.** Image preparation has an absolute ceiling, with default 1,800 seconds. The first authenticated admission report opens a separate repair window, default 300 seconds. The attempt and configuration-change identity determine whether changes or the first rejection can extend it. Duplicate/reconnected reports preserve the original timing. Expiration is a durable phase decision before any cleanup I/O. A STOP issued before a late CREATE settles cannot prove reclamation even when it saw absence. - **One live boundary owner can apply effects.** The pool stores assignment ownership at member/process/term granularity. A membership stream includes an increasing connection epoch and acknowledges revisions sent on that stream. Recovery keeps or moves existing desired routes from durable data, and absence from a member's assignment means relinquish unless explicitly told to stop. At the boundary, confirmation promotes a later authenticated term and excludes old owner effects. Loss of the active connection freezes the workload pending recovery. The recovery ID prevents a timer from killing a workload on a newer connection. - **Ownership extends beyond successful requests.** Per-ID guards and durable operation records preserve causality when an RPC caller leaves. Delete, stop/start transitions, long-running provisioning and hosted-instance removal carry explicit owners. ## 5. Weaknesses and evidence status

### Persisted ambiguity keeps a sandbox unavailable after a hard gateway loss

**High, source-confirmed contract limitation.** Create/Start commits a local durable claim before the gateway worker dispatches I/O. A crash can happen before dispatch, during the call, or after the remote operation returns while settlement is still only in the worker's memory. The new process sees the same durable pending marker in each case. Recovery deliberately retains those records, and timeout reclamation can stop visible compute while still refusing to declare cleanup complete. Ordinary start and delete remain fenced. The matching pending *image update* is a separate case with a resumable intent and driver operation ID. The Create/Start wire lacks the equivalent queryable durable operation receipt. A long lease or an observed absent resource alone cannot establish that no create is still in flight. This is a liveness gap arising from the operation contract, with a sound reason for conserving the interlock. [Documented hard-crash limit](repos/NVIDIA__OpenShell/docs/how-it-works/sandboxes/overview.mdx:1189) [Claim](repos/NVIDIA__OpenShell/crates/openshell-server/src/compute/provisioning_operation.rs:194) [Settlement and hard-crash comment](repos/NVIDIA__OpenShell/crates/openshell-server/src/compute/provisioning_operation.rs:254) [Startup recovery](repos/NVIDIA__OpenShell/crates/openshell-server/src/compute/mod.rs:4546) [Interlock exception](repos/NVIDIA__OpenShell/crates/openshell-server/src/compute/image_update.rs:507) [Wire comparison](repos/NVIDIA__OpenShell/proto/compute_driver.proto:510)

The API request ID ledger has an independent availability cost. Once a request ID has consumed a per-caller slot, an error or panic during execution leaves that admission unresolved because the status cannot establish how far the operation got. A sweeper reclaims expired completed admissions. Accumulated unresolved admissions can eventually deny new request-ID mutations from that identity across replicas. ### Kubernetes delete conflates a version conflict with absence

**High, source-derived under a same-object update.** The driver applies both UID and Kubernetes resource-version preconditions. Its delete result maps HTTP 409 and 404 to the same `deleted=false` outcome without rereading the resource. A concurrent controller update can change resource version while retaining the UID, leaving the object present after the precondition fails. The gRPC bridge preserves the boolean and the gateway removes the Deleting row when it is false. Both watch and periodic reconciliation ignore snapshots for IDs absent from the store, while Kubernetes resource recovery keys off the CR list. The call chain can therefore acknowledge deletion of a resource that continues to exist. A reduced Rust fixture with the exact error-mapping and gateway settlement branches confirmed that injected 409 and 404 both report Completed and remove the local row without checking native absence. A simulated native acceptance checked absence and returned Accepted when the resource remained. Injected 500 and timeout took the failed-delete recovery path. The current compute protocol supplies only a deletion boolean. The gateway implicitly relies on false meaning verified absence, a stronger condition than the wire comment's definition. The same Kubernetes driver already distinguishes resource-version conflicts elsewhere. The platform race is conditional. No cluster ran here. ### Whole-fleet scans and shutdown waits have weak latency bounds

**Medium, source-derived under slow dependencies.** Restart decodes all paged sandbox rows on each pass and awaits applicable Stop/Start work one sandbox at a time. The nominal 500 ms is a sleep after a pass, so a held gate or stuck driver can delay later restart intents. Provisioning has a better split, with a shared 500 ms budget for local lock acquisition and detached cleanup. Its scan still collects all sandbox rows, and a decode, configuration-refresh or persistence error can abort the pass before it reaches later rows. Shutdown bounds concurrency for local stops but awaits them before signalling the managed child and draining owner sessions. No single gateway shutdown budget covers those awaits. ## 9. Post-mortem and highest-leverage improvements

The recurring pressure is that OpenShell has to join state machines it cannot atomically commit together. A gateway row, Docker or Kubernetes mutation, supervisor session, terminal attachment and process exit may each become observable at a different time. The design answers this with durable intent, per-layer identity and compensating reconciliation. This works when each boundary can return authoritative evidence for the same operation. The largest residual failure follows when the gateway persists that a Create/Start may happen, loses its worker, and cannot ask the driver what happened. A similar mismatch occurs when Kubernetes's version fence provides correct evidence that a mutation failed, but a narrower boolean loses that information. These are distinct versions of the same design pressure. The transport cannot infer a stronger lifecycle fact than its driver reported. A likely incident sequence is a gateway restart while an asynchronous platform launch is settling.
