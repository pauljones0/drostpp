### Agent from caller to durable result

1. `Agent.run` and `Agent.arun` delegate to dispatchers. An explicit `stream=True` selects an iterator or async iterator. The ordinary async call returns a coroutine. Dispatch validates the input against `input_schema`, normalizes hooks, resolves or assigns run and session IDs, initializes the Agent and manager dependencies, and builds `RunInput` and `RunOutput`. An omitted session ID is sticky on a reused Agent instance. Sync run rejects async DB or media configuration early. The default model is OpenAI Responses when the caller supplies no model. [Public async signature](repos/agno-agi__agno/libs/agno/agno/agent/agent.py:1576), [Sync dispatch](repos/agno-agi__agno/libs/agno/agno/agent/_run.py:1322), [Async dispatch](repos/agno-agi__agno/libs/agno/agno/agent/_run.py:2712), [Session identity](repos/agno-agi__agno/libs/agno/agno/agent/_session.py:46), [Default model](repos/agno-agi__agno/libs/agno/agno/agent/_init.py:89).
2. Run options choose stream/event controls, context flags, dependencies, metadata and schema. The general precedence is explicit calls over defaults, with the existing context used for inherited dependencies, filters and metadata unless the caller overrides them. Component, session and caller metadata merge in that order when the session layer is available at resolution. A schema is freshly assigned for the executor because a parent context may be reused across heterogeneous steps. The lifecycle reads or creates the session, merges persisted and caller state, adds transient current IDs, resolves dependency callables, and invokes pre-hooks before prompt assembly. [Options](repos/agno-agi__agno/libs/agno/agno/agent/_run_options.py:18), [Option resolution](repos/agno-agi__agno/libs/agno/agno/agent/_run_options.py:79), [State merge](repos/agno-agi__agno/libs/agno/agno/agent/_storage.py:569), [Run ingress](repos/agno-agi__agno/libs/agno/agno/agent/_run.py:418).
3. Tool resolution combines component functions, toolkits, provider-native tool descriptors, framework helpers and optional per-run tools. The framework derives schemas from Python callables and assigns context, ownership, and runtime injection separately. Prompt assembly adds system instructions, optional session state, dependencies, memories, summaries and filtered history, then produces the message list for the model. History messages are copied for model-facing annotation, and tool-call/result pairs are reconciled before replay. Compaction can present a stored summary plus a fresh, pair-safe tail. Its history view preserves the full transcript in session storage. [Tools](repos/agno-agi__agno/libs/agno/agno/agent/_tools.py:205), [Schema derivation](repos/agno-agi__agno/libs/agno/agno/tools/function.py:586), [History](repos/agno-agi__agno/libs/agno/agno/session/agent.py:141), [Prompt construction](repos/agno-agi__agno/libs/agno/agno/agent/_messages.py:1926), [Compaction view](repos/agno-agi__agno/libs/agno/agno/compaction/_view.py:67).
4. A provider adapter implements `invoke`, `ainvoke`, and their streaming counterparts, plus provider response and delta parsing. The base `Model` owns the portable loop. It formats tool definitions, invokes the provider, appends the assistant message, resolves function calls by name, correlates results by call ID, and appends tool messages before a new model request. A provider-native tool descriptor contributes a schema. A framework `Function` contributes a local callable. Async tool execution uses producer tasks and a queue for generator/tool events, with the batch gathered before the next provider leg. The synchronous batch walks calls in sequence. Completion, a stop-after-tool result or a pending requirement bounds a normal loop, with optional local tool-call limits. [Provider contract](repos/agno-agi__agno/libs/agno/agno/models/base.py:552), [Turn loop](repos/agno-agi__agno/libs/agno/agno/models/base.py:651), [Sync tool batch](repos/agno-agi__agno/libs/agno/agno/models/base.py:2418), [Async tool batch](repos/agno-agi__agno/libs/agno/agno/models/base.py:2630), [Results appended to the transcript](repos/agno-agi__agno/libs/agno/agno/models/base.py:3169).
5. The Agent can run an auxiliary reasoning model, additional output model, parser model or follow-up model, and merge attribution into run metrics. Pydantic output schemas can be passed to a native provider parser, translated to provider JSON schema, or approximated with JSON mode and local parsing. An output model can produce a final answer from earlier outputs, while a parser model attempts to structure an existing answer. Local conversion stores a structured value and its `content_type` on success. Conversion failure can leave text with a successful run status. A tool pause diverts into a separate save-and-return path. On success the runtime invokes post-hooks, joins memory and learning work, can create a session summary, sets the run status, writes the session and run, and releases tracked tools and cancellation state. [Response formatting and conversion](repos/agno-agi__agno/libs/agno/agno/agent/_response.py:845), [Parser model](repos/agno-agi__agno/libs/agno/agno/agent/_response.py:349), [Agent run finalization](repos/agno-agi__agno/libs/agno/agno/agent/_run.py:542), [Paused save](repos/agno-agi__agno/libs/agno/agno/agent/_run.py:237), [Persistence](repos/agno-agi__agno/libs/agno/agno/agent/_run.py:6053).

### Team as a leader model with member runs

A Team constructs a leader prompt and exposes delegation as local functions to the same model loop. `coordinate` assigns tasks and synthesizes replies. `route` forwards a selected member's answer. `broadcast` forwards an input to all members, sequentially in sync execution and via concurrent work in async execution. `tasks` adds a durable task list and an outer iteration loop. The task list stores statuses, notes, blocking dependencies and outputs in session state. The outer loop can stop on terminal tasks, a direct answer without task work, a pause, or the iteration cap. The model makes planning and routing decisions, while IDs, task transitions and execution are in framework code. [Mode contract](repos/agno-agi__agno/libs/agno/agno/team/mode.py:6), [Task state](repos/agno-agi__agno/libs/agno/agno/team/task.py:79), [Task execution loop](repos/agno-agi__agno/libs/agno/agno/team/_run.py:372), [Leader tools](repos/agno-agi__agno/libs/agno/agno/team/_default_tools.py:1517).

The delegation closure resolves the member and prepares its task, optional Team/member history, context and media. It provides a member run ID and registers it under the leader for cancellation. Local children share the parent session ID, with filtering by component and parent lineage when reading history. Member completion yields output for the leader's next model leg and attaches the child run to the Team's response and session. For a paused member, the Team carries the requirement together with its member ID and run ID. Continuation resolves the owning executor and routes through subteams where necessary. This preserves the member transcript and allows resume from a stored graph. Direct reply and model inheritance configure shared component objects in some paths, a consequential ownership choice for reuse. [Member setup](repos/agno-agi__agno/libs/agno/agno/team/_default_tools.py:505), [Delegation execution](repos/agno-agi__agno/libs/agno/agno/team/_default_tools.py:713), [Async broadcast](repos/agno-agi__agno/libs/agno/agno/team/_default_tools.py:1237), [Pause propagation](repos/agno-agi__agno/libs/agno/agno/team/_tools.py:656), [Continuation routing](repos/agno-agi__agno/libs/agno/agno/team/_run.py:6297), [Async member continuation](repos/agno-agi__agno/libs/agno/agno/team/_run.py:6643).

### Workflow as an interpreter for a step tree

A Workflow can invoke a Python callable or prepare a tree of `Step`, `Steps`, `Condition`, `Router`, `Loop` and `Parallel` nodes. The sequential driver builds a `StepInput` from original input, prior outputs, additional data and accumulated media. A Step invokes a Python callback, an Agent, a Team, or a nested Workflow. It normalizes the result to `StepOutput`, with a success marker, content, optional metrics and media, and nested results. The next step can use the previous content or fetch the output of a named step. Step configuration governs retry, error, skip, or pause and review behavior. A Workflow can also attach a WorkflowAgent to choose execution or reply directly. [Workflow preparation](repos/agno-agi__agno/libs/agno/agno/workflow/workflow.py:11062), [Step input](repos/agno-agi__agno/libs/agno/agno/workflow/types.py:300), [Step output](repos/agno-agi__agno/libs/agno/agno/workflow/types.py:550), [Step dispatch](repos/agno-agi__agno/libs/agno/agno/workflow/step.py:1151), [Workflow execution](repos/agno-agi__agno/libs/agno/agno/workflow/workflow.py:2943), [WorkflowAgent dispatch](repos/agno-agi__agno/libs/agno/agno/workflow/workflow.py:11005).

Conditions and routers use Python callbacks and optionally CEL expressions. Loops and sequence containers build nested result trees. A parallel container fans out to a thread pool for sync work or tasks for async work, then aggregates child values, media, success and stop signals. The driver can descend to the last leaf for the final Workflow content. Event paths can forward step progress and nested executor events tagged with workflow and step context. Human review can pause before a step, after output, or on failure. Executor pauses carry the executor run ID and its requirements. The continuation driver rebuilds its progress at the paused step so that completed earlier steps can be retained. The parallel executor explicitly rejects a paused embedded Agent or Team in its aggregate. [Async Workflow loop and events](repos/agno-agi__agno/libs/agno/agno/workflow/workflow.py:4448), [Parallel aggregation and pause boundary](repos/agno-agi__agno/libs/agno/agno/workflow/parallel.py:184), [Review configuration](repos/agno-agi__agno/libs/agno/agno/workflow/types.py:65), [Executor pause](repos/agno-agi__agno/libs/agno/agno/workflow/utils/hitl.py:594), [Continuation dispatch](repos/agno-agi__agno/libs/agno/agno/workflow/workflow.py:6596), [Step child run recording](repos/agno-agi__agno/libs/agno/agno/workflow/step.py:2667).

### State, persistence, reasoning and events

Session state is mutable application data. Session history is a view over run transcript records. User memory is a separate, user-keyed store. Agentic memory tools let the model decide when to read or change memories. Automatic extraction uses a manager and runs concurrently with the main turn when enabled and suitable input exists. Session summaries update a digest of the session. Compaction manages a bounded model-facing history view, with an optional archive and a shrink check before a context-overflow retry. It can use a local tokenizer, a character estimate, or an explicitly configured token counter. These mechanisms have separate storage and timing semantics. The current turn assembles context before automatic extraction starts. The successful terminal path joins extraction before saving. [Memory configuration](repos/agno-agi__agno/libs/agno/agno/agent/_init.py:104), [Background memory extraction](repos/agno-agi__agno/libs/agno/agno/agent/_managers.py:139), [Memory manager](repos/agno-agi__agno/libs/agno/agno/memory/manager.py:377), [Summary manager](repos/agno-agi__agno/libs/agno/agno/session/summary.py:242), [Compaction replay and retry](repos/agno-agi__agno/libs/agno/agno/agent/_messages.py:655).

On the normalized persistence path the session row carries state, summary, metadata and component identity. Individual run rows carry serialized run envelopes and an ordering index. SQLite allocates the index within the insert and preserves the existing index on updates. The read path can reconcile legacy inline run blobs and normalized rows by run identity. The parent component owns session writes for native nested executors and persists child records along with its own. Storage can copy and scrub messages, history, tool results and media, or replace large results with references. This allows the live output to retain its full result while the persisted representation follows storage policy. [SQLite run upsert](repos/agno-agi__agno/libs/agno/agno/db/sqlite/sqlite.py:1283), [Legacy run reconciliation](repos/agno-agi__agno/libs/agno/agno/db/utils.py:448), [Agent session ownership](repos/agno-agi__agno/libs/agno/agno/agent/_session.py:293), [Team child persistence](repos/agno-agi__agno/libs/agno/agno/team/_run.py:4583), [Workflow session and run persistence](repos/agno-agi__agno/libs/agno/agno/workflow/workflow.py:2337).

Reasoning has three distinct paths. A primary adapter can return native reasoning fields and deltas in its normalized response. An optional separate `reasoning_model` passes through `ReasoningManager` for recognized native reasoning models, yielding generic events that Agent and Team translate and use for run metadata and prompt context. Recognition is cached per manager and the asynchronous detection path can offload a synchronous lookup. A non-native auxiliary model takes the warning/continue path. `ReasoningTools` provides explicit think/analyze functions in the regular tool loop. Reasoning state and model-attributed usage are available to the runtime independently of whether the caller asks for intermediate events. [Reasoning entry](repos/agno-agi__agno/libs/agno/agno/agent/_response.py:252), [Model recognition](repos/agno-agi__agno/libs/agno/agno/reasoning/manager.py:113), [Reasoning dispatch](repos/agno-agi__agno/libs/agno/agno/reasoning/manager.py:859), [Event mapping](repos/agno-agi__agno/libs/agno/agno/agent/_response.py:168), [Reasoning tools](repos/agno-agi__agno/libs/agno/agno/tools/reasoning.py:50).

There are three event representations. Provider adapters emit normalized model deltas. The component drives typed `RunOutputEvent`, `TeamRunOutputEvent`, or `WorkflowRunOutputEvent` objects, including intermediate content, model/step phases, tools, and lifecycle. Persisted or detached streams can give events a monotonic index for replay. The background path accepts a pending run, gates execution using a per-loop semaphore, publishes to the event stream and attached client independently, and writes status for polling. The shared event stream can use local memory or Redis. Memory replay subscribes before replay and deduplicates by index. ### Cancellation, errors and execution ownership

The default cancellation manager maintains expiring run IDs and intent, including requests received before the run registers. A running component observes the intent at cooperative checkpoints around model, tool, event and step work. It can record a cancellation stage along with partial output. Team records a separate member relation. Its cancellation path requests cancellation on the linked children and waits for tracked async delegation tasks under a bounded drain so their partial child results can be attached before persistence. A Python task cancellation or generator close can arrive directly at the runner and takes a different path from a cancellation intent observed at a checkpoint. Foreground paths release toolkit connections and run tracking in cleanup. The detached stream's consumer close detaches the queue and lets the background execution retain ownership. [Intent and return contract](repos/agno-agi__agno/libs/agno/agno/run/cancellation_management/in_memory_cancellation_manager.py:83), [Cancellation stages](repos/agno-agi__agno/libs/agno/agno/run/base.py:395), [Team cancel and drain](repos/agno-agi__agno/libs/agno/agno/team/_run.py:4011), [Bounded drain](repos/agno-agi__agno/libs/agno/agno/run/cancel.py:167), [Agent cleanup](repos/agno-agi__agno/libs/agno/agno/agent/_run.py:2688), [Background consumer detach](repos/agno-agi__agno/libs/agno/agno/run/background.py:174).

Errors take different forms at different layers. Provider adapter errors carry a status and are classified before model-call retries. A local tool failure can become a tool result the model sees, which preserves its option to recover in the same run. Workflow can turn a step failure into review or a terminal Workflow error according to the step's policy. A workflow can also retain partial step progress. For durable execution, lease monitoring and attempt-fenced writes give the worker separate authority over status and prevent a stale attempt from claiming a later job's outcome. The run status, step success and a tool-level error answer different questions about the same execution. [Provider error classification](repos/agno-agi__agno/libs/agno/agno/models/base.py:199), [Tool execution error handling](repos/agno-agi__agno/libs/agno/agno/models/base.py:2194), [Step failure to review](repos/agno-agi__agno/libs/agno/agno/workflow/step.py:929), [Workflow terminal error](repos/agno-agi__agno/libs/agno/agno/workflow/workflow.py:4785), [Worker lease monitor](repos/agno-agi__agno/libs/agno/agno/os/job_queue.py:1051), [Worker fenced persistence](repos/agno-agi__agno/libs/agno/agno/run/status_persist.py:254).

These invariants let deterministic Workflow logic and model-directed Agent/Team logic compose. Python functions return plain values or structured models and the same execution envelope carries intermediate status, state, child ownership and errors to the caller. Durable progress is conditional on a configured backend, retained inputs/results and the selected runner's lifecycle. The existence of a checkpoint or event interface alone does not supply transactional or exactly-once execution.

## 5. Weaknesses and their evidence

### Reproduced defects and inconsistencies

The priority levels below rank impact within this review. High means a normal lifecycle action can lose or contradict durable output, duplicate output, or allow work to continue after the parent ends. Medium means the observed failure requires a particular configuration, ownership pattern, or secondary interface.

#### F1. Closing a foreground stream after its terminal event breaks durable lifecycle state — high

Agent and Team persist completion or pause before delivery, then yield while still inside a handler that treats `GeneratorExit` as cancellation. Closing with `aclose()` after that event schedules another write. The Agent/Team run changed from `COMPLETED` or `PAUSED` to `CANCELLED` in all three tested adapters. Paused requirements fell from one to zero. With event storage enabled, the new record carried a cancellation and an additional completion marker. Synchronous Agent and Team controls kept their original completion or pause. Async drains kept it as well. [Agent completion yield](repos/agno-agi__agno/libs/agno/agno/agent/_run.py:2528), [Agent close handling](repos/agno-agi__agno/libs/agno/agno/agent/_run.py:2612), [Agent paused save and yield](repos/agno-agi__agno/libs/agno/agno/agent/_run.py:326), [Team close handling](repos/agno-agi__agno/libs/agno/agno/team/_run.py:4052), [Agent cancellation mutation](repos/agno-agi__agno/libs/agno/agno/agent/_run.py:5936).

Workflow has a second form of the defect. On the ordinary step-list path it yields `WorkflowCompleted` before it saves the run or clears tracking. Closing on that event produced no persisted run across sync and async entry points. Async `StepPaused` likewise arrives before its save. Closing there entered the cancellation handler and wrote `CANCELLED` with the unresolved step requirement still attached. Sync close at `StepPaused` left no row. Fully exhausting the very same streams persisted the expected states. A caller that sees a marker documented by the runtime as a stream end can reasonably stop consuming there. The difference between a pause, successful completion and absence of a record is operationally material. [Sync Workflow completion](repos/agno-agi__agno/libs/agno/agno/workflow/workflow.py:3838), [Async Workflow pause](repos/agno-agi__agno/libs/agno/agno/workflow/workflow.py:4465), [Async Workflow completion](repos/agno-agi__agno/libs/agno/agno/workflow/workflow.py:4895), [Terminal event definitions](repos/agno-agi__agno/libs/agno/agno/run/background.py:38).

Composition can trigger the defect even when the public caller drains the outer stream. `Step.aexecute_stream` requests `yield_run_output=True` from the Agent/Team, then breaks as soon as the object arrives. It attaches that same object to the parent run. The child generator can finalize through its cancellation branch and mutate the retained child output. The fully drained composed async Workflow completed with the intended result and stored a `CANCELLED` Team executor despite emitting `TeamRunCompleted`. Its member stayed completed. Sync and async non-streamed controls and the sync streamed control stored a completed Team. [Inner capture and break](repos/agno-agi__agno/libs/agno/agno/workflow/step.py:2413), [Child object attachment](repos/agno-agi__agno/libs/agno/agno/workflow/step.py:2667), [Team terminal yield](repos/agno-agi__agno/libs/agno/agno/team/_run.py:3993), [Composed status records]($HOME/agent-work/scratch/agno-runtime-20261119/logs/probe-composition.txt:1).

#### F2. A partial model stream and its retry are concatenated — high

With one provider-level retry and zero component retries, a typed transient 503 after the first `"blue "` delta triggered a fresh invocation. It streamed `"blue "` and `"sky"` again. The observable output was three chunks, and both the final content and persisted assistant message were `"blue blue sky"` with status `COMPLETED`. Both sync and async reproduced it. With a first-attempt failure before any delta the same retry correctly yielded `"blue sky"`. With retry disabled, a midstream fault yielded partial content followed by `RunError`. The retry wrapper forwards deltas before knowing the invocation will succeed, then re-enters the same assembly accumulator. #### F4. Parallel Workflow results depend on streaming and branch completion order — medium

### Design tradeoffs, source-supported risks, and open questions

- **Foreground completion acknowledges computation separately from storage success.** A SQLite trigger rejected the run insert after successful computation. Across Agent, Team and Workflow, sync and async, streamed and non-streamed, all 12 callers received the completed status or event. An independent read found the new session-state value and no run record. Storage logged the error. The next successful call wrote a new run and left the gap. This reproduces the best-effort persistence contract of the tested foreground paths. It creates an ambiguous success for applications that equate completion with saved history. [Agent normalized save](repos/agno-agi__agno/libs/agno/agno/agent/_storage.py:474), [Team normalized save](repos/agno-agi__agno/libs/agno/agno/team/_session.py:474), [Workflow normalized save](repos/agno-agi__agno/libs/agno/agno/workflow/workflow.py:2181), [Fenced worker outcomes](repos/agno-agi__agno/libs/agno/agno/run/status_persist.py:23), [Persistence fault matrix]($HOME/agent-work/scratch/agno-runtime-20261119/logs/probe-persistence-fault.txt:1).
- **Whole-run and provider attempts have different replay implications.** A provider retry acts inside a model leg. An Agent retry can re-enter the run through hooks and the model/tool loop. Context-overflow recovery can mutate a reduced prompt view and retry. Checkpoints preserve progress, while arbitrary Python tool effects require their own idempotency or an externally managed transaction. Tool-call count limits local execution and cannot stand in for model-request or elapsed-time budgets. [Agent whole-run retry](repos/agno-agi__agno/libs/agno/agno/agent/_run.py:424), [Agent retry exception branch](repos/agno-agi__agno/libs/agno/agno/agent/_run.py:735), [Provider fallback](repos/agno-agi__agno/libs/agno/agno/models/fallback.py:203), [Tool limit](repos/agno-agi__agno/libs/agno/agno/models/base.py:2433).
- **Parallel context is partly shared.** Parallel copies the context envelope to isolate the output schema, while the normal Workflow path shares its state dictionary. The repository tests specify this. It is useful for cooperating steps with disjoint updates, and provides no isolation for read-modify-write operations across async awaits or threads. Queue session serialization addresses separate runs and does not change branch aliasing. [Parallel scope](repos/agno-agi__agno/libs/agno/agno/workflow/parallel.py:334), [Repository test](repos/agno-agi__agno/libs/agno/tests/unit/workflow/test_parallel_run_context_isolation.py:77).
- **Async entry points still depend on the resource type.** An async run with a synchronous adapter can perform synchronous database I/O in the event-loop thread. Synchronous callbacks and already-running thread-pool tasks have limits on interruption. Agno pools HTTP clients and lock-protects lazy creation. The default async client is process-global and unkeyed by event loop. Integration fixtures reset it explicitly between loops. Cross-loop transport reuse and cancellation latency are source-supported risks here. The review did not exercise live connections. [Sync DB branch](repos/agno-agi__agno/libs/agno/agno/agent/_session.py:262), [Memory future cancellation](repos/agno-agi__agno/libs/agno/agno/agent/_managers.py:180), [Shared async HTTP client](repos/agno-agi__agno/libs/agno/agno/utils/http.py:57), [Loop fixture](repos/agno-agi__agno/libs/agno/tests/integration/conftest.py:24).
- **Structured output is a value shape that can degrade gracefully.** A valid reply became a live Pydantic `Label` and a persisted dict in Agent and Team. A syntactically valid reply with the required field omitted was logged and returned as text with `COMPLETED`. This matches the local conversion code. Applications that require validation for success must inspect the type, use an output gate, or select an appropriate provider path. The review treats this as a contract tradeoff. [Agent conversion](repos/agno-agi__agno/libs/agno/agno/agent/_response.py:904), [Team conversion](repos/agno-agi__agno/libs/agno/agno/team/_response.py:1671), [Structured-output control]($HOME/agent-work/scratch/agno-runtime-20261119/logs/probe-structured.txt:1).
- **Background capacity couples producer speed and backlog.** The default per-loop limit of 32 bounds active detached execution. Admission and the per-consumer `asyncio.Queue` remain unbounded in the in-process path, and queued cancellation polls a backend per pending run. The durable worker path has different admission controls. A slow consumer or a large burst deserves a specific hot-path characterization before sizing a deployment. [Execution cap and admission](repos/agno-agi__agno/libs/agno/agno/run/concurrency.py:1), [Pending cancellation polling](repos/agno-agi__agno/libs/agno/agno/run/concurrency.py:97), [Attached stream queue](repos/agno-agi__agno/libs/agno/agno/run/background.py:121).
- **Unresolved scope.** Distributed storage/event/cancellation parity under real inter-process timeouts, long-running provider streams, the behavior of third-party instrumentation under actual model calls, and saturation limits were outside the measured environment. Existing SQL and Redis code provides contracts and test targets. The local results support claims about SQLite, in-memory queues and process-local flow. [Redis event stream](repos/agno-agi__agno/libs/agno/agno/os/event_streams/redis.py:93), [Redis cancellation manager](repos/agno-agi__agno/libs/agno/agno/run/cancellation_management/redis_cancellation_manager.py:32), [Queue worker](repos/agno-agi__agno/libs/agno/agno/os/job_queue.py:635).

## 9. Post-mortem and prioritized improvements

Agno has to expose incremental model output, provide synchronous and asynchronous entry points, normalize providers with different tool and structured-output capabilities, and preserve the meaning of saved runs across storage adapters and schema versions. It also lets a Workflow compose editable Python steps with nested components whose progress may outlive a model call or a process. The strongest solutions encode a stable contract once and preserve it at each boundary. Normalized messages, typed requirements, ordered run records and queue attempt fencing are examples. The observed failures cluster where equivalent lifecycle decisions are made in separate implementations, where a live object doubles as a durable result, or where a child can outlive the code that owns it. [Message representation](repos/agno-agi__agno/libs/agno/agno/models/message.py:56), [Requirement representation](repos/agno-agi__agno/libs/agno/agno/run/requirement.py:1), [Normalized run upsert](repos/agno-agi__agno/libs/agno/agno/db/sqlite/sqlite.py:1283), [Worker transition outcomes](repos/agno-agi__agno/libs/agno/agno/run/status_persist.py:23).

| Priority | Improvement | Acceptance criterion |
| --- | --- | --- |
| P0 | Centralize run settlement. Make a successful, paused, failed or cancelled transition idempotent for the same run or attempt. Resolve the persistence outcome before delivering the foreground terminal event. Close model and child generators and release their resources before handing an immutable terminal snapshot to the caller. Preserve existing queue fencing and expose a storage error where durability is part of the call contract. | Closing at any terminal marker or final output leaves the same durable status, requirements and final event as draining. Pause is resumable. An explicit cancellation before settlement remains distinguishable from closure after settlement. Exercise nested and standalone execution with each supported local storage mode. |
| P0 | Give async Workflow fan-out structured ownership. Put spawned tasks under a scope that cancels and joins them on early closure and errors. Keep live event delivery in arrival order and collect final outputs by branch slot. Document interruption limits for sync Python callables. | Cancelling a foreground async Workflow prevents still-suspended child branches from taking further steps after cancellation is acknowledged. Reversing completion order or toggling streaming produces the same stored output tree and final content. |
| P0 | Carry a typed pause route from the exact executor invocation that paused. Include the step identity or path, executor kind, executor instance ID, executor run ID and member route. Treat optional retained member results as display and audit data. Validate route identity and expected output kind before handing control to a continuation method. | A Team member requiring confirmation pauses and resumes the same Workflow after reload with retained responses enabled or disabled. The member tool and later steps each execute once. Ancestor and earlier step records do not change the chosen route. |
| P1 | Define the model-attempt boundary. Keep partial message and tool-fragment assembly scoped to the attempt. Give existing streams a clear behavior after the first externally visible delta, such as surfacing an interrupted response and ending the attempt. A replay-capable protocol would also need explicit replacement events, stable attempt identity and documented consumer behavior. Expose a separate replay policy for whole-run retries with effects. | A transient failure before the first emitted delta can retry, and a failure after it can neither create a duplicate persisted message nor join tool fragments from two attempts. A whole-run replay after an effect is visible to the application or can be avoided through a supported policy. |
| P1 | Make direct session concurrency explicit. Provide a per-session sequencing option or optimistic versioning with a defined merge or conflict outcome. Keep ordered insert and final state update in a documented consistency boundary for each adapter. Report session and run persistence outcomes distinctly where transactional pairing is unavailable. | Two overlapping runs with disjoint changes either persist both or report a clear conflict. Retrying a conflict has defined limits around tool effects. Tests verify the run history and state snapshot separately on legacy and normalized storage. |
| P2 | Give resource and observation contracts an owner. Use a refcounted lease, per-run instance or explicit caller management for live toolkits. Bind cached async clients to an event-loop lifetime. Resolve stored metadata after an awaited session read. Track exporter tasks with a separate awaitable drain and bounded shutdown behavior. | One run can finish while another still uses its lease. A second event loop receives its own owned client. All run variants apply the same metadata precedence. Trace drain completion corresponds to a durable write or a reported failure. |

The practical regression suite is a credential-free contract matrix around the existing extension seams. Start with initial and continued runs, Agent and Team nested in Steps, four execution modes, close before and after settlement, and in-memory plus SQLite adapters. Add per-attempt model faults and a gated parallel branch, then assert both public events and fresh durable reads. Existing reusable scripted models and local SQLite coverage make this achievable without external service integration. The matrix has more leverage than more isolated assertions that a particular helper was invoked. Keep provider wire-format testing separately scoped to mocked adapters.
