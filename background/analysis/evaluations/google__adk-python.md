**Assessment.** ADK has a coherent design for composing asynchronous agents, tools, and typed workflow steps. A small set of durable identifiers connects user inputs, execution paths, function calls, interruption responses, and conversation views. Its strongest implementation work is in lifecycle cleanup, branch-aware history construction, and replay of completed work. Its main liability is the number of places that assign meaning to the same event. The current run can consume a node result from its Context while a later run recovers the result from a plugin-processed Session. The implementation also ships graph, legacy agent-tree, and live paths that share contracts unevenly. The archive supports substantial local behavior coverage, several known replay and persistence deficits, and a specific node-path resume routing bug at the user-message callback boundary. ## 2. Architecture and end-to-end control and data flow

### 2.1 Entry points and execution ownership

`App` holds the app name, root definition, plugins, and optional context-cache, compaction and resumability settings. `Runner` attaches concrete services and builds a plugin manager. Its constructor normalizes an `App`, a legacy `agent=`, or a `node=` to one object. Wrapping either bare definition uses `model_construct` for compatibility with the old constructor. Direct `App` construction goes through validation. Session lookup uses the `(app_name, user_id, session_id)` tuple and can lazily create a missing session when asked. A Runner can serve successive invocations with the same definitions and services. It builds a fresh invocation context for each call, including a continuation of an existing invocation. [App model][app], [Runner initialization][runner-init], [compatibility construction][runner-app], [session lookup][runner-session], [context factory][runner-context].

| Entry | Execution at this commit | Where events cross the persistence boundary |
| --- | --- | --- |
| Async text, root `LlmAgent` | Defaults to chat. Chat may select a sub-agent from conversation history. Chat and task roots are executed through the node driver and LLM-agent wrapper. | Common queue consumer for node events. User-message events have their own ingress path. |
| Async text, root `Workflow` or other non-agent `BaseNode` | Background root task drives the node, with a scheduler that owns task and replay bookkeeping where applicable. | Common queue consumer. |
| Async text, other `BaseAgent` root | Legacy path chooses an active agent and drives its `run_async()` generator. | Runner's invocation plugin wrapper processes the yielded agent events. |
| Sync `run()` | Convenience adapter drives `run_async()` on its own event-loop thread, forwarding events and terminal errors through a thread-safe queue. Early close cancels that task and joins the thread. | The underlying async path. |
| `run_live()` | Agent roots use agent live lifecycle plus queued tool/node events. Non-agent roots use the live node driver. | Direct agent events use live-specific append policy. The queued stream travels through the common node queue consumer. |

The split matters when reading test results. Running an agent method in a unit test can exercise the LLM loop and agent callbacks while bypassing Runner ingestion, the event queue, and session write behavior. Likewise, live agent execution reaches different wrappers from the same root in text mode. [Runner text dispatch][runner-dispatch], [legacy path][runner-legacy], [sync adapter][runner-sync], [live dispatch][live-runner], [live stream merge][live-merge].

On the node path, the Runner first extracts function-response IDs, validates inputs, and resolves the owning invocation against the session. It recovers original user content for replay, attaches the abort signal, and allocates a shared queue. The input-message hook can replace the message before append. The user message and supplied state delta enter the history before node execution, and can be yielded with `yield_user_message`. A before-run hook can return content and finish the run early. Otherwise the driver creates a parent Context, starts the root task, drains events until the sentinel, and awaits the task so failures reach the caller after previously emitted events. A supplied or inferred historical invocation ID gives new execution objects the same durable identity. A paused task delegation can also admit a new user turn into its existing invocation and scope. [Node invocation bootstrap][node-root], [message hook and append][node-ingress], [root task and drain][node-drive].

### 2.2 Invocation objects and the two result channels

- **InvocationContext** carries session and services, current agent, run configuration, logical invocation ID, branch and scope, and bookkeeping for agent progress, model calls, cancellation, and live activity. A derived invocation context generally shallow-copies that container. The queue, session, shared maps and abort-state object can therefore remain shared, while local fields such as branch and agent can differ. The model-call limit counts through a shared cost manager. `end_invocation`, a control flag visible to processing stages, has a different role from caller abort and from persisted human-input interruption. [Invocation context fields][invocation-fields], [shared fields][invocation-queue], [abort sharing][invocation-abort], [model call budget][invocation-budget].
- **Context** represents one node execution attempt. It carries node, parent, run ID, node path, retry count, current output and route, pending interrupts and resume inputs. Its State points at the live session's values and this context's `EventActions.state_delta`. The read-only facade exposes mappings through a proxy and also exposes the Session. It is an API convention and a shallow view. The callback and tool contexts use the same mutable Context machinery. [Context construction][ctx-init], [Context output][ctx-output], [read-only state view][readonly-ctx], [Context aliases][ctx-aliases].
- **Event** is the yielded and stored record. It extends `LlmResponse` with invocation ID, author, event ID/time, branch, isolation scope, node metadata, long-running call IDs, output and `EventActions`. GenAI content parts carry messages and function calls/responses. Actions carry state and artifact deltas, route, transfer, progress and other control data. `NodeInfo.run_id` derives from the last segment of the node path, and `output_for` links an output to ancestors that claim it. A single persistent event can represent a message and a state or output transition. [Event model][event], [node metadata][node-info], [event actions][event-actions].
- **In-process result.** NodeRunner records the yielded output, route and interrupts onto the attempt's Context, enriches the Event, flushes pending deltas onto complete records, and enqueues it. The parent reads the returned Context to schedule the next step. A directly assigned output or route can be flushed after the generator finishes. Stored events support streaming and reconstruction after a pause. The queue's one consumer applies event plugins, appends non-partials to the Session, yields to the caller, and acknowledges the producer when the consumer advances. On a buffered service, append updates the logical live session and queues the physical write. [Node result tracking][node-track], [event metadata][node-enrich], [deferred output][node-flush], [queue producer][queue-put], [queue consumer][queue-drain], [buffered append][buffer-append].

Three forms of identity coexist for a reason. The invocation ID selects a logical run in a session across calls. A path such as `review@1/check@2` identifies an execution in the scheduler and replay. The branch governs what conversational history an agent sees, with a separate exact-match scope for a delegated task instance. Branch and node path can differ, for example when two workflow branches converge or an ancestor claims a descendant's output. Function-call IDs join requests and responses across events and may also supply a stable run ID for a delegated child. Author identifies who spoke or the workflow owning the event. Replay needs the path as well because ordinary workflow events can share the workflow author. [Node metadata][node-info], [NodeRunner enrichment][node-enrich], [task dispatch][task-dispatch], [branch and scope filter][contents-filter], [response resolution][runner-resolve-fr].

### 2.3 Agent tree and graph

`BaseAgent` adds a named parent/child hierarchy and agent lifecycle to `BaseNode`. Its bridge calls the normal agent generator, retaining the original author. Extension subclasses normally override `_run_async_impl` and optionally `_run_live_impl`, preserving the base lifecycle. Agent clones recursively copy sub-agents and rebind methods belonging to the source agent. Parent links enable ancestor defaults such as model selection and give the router a hierarchy for transfers. In the agent-tree composites, SequentialAgent walks children in order, LoopAgent repeats them within its configured bound or until escalation, and ParallelAgent merges branch generators with a TaskGroup and one-event acknowledgement per branch. Branch conversation isolation still leaves shared session state. These composites are marked deprecated in favor of Workflow, whose node input/output and graph edges are a different orchestration contract. [Agent bridge][agent-bridge], [agent lifecycle][agent-life], [cloning][agent-clone], [tree validation][agent-names], [sequential][sequential], [loop][loop], [parallel][parallel].

A Workflow compiles chains, fan-outs and route maps into edges. Named graph nodes are validated for reachability, START placement, uniqueness and unconditionally cyclic topology, with edge and schema checks. START seeds the trigger buffer and does not execute. The loop dispatches one outstanding run per named static node, assigns a run ID, and waits for the first tasks to complete. When several tasks are ready together, it processes them in scheduler insertion order with recovered order taking precedence on replay. Results become downstream triggers with the predecessor output, route and branch. Conditional edges match the route, an untagged edge always fires, and a default is selected if no specific route matched. A join can require all predecessors, buffer their arrivals and pass their outputs as a mapping at a common branch prefix. On a loop, arrivals from predecessors inside the cycle are consumed while an upstream setup step may remain satisfied. The Workflow returns one terminal output or propagates outstanding interrupts. [Graph construction][graph], [graph validation][graph-validate], [workflow setup][workflow-run], [completion loop][workflow-loop], [ready dispatch][workflow-ready], [static runs][workflow-start], [route selection][graph-routes], [join barrier][workflow-join], [workflow finalization][workflow-final].

Dynamic work uses `ctx.run_node()` and shares the same scheduler state, replay and outcome vocabulary with graph children. Nested workflows install their own scheduler and pass Context state back to the outer graph. A dynamic call can reserve a run ID, run on a sub-branch or claim its child's output. The scheduler remembers in-flight tasks and recovered outcomes by full path and avoids a repeated same-path execution in the same orchestration. It reserves ancestor IDs for an initially re-entered agent subtree so a real transfer back does not accidentally reuse the original path. Join gating, interrupt propagation and output ownership are handled at scheduler boundaries. `max_concurrency` limits new graph-scheduled work, permitting inline dynamic descendants and replay-only tasks to make progress even when parent slots are occupied. [Dynamic call contract][ctx-run-node], [run outcome][dynamic-outcome], [dynamic step][dynamic-step], [dynamic replay][dynamic-replay], [parallelism limit][workflow-concurrency].

A graph join waits for all configured incoming edges' predecessors to arrive. A predecessor that takes a different conditional branch does not satisfy it. An ordinary node that receives several triggers can execute once per trigger, in series. The parallel-worker wrapper is a separate form of fan-out. It assigns one dynamic child to each input, limits the number of active items with its own option, and collects results in input order. An interrupt stops admission while in-flight items settle. Item retry policies and a bounded cancellation drain keep the worker's failure vocabulary consistent with ordinary node outcomes. [Join buffering][workflow-join], [conditional join control][test-join-route], [worker admission and outcomes][parallel-worker], [worker cleanup][parallel-worker-drain], [per-item retry test][test-worker-retry].

For a concrete walkthrough, consider a graph in which a producer yields a value, an approval node takes that value and yields a `RequestInput`, and a final node consumes the approved result. Runner first appends the user input. The producer's value becomes an output event and its live Context output feeds the approval node. The approval's interrupt event identifies the call that the user should answer. The scheduler marks the run waiting and lets independent branches finish. On a subsequent call, a function response in the input identifies the old invocation, and the reconstructed producer output re-seeds the approval input. The approval node either takes its matched answer as output or reruns with `ctx.resume_inputs`, depending on its contract. The final node receives the approval result and its output can belong to the workflow without a duplicate parent event. This walkthrough follows the code and the repository's reload tests. [Yield normalization][base-node-run], [Workflow completion][workflow-complete], [resume decision][replay-intercept], [reload test][test-resume-reload].

### 2.4 From conversation history to model response

An LlmAgent's default text flow is SingleFlow or AutoFlow. The latter adds a transfer processor to the same request/response pipeline. Each ordinary step constructs an `LlmRequest`, applies ordered request processors, then decides whether to pause, replay unexecuted calls, or make the next model call. The processors assemble generation settings, handle pending interactive requests, add instructions and identity, prepare compaction and interaction-chain metadata, project the event history, apply caching/planning, and resolve tools. Some stages can emit events or stop the invocation before model dispatch. Stable processor names allow a flow author to locate or replace a stage, while the declared order carries dependencies such as compaction before content construction. [Flow selection][agent-flow], [standard processors][flow-processors], [processor extension API][flow-extension], [step driver][flow-step], [flow resume][flow-resume].

The content builder derives the model's view from the event ledger. It applies rewind markers, matches the current branch and scope, filters orchestration records, and removes tool sub-branch progress from the parent model's input. It rebuilds the initiating task input from the delegating function call or the explicit workflow input, presents other agents' visible messages as context, and preserves or removes synthesized call IDs depending on adapter needs. It rearranges late function responses, recovers earlier matching calls when compaction obscures them, and removes unmatched pieces before projecting request contents. Full history and current-turn-only building are separate paths. Server-side interaction chaining is one reason for the latter. The execution-oriented branch query in InvocationContext has different inclusion rules because it is looking for call and resume ownership. [Content projection][contents-processor], [event filtering][contents-filter], [history and pairing][contents-build], [branch visibility][contents-branch], [execution event lookup][invocation-events], [compacted call test][test-compacted-call].

Models implement `BaseLlm.generate_content_async` for one turn or supply a connection context manager for live I/O. The caller can supply a model object, specify a registered name, or inherit from an ancestor/default. Lazy registry entries allow importing the runtime without loading all adapters. Provider classes map their specific responses into ADK's `LlmResponse` and its GenAI content types. Model capability snapshots influence whether native structured output can be combined with callable tools. For a model that lacks that combination, the flow can install `set_model_response` and turn its validated output into a final model event. Task-mode agents use a separate task completion tool. An experimental fallback model is a model-level policy with its own request snapshot and opening/response rules. It is independent of a workflow node retry. [Base model contract][base-llm], [connection contract][base-connection], [model selection][agent-model], [registry][model-registry], [wire representation][llm-request], [capabilities][llm-capabilities], [structured output fallback][schema-processor], [model fallback][fallback].

The model call stage enforces the invocation's model-call budget and runs before, after, and error hooks around provider work. A before-model response can replace the provider call without incrementing the count. A model-error callback can recover with an ordinary response. The flow finalizes provider data into a model event, including call IDs, and yields it before dispatching completed function calls. The resulting function-response event is part of the next model request. The loop stops on a final response, a pause, an end flag, or absence of further useful work. The public final-response predicate can also mark the end of an agent's current stream when it waits on a tool. An LlmAgent configured with an output key can write the final text or structured value into the event's state delta. A node wrapper can also promote a model reply or validated task completion to graph output. This gives a single answer both conversational and orchestration meaning with explicit ownership metadata. [Model call][model-call], [event finalization][model-finalizer], [step postprocessing][flow-postprocess], [final response predicate][event-finality], [agent output key][agent-output-key], [graph LLM output][wrapper-output].

The fallback adapter illustrates how the contract handles partial progress. It can try a different model before the first response or before a live connection opens. Once output or a connection exists, errors stay with that attempt. It snapshots request fields that delegates can mutate while retaining live tool objects. Capability discovery uses the primary model before fallback is needed, so a backup with different capabilities receives a request prepared for the primary. One ADK budget unit can consequently cover several delegate attempts, and a node retry can repeat flow work. The individual limits are useful within their layers. Their composition does not guarantee a ceiling on provider attempts. The archive's fallback test module was blocked on LiteLLM at collection, so this is an inspected contract. ### 2.5 Tools, transfers and agent modes

Tools provide a declaration and an execution interface. `FunctionTool` derives declarations from a callable's signature and types, excluding runtime context arguments. It converts and validates the model's arguments, injects `ToolContext` and live input streams when appropriate, and returns model-facing errors for recognized input problems. `BaseToolset` resolves tools for a context, supports filtering and prefixing, and can release owned resources at close. The request carries both provider-facing declarations and the executable tool map. On a completed call the dispatcher copies arguments, resolves by name, gives each call its own context and delta, runs hooks and confirmation gating, then associates the normalized result with the original call ID. Long-running or deferred calls with no immediate result remain open. [Base tool][base-tool], [FunctionTool declaration][function-declaration], [FunctionTool execution][function-execute], [toolsets][toolset], [tool request registry][llm-request], [call preparation][tool-prep], [call execution][tool-execute], [tool response][tool-response].

In ordinary text mode, a batch executes through asynchronous tasks and yields a merged function-response event. Result parts follow call order, while state changes use a deliberate merge policy, including a correction for shared container values changed by overlapping calls. If one call fails or interrupts, the dispatcher cancels unfinished siblings and can preserve finished plain results so a later turn does not rerun work whose result was available. Control actions such as a transfer are excluded from that salvage path. The postprocessor can emit interactive requests, convert structured results into final model responses, and interpret transfer actions. Request dispatch uses completed call records. Partial argument chunks only represent progress. [Batch assembly][tool-batch], [failure and sibling result handling][tool-batch-run], [postprocessing][function-postprocessor], [streaming response contract][llm-partial].

The delegation mechanisms have different ownership of the next turn.

| Mechanism | Control flow | History and result |
| --- | --- | --- |
| `transfer_to_agent` | A tool sets an Event action naming an eligible target. Chat and task node wrappers hand this to the dynamic scheduler. The legacy flow and single-turn wrapper can execute the target inline, with a separate connection handoff in live mode. | Conversation continues under the target and its branch. The next chat invocation may be routed from the last valid transfer, reply or tool ownership. |
| Direct `AgentTool` | A tool creates a nested Runner and scratch in-memory session. It runs the child, collects the last content/result, and forwards state changes and artifact operations. It inherits run settings with a separate invocation call counter. | Ordinary tool return. The nested scratch history is discarded. A child with an unresolved interrupt cannot be resumed by this adapter. |
| Single-turn sub-agent or `NodeTool` | The tool invokes a node through `ToolContext.run_node`, on a tool sub-branch associated with the function call. | The parent's model receives the paired tool response and can continue. Intermediate node events are available to the outer event stream and are filtered out of that model's context. |
| Task-mode delegation | The chat/task node wrapper recognizes a deferred task tool call, uses the call ID as run ID and scope, and dispatches the child. A valid `finish_task` response promotes the submitted task output. | The caller receives a synthesized function response when the task completes. A paused child can reacquire the same identity from stored calls. Mixed batches are drained for eager responses before re-entering the coordinator. |

A graph LlmAgent defaults to single-turn when converted as a standalone node by graph construction. Root chat selection and sub-agent conversion supply different defaults. Chat consults conversation context. A single-turn graph node prepares typed input as local user content, may run a configured agent transfer inline, and clears that handoff in its live Context after consuming it. Task mode has a separate wait-for-output contract. These differences explain why a wrapper or mode choice changes resume behavior even with the same model and function. ### 2.6 Persistence, state, and compaction

The public session service can create, retrieve, list, delete and append. The mutable Session represents an ordered history plus a materialized state view. Normal state assignments affect the session immediately and record a pending delta. NodeRunner or the callback/tool adapter puts that delta on an event. The session service applies it to the caller's live Session and routes scoped keys into the corresponding storage. Application state is shared by app, user state by app and user, and ordinary state by session. Temporary state is usable during the current run and stripped from the persisted delta. Artifact methods write through a separate versioned service and carry references/deltas in events. Memory is a separate recall service. The same Event extension can cross a durability boundary and a model request boundary, while each boundary can project its own representation. [Session model][session], [append and scope][session-interface], [state assignment and nested writes][state], [state scoping][session-util], [artifact save][ctx-artifact], [memory service access][ctx-memory].

| Store | Behavior relevant to the runtime |
| --- | --- |
| `InMemorySessionService` | Stores session data in dictionaries with separate shared state buckets. Normal reads and appends copy saved data. An opt-in light-copy feature shares nested objects and event instances. Equal re-deliveries with the same ID are deduplicated. |
| `SqliteSessionService` | Stores event payloads as JSON with separate scope state. `BEGIN IMMEDIATE` serializes writes across stale check and commit. Fetch reverses descending timestamp and rowid order. The staleness check uses the update time. |
| `DatabaseSessionService` | SQLAlchemy handles schema versions and maps events and state through a transaction. Per-session/shared-state locking and dialect-dependent row locking guard concurrent updates. The loaded revision marker is an exact representation of a timestamp, so it distinguishes rounding artifacts and can repeat for two writes at the same time. |
| Experimental `BufferedSessionService` | Appends optimistically to the live Session and snapshots the event for an ordered writer. Writers coordinate across shared app/user scopes, and reads wait for writes affecting their view. Overrides of `append_events` must implement atomic batches. Failed writes surface through persistence errors and a rejected stale or failed live Session. Flush is the durability boundary exposed to callers. |

The Runner flushes the supplied session service at close. Connections owned by a concrete service have a separate close lifecycle. The node queue acknowledgement is therefore a logical visibility boundary with buffered storage. It is also tied to caller advancement, which matters for execution timeouts. Per-invocation queueing serializes writes by that consumer. Concurrent invocations can still hold different snapshots of the same session, and store semantics determine which stale writes can be rejected. Buffered writers are loop-affine while work is pending. A quiescent buffer can move to a new loop, and writes stranded when a loop ends become reported failures. This matters when combining the buffer with the sync Runner adapter, whose worker loop is scoped to one run and ends after the event stream. [Memory persistence][memory-store], [light-copy semantics][memory-copy], [SQLite append][sqlite-append], [SQLite reload][sqlite-read], [database append][db-append], [database marker][db-marker], [buffered contract][buffer-contract], [shared scope append/read][buffer-scope], [loop transitions][buffer-loop], [loop teardown test][test-buffer-loop], [sync adapter][runner-sync], [Runner close][runner-close].

Schema age affects replay. Database v1 stores the Event as JSON plus indexed row fields, and reconstructs the complete record. The legacy v0 mapper retains a fixed set of columns and warns about fields it cannot store. Its repository tests establish that `output`, `node_info`, and `isolation_scope` can be dropped on that round trip. These fields let newer workflow and task paths recover values, addresses and visibility. Continued read support for old sessions is valuable, but workflow recovery on that schema cannot depend on complete preservation of those fields. This is a documented compatibility limit, independently of the tied-timestamp test. [Schema selection and warning][db-schema-warning], [v0 field inventory][db-v0-event], [v1 event payload][db-v1-event], [round-trip tests][test-v0-event], [workflow resume setup][workflow-run].

Compaction produces summary records and a shorter model projection, preserving the original history for replay. The request path can compact against a token estimate, and a completed run can compact based on app policy. A compacted prefix must preserve the relation between calls and responses in the retained tail. The compactor tracks open calls and adjusts a split to keep matching events together. If a concurrent turn advances the session while a post-run summary is being computed, the Runner discards the stale summary. Rewind appends a marker with state/artifact adjustments, and the active-history filter hides the rewound interval from its consumers. Rewind fetches the full history, restores session-scoped values represented by earlier events, and leaves shared app/user state alone. One documented limit is that an initial value supplied only to `create_session` is unavailable to rewind after a later event overwrites it. The passing control expects a cleared value in that case. ### 2.7 Resumption, retries and cancellation

An interrupt is a persisted request, with an identifier on a function-call part and a corresponding interrupt set. The scheduler records a waiting outcome, propagates interrupts across awaited parents, and can finish unrelated siblings. Static task-mode pauses can also gate admission of new work. A new user FunctionResponse matches the call by ID and invocation. The strict node ingress rejects a message whose response IDs belong to several invocations. Resuming reconstructs execution state from saved events and original input, keeping the node's run path stable. RequestInput serializes a response schema, and the reconstruction helper validates its supported shapes. A directly coordinated LLM flow inspects its branch history and calls to decide whether to rerun a tool after confirmation, forward the supplied deferred result to the model, or keep waiting. When a call batch has partially settled, it selects the subset of unexecuted calls. [Interrupt conversion][request-input], [task-mode gating][workflow-ready], [strict invocation match][runner-resolve-fr], [resume validation][reconstruct-responses], [open interrupt index][interrupt-index], [LLM resume actions][flow-resume], [replay call subset][flow-call-subset].

A Workflow creates a fresh loop state and replay index on each execution. It scans active events in the invocation and identifies child paths, results, failures, interrupted calls, and resolved responses. Dynamic descendants can be indexed and rehydrated lazily. Replay can yield a cached outcome through a synthetic Context, rerun a node with resolved inputs, or keep it waiting without running it. A non-rerunning leaf can complete directly from all answers. A rerunning orchestrator can advance on a partial set. Nested workflows re-enter to make these decisions for their own descendants. Sequence barriers constrain the order of historically completed work and report divergence on a bounded wait. Fresh sibling completion order still depends on real scheduling. [Workflow replay setup][workflow-run], [incremental index][replay-index], [workflow replay scan][replay-scan], [replay result classification][replay-intercept], [sequence barrier][replay-barrier].

`ResumabilityConfig.is_resumable` adds agent progress and end markers and changes legacy Runner admission and resume behavior. The graph scan is unconditional. A root node can receive a matching function response with either flag value. The flag enables Workflow status snapshot emission. The load path reconstructs state from events, and the snapshot loader remains a TODO. Legacy agent composites use their saved state. The documented guarantee is best-effort and at least once, so a run whose side effects occurred before a durable terminal record can repeat work. A terminal result, transfer, route, or other qualifying event is currently the evidence for progress. [Resumability config][resumability], [legacy resume dispatch][runner-legacy], [agent state load][agent-state-load], [workflow checkpoint writes][workflow-checkpoints], [workflow load path][workflow-run], [replay classification][replay-intercept].

NodeRunner has per-attempt timeouts and retry policy. An exception can first become an error Event, then be retried after a delay. Filters match exception types through their class hierarchies, and configuration and invariant errors bypass retry. Attempt counts belong to the current local execution and reset on cross-call resume. A workflow can report a child's error through its Context so a retry policy at the workflow layer can act on it. For a dynamic child failure the runner restores allocation counters to reuse completed work from that attempt, and waits for prior queued events to be appended before a rescan. Retry of a node's own exception follows the node's documented semantics. A timeout and a caller's cancellation are distinct paths. `NodeInterruptedError` is a dedicated control signal that bypasses ordinary exception handlers and is collected as waiting. Once retry is exhausted, errors reach parent Context or the outer async generator, with the original cause retained where possible. ## 3. Why the design works and governing invariants

| Invariant | Consequence and limit |
| --- | --- |
| An invocation ID names a logical run, while a node path names a particular execution in it. | Replay can reconstruct graph state and correlate inputs after process-local task state has been discarded. Dynamic callers need stable naming and dispatch when replay should find the same path. Distinct loop iterations consume distinct IDs. |
| A function response must be associated with its originating invocation and be visible to the originating call's branch. | One history can carry several pending calls and branches. The same identifiers tell the Runner where to resume, let the workflow reconstruct an interrupt, and allow the model context projection to pair calls with results. Validation has to use the effective message after transformation. |
| A node reports at most one present output per attempt, and records route and outcome separately. | Parents can route one result without parsing conversational content. Output-bearing events may represent multiple owners via `output_for`. A workflow with several terminal candidates checks for one present result. A node can emit an output and then interrupt, in which case WAITING wins over downstream scheduling. A missing output can be a valid outcome, so durable completion needs more than a payload check. |
| Completed records enter the logical session before the consumer yields them. | A dependent step can read the tool result or state it just produced. A queued node resumes after the consumer acknowledges, and retry waits for already enqueued events. Buffered writing changes when that visibility becomes durable. |
| Partial model fragments are provisional and completed tool-call events are executable. | Partial function arguments can stream as data arrives. The committed content carries a complete call and an ID with which a result can be paired. A later replay reads the complete record. |
| Parallel schedulers own their tasks and define completion ordering. | Fresh work can overlap and sibling conversation views stay separate. Outcome reduction handles a batch of ready tasks predictably, and historical completions retain order through a replay barrier. State remains shared, and independent fresh task completions still reflect scheduling. |
| Abort, pause, normal close, and failure have different lifecycle meanings. | A caller can retain a request for later continuation by closing early, or abort with a terminal event that balances outstanding calls. Failure can be recovered at a tool/model hook or reported at node/agent/invocation boundaries. Started external effects and synchronous worker calls have their own lifetimes. |
| The ledger and its views have different retention requirements. | A model prompt may discard or summarize old conversation. Session recovery still needs enough actual history to recover invocations, paths, request arguments and completed results. A filtered fetch is a narrower recovery substrate as well as a shorter prompt history. |

These invariants are implementation contracts, with limits exposed when composing paths. For example, round-tripping a plain JSON node result through the same session schema is a straightforward replay operation. Converting it at the late event hook introduces two possible values for a downstream edge. The serial node queue establishes an order for its own consumer. Concurrent writers need revision handling in storage. ## 5. Weaknesses

### Reproduced behavior with a specific mechanism

**A rewritten function response can be recorded under the wrong invocation.** The archived control runs resume the original workflow in both stores. With an ingress plugin returning a valid response for a different existing call, the effective response is appended under the original invocation ID and the intended workflow remains unfinished. This is a node-path ingress defect. The initial message is resolved to an invocation before the hook. After replacement, resume inputs are recalculated, while invocation resolution is conditional on the old ID being absent. The append stamps the chosen ID from Context. The same mechanism explains both the explicitly supplied and inferred-ID cases. Repository source tests establish the component contracts for callback replacement, post-callback routing, and strict function-response ownership. The combined case comes from the existing observations. **An effect-only step can execute again after successful completion.** A step that finishes without emitting a durable result, route or delta can leave no event that distinguishes completed work from work never run. ## 9. Post-mortem and prioritized improvements

ADK is carrying a working conversational agent API into a runtime that also needs graph-style dataflow and durable suspension. Reusing Events, agent definitions and session adapters lets those features compose with existing tools, plugins and model adapters. It also gives one type responsibility for model input, user-visible output, state commit and scheduler recovery. Most of the behavior findings occur where a later layer changes an event that an earlier layer has already acted on, or when a layer assumes a timestamp, persistence call, or consumer yield represents something stronger than it does. Several different mechanisms already protect useful work, including the replay barrier, child-outcome tracking, and ordered buffered writes. The improvements below preserve those mechanisms while tightening where a commitment is made. [Agent bridge][agent-bridge], [event shape][event], [node tracking][node-track], [replay barrier][replay-barrier], [buffer ordering][buffer-scope].

1. **P0. Resolve the effective user message before committing it.** Recompute invocation ID, branch, original turn input and collected responses together before append. Use the existing explicit-ID rule, which warns on mismatch and takes the matched call's invocation. Keep the legacy non-resumable admission rule in its own driver. Add a test that checks both the store and the resumed output with two pending invocations, with explicit and inferred IDs. Run it against both in-memory and a file-backed service. [Fault boundary][node-ingress], [explicit-ID reconciliation][runner-reconcile], [strict resolver][runner-resolve-fr], [observed controls][probe-response].
2. **P1. Give replay an explicit terminal outcome and a distinct delivery policy.** Persist completion even when a node has no output. Represent an emitted transfer and its consumption separately, so replay cannot take an already completed handoff twice. Associate a stable outcome identity with stream re-delivery, and declare which callback fields may change replayable results. Use the same output normalization for yielded values, direct assignments and recovered outcomes. Version the recovery representation and retain a reader for current histories. Resume controls should cover two interruptions, graph versions, silent work, nested delegation, and service reload. Position-backed snapshots could then bound the tail that needs scanning. This limits avoidable repeat work while preserving the at-least-once contract across a crash. [Missing completion evidence][node-flush], [replayed action][reconstruct-results], [checkpoint TODO][workflow-run], [schema compatibility test][test-v0-event].
3. **P1. Commit a revision independent of event timestamps.** Use a monotonic per-session revision in the same transaction as the append and state merge. Use an explicit appended-event sequence for replay order and keep event timestamps for time-based queries. Align native SQLite, SQLAlchemy and buffered-store conformance. Protect against both false rejection of the writer who made the last commit and false acceptance of a writer whose history lacks it. Test the two directions with equal event timestamps and independent service handles. [Database compare][db-append], [SQL tie ordering][db-order], [native SQLite append][sqlite-append], [reproducing case][test-db-tie].
4. **P2. Unify event commitment and define deadline ownership across text and live.** Separate the persistence acknowledgement from delivery progress, with a bounded delivery queue and a defined overflow or cancellation policy. At minimum, document whether a deadline includes plugin, storage and consumer waits. Apply the same explicit live media persistence decision to both direct and queued events. Make pump teardown cancel and join all owned tasks before choosing which failure to propagate. Currently an exception from the first cleanup in live merge skips the second. The ordinary early-close regression covers backlog and normal cancellation. A coincident producer failure and early close remains an uncovered source-level lifecycle risk. [Queue consumer][queue-drain], [deadline scope][node-timeout], [live media policy][runner-live-append], [live merge teardown][live-merge-cleanup], [early-close control][test-live-backlog].
5. **P2. Make the minimum-dependency test tier exercise the public core.** Move tests that require optional adapters out of modules that cover plain Runner, capability, workflow and hook contracts. Publish the selected modules, installed versions, fixture backends and result categories for each tier. Define a small cross-path conformance matrix for normalized durable effects, model transcripts and plugin order. Give tests owning a database service a fixture that disposes it before its event loop closes. This would make the next investigation spend less time attributing collection and cleanup noise while preserving full-extra tests. [Collection evidence][collection-log], [setup reference][setup-skill], [local store matrix][session-conformance], [teardown control][test-compaction-close].
