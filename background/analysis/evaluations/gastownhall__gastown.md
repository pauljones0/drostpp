Gas Town is strongest where it makes work survive a process lifetime and verifies Git evidence before cleanup. ## 2. Core architecture and end-to-end control/data flow

### Authority and state

`gt` is a local Cobra command surface shared by humans, agent processes and the Go daemon. The workspace is a town with rig records for individual repositories. The Mayor handles plans and cross-rig coordination. Crew are user-managed workspaces. The Deacon, Boot and dogs perform different levels of recovery, automation and checks. Witnesses inspect a rig's workers. Polecats implement assigned work in Git worktrees, and a Refinery agent consumes each rig's integration queue. The town's tmux socket derives from the canonical town path, and the registry maps rig prefixes to session names. The daemon takes a town-scoped flock before writing a PID file, performs Dolt and SDK preflight, opens stores, starts the convoy and feed loops, and then enters the recovery loop. ### Provider, delivery and extension contracts

The provider boundary is operational. A runtime preset or a town/rig/role override supplies executable, arguments, process names, prompt mode, readiness, session resume and hook layout. The supervisor passes that contract into tmux and does not implement provider inference or gate every tool call. For providers that support ACP, the proxy manages JSON-RPC stdio, tracks session/handshake and prompt state, and can inject messages while preserving its transport contract. The standalone `internal/agent` and `internal/agent/provider` tests exercised registration and message parsing. Source import tracing found no production consumer in the command and internal packages, so those tests do not demonstrate the provider behavior of the tmux or ACP paths. Provider hooks, local directives, formulas and plugin manifests extend the runtime at different layers. Dog plugins can carry instructions or shell scripts, and exec-wrapper plugins provide operator-selected startup wrappers. Default presets can give model subprocesses broad permissions, so separate Git worktrees and town sockets provide operational ownership rather than OS-level containment. Trust and resource policy matter at the chosen runtime/wrapper boundary. ## 3. Why the design works and its governing invariants

- **Work owns the continuation.** A process can die without erasing the assigned work, its branch, or the authority to resume. The worker identity, assignment and session can advance at different times. Recovery therefore reads issue/agent fields, Git and live tmux independently. A durable hook plus an executable prime path makes recovering the next action cheaper than restoring every token of the previous conversation. [Identity, sandbox and session model](repos/gastownhall__gastown/docs/concepts/polecat-lifecycle.md:80) [Recovery behavior](repos/gastownhall__gastown/internal/cmd/prime.go:193) [Decision function](repos/gastownhall__gastown/internal/polecat/workstate.go:59)
- **Workers must see the same assignment that was admitted.** Resolve town and rig IDs before launching. Persist the hook first. Bind the actor and work directory at spawn. Scope queue close and retry to the store that owns the context, not whatever database the scheduler inherited. The per-bead flock prevents simultaneous normal assignments of one source on one host. Per-assignee locking helps serialize hook updates to the same agent. These are local serialization mechanisms with explicit force/recovery paths. [Bead lock](repos/gastownhall__gastown/internal/cmd/sling_dispatch.go:97) [Hook ownership and ordering](repos/gastownhall__gastown/internal/cmd/sling_dispatch.go:373) [Queue owner routing](repos/gastownhall__gastown/internal/cmd/capacity_dispatch.go:391) [Spawn identity](repos/gastownhall__gastown/internal/session/lifecycle.go:198)
- **Admission counts work state, not just windows.** Live work and certain recovery-blocked records occupy capacity. Idle reusable or terminal slots, and pending merge work with no active polecat workload, are distinguished from productive capacity. A reservation covers the interval between admission and visibility of the worker state. The scheduler dispatch lock and admission flock have different scopes. Host pressure checks are optional additional gates and process count is an estimate. [Capacity model](repos/gastownhall__gastown/internal/cmd/polecat_capacity.go:24) [Reservation transaction](repos/gastownhall__gastown/internal/cmd/polecat_capacity.go:111) [Workstate accounting](repos/gastownhall__gastown/internal/cmd/polecat_capacity.go:270) [Host pressure policy](repos/gastownhall__gastown/internal/daemon/pressure.go:31)
- **Cleanup needs evidence.** A clean terminal worker can retire independently of later Git cleanup. Dirty Git state, active hooks, unknown state and live merge evidence can block unsafe slot reuse. The MR source code is tied to a SHA and cleanup validates reachability from the actual remote target before closing (with a branch-head check before deletion). This separates durable progress from wake delivery and prevents a majority of plausible premature deletions. [Recovery classifier](repos/gastownhall__gastown/internal/polecat/workstate.go:59) [Safe reuse policy](repos/gastownhall__gastown/internal/polecat/reuse.go:43) [Retirement policy](repos/gastownhall__gastown/internal/cmd/done.go:1936) [Submitted head validation](repos/gastownhall__gastown/internal/refinery/engineer.go:1478) [Remote reachability proof](repos/gastownhall__gastown/internal/refinery/engineer.go:1538)
- **Prefer reconciliation to persistent process belief.** The convoy watcher intentionally warms high-water marks at startup and has a periodic state sweep for completions or feed missed during outage. The daemon detects locks and processes anew, keeps unhealthy database behavior separate from empty work, and retains janitors and doctor routines. The invariants depend on visibility of Beads and Git evidence, a healthy local supervisor, and compatible runtime hooks. ## 5. Weaknesses and evidence status

P1 issues can block supervision, defeat an operator stop or leave work recorded as complete with the wrong durable result. P2 issues affect reliability or diagnosis at narrower boundaries. The labels express triage priority for this snapshot.

**W1. P1 — An acknowledged scheduler pause can be overwritten, and queue clear does not fence a planned dispatch.** Pause and resume do a load-modify-save of the whole scheduler JSON. The dispatch completion path reloads the file, updates the dispatch fields, then independently replaces it. If pause saves between that reload and replace, dispatch writes the older pause bit back as false. The isolated state-file control verified both orderings, starting with a successful read of the operator's saved pause. State-file atomicity prevents torn JSON and provides no transactional merge of fields. Separately, clear closes queue records without the dispatch flock. A cycle already holding a plan reuses the cached record and validates the work issue, so a cleared context can still reach execution. The pause loss is reproduced at the file boundary. The symmetric control also loses an acknowledged resume when stale accounting still holds the paused state. The clear race is traced through the source and is conditional on the plan already being built. **W2. P1 — Daemon cancellation is weaker than the timeout topology implies.** The per-rig worker pool limits simultaneous callbacks and gives each a derived context, then waits for every callback. Several heartbeat callers discard that context, including witness/refinery starts, polecat health and pruning. The cooperative and non-cooperative controls used the same pool and deadline and showed the fast rig finishing in both cases, but the outer stage stayed blocked in the latter. A canceled parent still entered all three queued callbacks. Separately, queued dispatch uses a fresh background timeout, Unix `Setpgid` without a group-aware cancel function, and unbounded `CombinedOutput` pipe waiting. In a local process control the leader died on cancel and the child held its inherited output pipe until killed. Giving the control a group-wide cancel made it finish. A configured five-minute scheduler timeout therefore cannot bound every subprocess tree or guarantee prompt daemon shutdown. The main select loop handles shutdown, heartbeat and Dolt health serially. Convoy close processing also invokes a plain `exec.Command` for cross-rig nudges while manager stop waits for the event-poller goroutine. That call has no deadline from the manager's cancellation context. **W3. P1 — Deacon crash-loop detection latches outside the advertised window.** `RecordRestart` overwrites `LastRestart` with now before checking whether it is within the current window. It also counts starts since the stability reset without storing a window of attempts. With defaults, a control drove five starts spaced 14 simulated minutes apart, with two starts in the final 15 minutes. The tracker fired and persisted the latch. Five starts one minute apart correctly fired, and gaps beyond the 30-minute reset did not. Both ensure-running and stale-Deacon restart consult the latch, which can block future recovery until manually cleared. ## 9. Post-mortem and highest-leverage improvements

### Reconstructed failure, with individual boundaries verified

A plausible incident begins while a scheduler tick has already built a batch. An operator sees an acknowledged pause, but a concurrent successful dispatch overwrites the persisted pause with its pre-pause snapshot. A queue clear can also leave an already planned request eligible for execution in that cycle. The scheduler may proceed to spawn a worker and fail in its final context close, so live tmux and the work hook indicate a launch while the scheduler prints a failed item and exits successfully. Existing status guards usually keep the surviving context from immediately creating a second worker. A process loss or deliberate reopen changes those conditions. If a CLI child holds inherited stdout after the scheduler leader exits, the heartbeat does not finish until the pipe closes. Other recovery work in that main daemon loop waits behind it. Operators have separate process, queue and agent views, but no shared attempt record combining them. This sequence composes source paths with verified isolated mechanisms. It is a reconstruction, with no claim that the full chain occurred on a running town. The underlying architectural pressures are legitimate. External runtimes and tmux make provider support broad, Git gives recovery a hard evidence source, and Beads makes plans durable across sessions without building a conversation persistence layer. Local files and subprocesses also make the system possible to operate and inspect from an ordinary shell. The cost is that completing a task spans independently committed effects. The scheduler lock serializes a cycle but misses related operator writers. Rename gives coherent file images but cannot preserve another actor's intent. Cancellation reaches the command leader unless the launcher owns the whole tree. Retries keyed on an issue or branch name preserve identity through reuse but can conflate distinct attempts or SHAs. Compensators and polling recover many common cases and still need a precise source of truth at these boundaries. The problem is a narrow mismatch of authority and commit points across layers. The design can keep Git evidence, Beads work records, isolated runtime processes and reconciliation.
