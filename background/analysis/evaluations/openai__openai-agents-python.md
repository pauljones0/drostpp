**Verdict.** The SDK is a capable in-process agent interpreter with an unusually mature recovery model for intermittent approvals and tool work. Its strongest design choice is the explicit transition between model output, executable calls and an accepted turn. It has effective adapters and unusually deep tests for call identity, recovery, cancellation, and storage. It becomes harder to reason about when one logical turn spans several owners and several irreversible events. The highest-value changes are to unify the transition and persistence decisions across the two execution loops, tighten history provenance, and make event and policy boundaries explicit. The local investigations below show where those changes would affect observable behavior.

## 2. Architecture and end-to-end control and data flow

### Entry points, declarative configuration, and execution identity

`Agent[TContext]` binds a model or model name, instructions, optional provider prompt, tools, handoffs, guardrails, output shape and hooks. An agent is reusable configuration. `RunConfig` overlays run-level model selection, settings, guardrails, model input filters, tracing and execution policy. `Agent.clone()` is deliberately shallow. Mutable collection identity and individual tool and hook objects can remain shared. `RunContextWrapper` wraps application data, usage and approval decisions. A `ToolContext` shares the relevant run-owned state and adds tool name, canonical identity, call ID, arguments, history and invocation metadata. The model receives provider request items and instructions after explicit preparation. Application context enters the request only through application-authored instructions, input and tools. `AgentBindings` carries the public and execution agents independently when a prepared clone has sandbox-bound tools or instructions. Hooks and results describe the public agent. The public `Runner` dispatches to the default `AgentRunner`. `run_sync` schedules the async implementation on a per-thread usable loop and rejects use while a loop is running in that thread. Reusing the loop preserves loop-bound application/provider clients. `run_streamed` returns a mutable `RunResultStreaming` immediately and owns a background task. Its async iterator is a delivery and teardown interface. The runner normalizes `RunConfig` and records ownership of an implicitly constructed provider. It closes that provider on finish, including the streamed case where cancellation prevents the task from entering its body. Explicit providers remain application-owned. Cleanup of a model's run-scoped resources and closure of a provider's persistent resources are separate operations. A new run validates conversation settings, creates or adopts a context wrapper, prepares input from the selected history owner, and establishes a `RunState` and tracing scope. A resumed run takes the preserved turn budget and agent identity, reconciles pending session writes, reconstructs the per-agent tool-choice state and any server tracker, and restores the correct turn transition. A turn is one logical model invocation and response resolution. Retries may make several transport requests within it. The default budget is ten, `None` means unbounded, and approval resolution consumes no additional turn by itself. Initial user input is guarded by the starting agent and run guardrails. A separately staged `RunState.add_input()` batch is guarded at admission by the current agent and run guardrails. ### Handoffs, agents as tools, and schemas

A handoff is a model-advertised tool with a callback and an optional schema for structured routing arguments. It transfers continuation in the current loop. The runner invokes it, records the source and target and correlated call output, runs hooks and builds the next agent's view. Filters can rewrite `input_history`, pre-handoff items, current items or a separate model-input view. The opt-in nested history mapper renders earlier conversation content as a transcript and tracks items carried by that transcript to avoid re-adding them on later replay. Server-managed execution cannot use that client-side transformation. It explicitly rejects handoff input filters and disables nested history with a warning. `Agent.as_tool()` starts a nested run and returns a function-tool result to the parent agent, which retains control. The nested run uses the supplied input builder, has its own approval scope and resumable state, and contributes to parent usage. Nested streaming adds an opt-in event callback with a configurable pending-event cap. [Handoff schema and factory](repos/openai__openai-agents-python/src/agents/handoffs/__init__.py:284), [handoff invocation and history transformation](repos/openai__openai-agents-python/src/agents/run_internal/turn_resolution.py:545), [agent-tool contract](repos/openai__openai-agents-python/src/agents/agent.py:646), [nested state rebind](repos/openai__openai-agents-python/src/agents/agent.py:936), [nested streaming](repos/openai__openai-agents-python/src/agents/agent.py:970).

Function schemas come from the callable signature, annotations, metadata and parsed docstrings. First-position context injection stays out of the model-visible interface, and `FuncSchema.to_call_args` reconstructs positional and keyword arguments for the real callable. Strict conversion walks objects, references and unions, closes objects and makes their exposed fields required. A separate output schema adapter describes what the model should produce and independently validates the returned JSON with Pydantic. Plain text needs no JSON contract. Pydantic-model and dict outputs can use their object shape directly. Other Python types are generally wrapped under `response` for provider-facing object schemas and unwrapped after validation. Direct tool termination returns the tool result under its own contract, and `final_output_as` defaults to a typing cast with opt-in runtime checking. A structured model response, a tool result and an error-handler fallback therefore have different validation origins. ### History and recovery have different owners

| Mechanism | Owner and operational boundary |
| --- | --- |
| Explicit replay | Application uses `RunResult.to_input_list()` and passes history to the next run. The historical `preserve_all` view and normalized continuation view differ after some handoff filters. |
| `Session` | SDK reads history, prepares the model view and appends new input and accepted per-turn items under a logical session ID. The public protocol supplies get, add, pop and clear. Compatible extensions can opt into a context wrapper. SQLite moves operations onto worker threads and performs atomic batch inserts under its write lock and transaction. |
| OpenAI continuation | `conversation_id` or response chaining selects provider-owned history. `OpenAIServerConversationTracker` separates already acknowledged input, predicted or delivered state and unsent output. It uses item references in process and stable IDs or fingerprints across serialization. The runner sends delta-only input and rejects mixing this mode with `Session`. |
| `RunState` | A versioned SDK continuation record for an unfinished execution. It can store processed tool work, active agent identity, canonical approval decisions, turn counts, staging, provider continuation metadata, usage and trace state. Loading requires current trusted agent and capability definitions. |

The session input callback works on copies of history and incoming input and returns a model view. The implementation then infers which returned items belong to the new turn, using object identity and serialized frequency. After resolution an item is converted to its replay shape, boundary-specific metadata is removed, IDs and pairs are made consistent, and only the intended current batch is appended. A context-aware session must accept `wrapper` on its four operations for the adapter to pass it. SQLite protects each transaction, while a multi-step workflow remains a sequence of operations. Response compaction can wrap an underlying session using input or a stored response ID, defers updates while local outputs still need association, and uses backend-aware conditional replacement where available. ### Concurrency, cancellation and error decisions

Provider `parallel_tool_calls` and the SDK function-tool concurrency cap govern different layers. The SDK batch executor starts local handlers up to its cap, watches completion, preserves model order, and separates handlers still in execution from work in post-invocation processing. It has separate cleanup policies for a failure selected from a sibling and for parent cancellation. Tool-local cancellation can be shaped by tool failure policy. Parent cancellation must reach the caller. Decorated synchronous functions use `asyncio.to_thread`, while async handlers can use the SDK's explicit timeout path. Cancellation of the waiter cannot interrupt a Python thread executing synchronous application code. Input and output tool guardrails fence the side-effect and output commitment respectively, with optional early guardrails before an approval prompt and rechecking just before the approved invocation. A tool exception defaults to model-visible failure text. Explicit `None` propagates an ordinary exception, and timeout behavior and configuration-specific formatting use separate policy. Native tool families have distinct dispatch and lifecycle semantics. [Tool execution configuration](repos/openai__openai-agents-python/src/agents/run_config.py:143), [bounded batch executor](repos/openai__openai-agents-python/src/agents/run_internal/tool_execution.py:1600), [batch failure cleanup](repos/openai__openai-agents-python/src/agents/run_internal/tool_execution.py:1690), [single invocation](repos/openai__openai-agents-python/src/agents/run_internal/tool_execution.py:2021), [decorator use of worker threads](repos/openai__openai-agents-python/src/agents/tool.py:2818), [error formatter scope](repos/openai__openai-agents-python/src/agents/run_config.py:465).

Model retries operate within the turn. The retry circuit combines settings, normalized errors and provider advice, and gives aborts and emitted unsafe stream events a veto on the ordinary policy path. Stateful continuation and programmatic tool calling carry additional replay restrictions. There is a legacy `conversation_locked` exception path with its own cap and delay schedule. Timeout-owned stream iteration uses a task that owns construction, pulls and cleanup so context tokens and resources remain on the correct task. Usage merges provider counters with attempt entries, keeps known terminal usage, and indicates some attempts with zero known tokens. A model-run budget measures logical turns. It provides no complete transport quota because a provider client can also retry. Run error handlers are limited public decisions for `max_turns`, `model_refusal` and `invalid_final_output`, with validation and history inclusion policies. Model, tool, guardrail, user configuration and persistence errors remain distinguishable. ## 3. Why the design works and its governing invariants

| Invariant | Enforcement and architectural consequence |
| --- | --- |
| One active agent, one logical turn boundary | A turn snapshots the tools, handoffs, instructions and schema of the producer. Transfer selects a new owner for subsequent turns. Pausing during tool work preserves the budget and resumes that work first. The four transition shapes let common turn resolution be reused by both runners. |
| One canonical local invocation per call identity | Provider call ID, tool lookup key, payload, caller and owning agent have different roles. Canonical resolution and historical invocation records preserve the intended handler, correlate the output and let exact completed invocations be omitted. A reused tool definition can service several distinct requests. |
| Authorize before invocation and checkpoint after acceptance | Approvals and input tool guardrails precede local invocation. Output guardrails for a tool precede accepting its result. Accepted results can be recorded before best-effort metadata and end hooks, permitting recovery after those later callbacks fail. A model response is data until the local dispatcher recognizes an executable item and the application policy admits it. |
| Model replay, client session and public observations preserve different information | Replay strips approval-only artifacts and normalizes duplicate IDs or orphan calls. Session persistence retains the appropriate completed items under its own policy. Raw responses and semantic events can help diagnostic or UI clients interpret an ongoing run. Separate representations avoid conflating a caller's reconstructed model input with a stored event. |
| Provider acceptance and SDK completion are distinct | A Responses continuation request can succeed at the provider before local hooks and dispatch finish. Staged input is admitted only at its defined ownership boundary. The accepted-response interruption marker lets restore finish locally without re-requesting an accepted response. Ordinary retries apply only if replay is permitted. |
| Writes and lifecycle effects have explicit recovery limits | An interrupted turn can retain accepted tool output, owner and a pending append across JSON. Exact matching distinguishes lost acknowledgement from a pre-append failure under exclusive access. A later terminal write failure is deliberately fenced off because restarting terminal hooks or their effects may be incorrect. |
| Only the owner disposes a resource | Caller traces, providers and injected sandbox sessions are caller-owned. Task-owned websocket/MCP or sandbox resources must be closed or released by the appropriate owner. The trace processor exports a record independently of the run's success. |

These invariants are practical because each layer has a local answer to a different question. The model adapter decides what the wire response means. Turn resolution decides what work is actionable and who takes the next step. A session can answer whether a batch is present. `RunState` can answer which part of a paused turn remains. A trace processor can observe the execution independently. Their composition is strongest when the boundaries use stable identity and explicit outcomes. It is weakest when a layer reconstructs another layer's decision from incidental shape, such as history identity inferred from equal payload counts or future turn choice inferred from tool settings. Findings W1, W2 and W3 demonstrate these failure modes. ## 5. Weaknesses

The labels below distinguish observed defects, compatibility limits and design tradeoffs. Priority describes SDK reliability impact in the tested scope. It does not assign security severity or infer exposure through a live provider.

### W1. High priority, output-check cancellation is silent in streaming and commits unvalidated text in the async run

A normal assistant message entered an output guardrail that raised `asyncio.CancelledError`. `Runner.run` propagated cancellation and stored the assistant candidate in SQLite anyway. `Runner.run_streamed` exhausted `stream_events()` without an exception, final output or a diagnostic `run_loop_exception`, and stored only the user message. Application cancellation after the asynchronous guardrail started produced the same difference in durable history when using `Task.cancel()` for `run` and `result.cancel()` for streaming. Both guardrail `finally` blocks ran. A terminal tool output under explicit application cancellation stayed out of the durable history in both modes, which narrows the write divergence to the plain assistant candidate in the measured matrix. The swallowed child cancellation is separate from the documented behavior of explicit stream cancellation. [Async guardrail cancellation and write](repos/openai__openai-agents-python/src/agents/run.py:2167), [stream guardrail task](repos/openai__openai-agents-python/src/agents/run_internal/run_loop.py:511), [stream background exception handling](repos/openai__openai-agents-python/src/agents/run_internal/run_loop.py:2366), [stream cancelled-task detection](repos/openai__openai-agents-python/src/agents/result.py:1192), [stream terminal contract](repos/openai__openai-agents-python/docs/results.md:199).

An ordinary guardrail exception such as `RuntimeError` failed both runs and persisted the unchecked plain assistant message in both. A fresh unguarded run reading the same durable SQLite store saw that message as ordinary history. An explicit tripwire withheld the plain candidate. This is a distinct, observed persistence policy. The repository deliberately preserves completed tool work under a crashing terminal guardrail, which is justified when tool effects have already occurred. The plain-response failure showed persistence even with zero tool work. The candidate also reached `on_agent_end` before the guardrail in all four cases, including an explicit tripwire. ### W2. Medium priority, copying a repeated history item turns it into a durable new input

A `session_input_callback` intentionally repeated one older user message in the current model view. Returning the same object twice or a single deep copy preserved the intended SQLite history. Returning two equal deep copies submitted the same intended two occurrences to the current model and appended one old message to the database. The algorithm exhausts its history frequency, loses provenance for the second copied occurrence and classifies it as new input. ### W3. Medium priority, staged input rejects a continuation already determined by a handoff

### W9. Design limit, the top-level stream buffers an entire turn without transport backpressure

The top-level queue has no `maxsize`, and raw event publication uses `put_nowait`. An attached consumer participates in acknowledgement between continued turns. That mechanism does not apply during the production of a single turn, including when the consumer is paused at an earlier event. A detached consumer can let the whole run complete with events queued for later consumption. With the iterator started and paused on its first event, occupancy was 1,003 or 10,003. Both delivered every delta on drain. This buys immediate producer progress, while memory grows with the undelivered event burst and retention period. The nested `Agent.as_tool(on_stream=...)` dispatcher and default trace processor have explicit limits, which narrows the unbounded top-level behavior. ### W10. Explicit operational tradeoff, session transactions protect batches and recovery still requires conversation ownership

`Session` exposes append, read, pop and clear. The runner can await a known write outcome, keep a local checkpoint and compare tail fingerprints, but the protocol has no durable operation ID or compare-and-append guarantee across separate writers. The SDK explicitly requires the same backend, session ID and exclusive access for acknowledgement reconciliation. With two valid SQLite objects on the same file and session ID, a deterministic overlap let B read A's unanswered request and commit B's response before A's. The documented exclusive-history requirement prevents classifying the observed overlap as a defect in supported recovery. ## 9. Post-mortem and prioritized improvements

The core loop began from a compact abstraction that maps an output into a final answer, tools or a handoff. The pinned contract also has to deliver partial stream output, preserve resumable tool effects, bridge three different conversation owners, support older persisted records, and deal with actors that can cancel one another. The two loops make sense given different delivery mechanisms. The cost is that each boundary can be decided before or after different awaits, or decided twice using different evidence. The right incremental path is to add a shared typed decision where there is already a demonstrated parity gap. A large rewrite would risk losing the hard-won approval, checkpoint and provider semantics the suite now protects.

1. **P0 — Align terminal verdict, effects and error provenance.** Build a shared terminal outcome for accepted, rejected, validator-failed and cancelled output, and distinguish a cancellation originating in application code from one explicitly requested by the result consumer. Persist valid accepted items or a safe representation of already executed tool effects under that outcome. Make a plain unchecked assistant message ineligible for normal persistence after validator failure or cancellation unless an application explicitly opts in. Preserve the existing raw stream and end-hook observation semantics through an explicit candidate boundary, since changing their timing can break consumers. Start with the four guardrail outcomes and both runner modes, then cover resumed terminal leaves and max-turn fallbacks. [Async terminal gate](repos/openai__openai-agents-python/src/agents/run.py:2090), [streamed terminal gate](repos/openai__openai-agents-python/src/agents/run_internal/run_loop.py:559), [terminal guardrail recovery](repos/openai__openai-agents-python/src/agents/run_internal/blocked_output.py:426).
2. **P0 — Resolve effective history ownership before shaping a provider request.** Feed capability information from the resolved model into the turn preparation that selects full history or a server delta. For Chat Completions, honor explicit warn-and-ignore compatibility by replaying full local history. Reject all strict-mode continuation forms before the first model or local tool action. Treat synthetic stream IDs as diagnostics without server-continuation semantics. Add a two-turn wire-level contract under explicit and automatic settings, and cover a handoff between adapters with a different owner. [Model resolution boundary](repos/openai__openai-agents-python/src/agents/run_internal/turn_preparation.py:136), [adapter validation](repos/openai__openai-agents-python/src/agents/models/openai_chatcompletions.py:565), [server tracker](repos/openai__openai-agents-python/src/agents/run_internal/oai_conversation.py:124).
3. **P1 — Replace inferred ownership with explicit provenance at the apparent boundary.** Share a supported next-step eligibility decision between `RunState.add_input` and resumed turn resolution, with a stable rule for pending handoffs. Validate a selected handoff's history-mode incompatibility before transfer callbacks. Track new and historical session input sources explicitly when possible. Preserve old callback shape with a documented policy for ambiguity and ensure normal copied history cannot be promoted to a durable new turn. Deliver targeted changes with regression controls for previously completed siblings and duplicate legitimate incoming text. [Staged input gate](repos/openai__openai-agents-python/src/agents/run_state.py:1060), [handoff decision](repos/openai__openai-agents-python/src/agents/run_internal/turn_resolution.py:3066), [session callback classification](repos/openai__openai-agents-python/src/agents/run_internal/session_persistence.py:508).
4. **P1 — Turn implicit execution limits into explicit contracts.** Put the emitted-stream-event retry veto before compatibility retries. Clarify initial guardrail representation and add a parity fixture comparing the actual arguments, verdict and history. Provide an opt-in top-level stream queue policy, with tests for a deferred reader, a paused active reader, early close and the after-turn lifecycle. Preserve a deterministic delivery contract for raw and semantic events when limiting memory. Ensure mode-specific payload differences are intentional and observable. [Retry order](repos/openai__openai-agents-python/src/agents/run_internal/model_retry.py:832), [guardrail entry](repos/openai__openai-agents-python/src/agents/run_internal/run_loop.py:1899), [queue acknowledgement](repos/openai__openai-agents-python/src/agents/result.py:989).
5. **P2 — Take small correctness and portability wins.** Cache the valid empty MCP catalogue using an explicit sentinel, backfill completed guardrail siblings on ordinary failures, and correct the agent-scoped handoff hook description. Provide a documented owner/cleanup mechanism for implicitly created sync loops and track policy deprecation without breaking loop reuse. Prefer observable task-progress primitives to future or event-loop introspection where the runtime controls both sides. Quantify effects with the existing async stability checks and public concurrency tests. [MCP cached catalogue](repos/openai__openai-agents-python/src/agents/mcp/server.py:889), [guardrail result handling](repos/openai__openai-agents-python/src/agents/run_internal/guardrails.py:225), [handoff hook contract](repos/openai__openai-agents-python/src/agents/lifecycle.py:164), [sync loop reuse](repos/openai__openai-agents-python/src/agents/run.py:2579).

The operational consequences cluster around premature acceptance, false eligibility and mismatched history ownership. A callback can run before the transition it describes is valid. A tool result can reach a stateless provider without the call it answers. A background task can look complete even though its guardrail was cancelled. The normal application setup still benefits from explicit providers and per-dialogue ownership, and a deployment requiring exactly-once effects across process failures needs backend idempotency around the application's own tools. Adding external coordination semantics to the base `Session` contract would be a separate compatibility design. [Exclusive ownership requirements](repos/openai__openai-agents-python/docs/results.md:140), [ordinary Session protocol](repos/openai__openai-agents-python/src/agents/memory/session.py:69).

### Probe construction and primary witnesses

For streaming, call `Runner.run_streamed` and exhaust `stream_events()` while recording the public result and thrown exception. Use fresh objects for each repetition and explicitly close caller-owned clients and databases. Compare the recorded calls supplied to the model, application callback order, and persisted rows separately.
