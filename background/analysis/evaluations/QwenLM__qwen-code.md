## 3. Why the design works and its governing invariants

| Invariant | Mechanism and boundary |
| --- | --- |
| One authoritative mutable history per chat | Prompt admission should serialize through preparation, provider iteration, history commit and cleanup. Host queues provide an additional barrier. The chat's own queue breaks at two waiting sends, documented in F1. |
| One result for each executable model call | Separate internal and provider IDs, attempt reset, explicit replay and skipped-call responses, request-order finalization and repair of incomplete restored pairs preserve protocol structure. External mutation durability depends on the owning invocation and engine. |
| Checks apply to the operation that will actually run | Registration establishes discoverability. Per-invocation policy evaluates resolved target, trusted owner and effective arguments after rewrites. Approval and execution correlate by ID and restore the relevant owner context. |
| One terminal decision per loop run | Procedural early returns or one bus `loop.finished`/failure resolve the host view. Bus generation checks prevent late model or tool bookkeeping. Scheduler callback rejection exposes a gap before the loop sees a terminal payload, documented in F2. |
| Recover without fabricating an answer | Unfinished provider attempts are retried, compacted, continued or failed based on visible content, call emission and route. A restore can retain partial text or synthesize a tool result that explicitly reports an interruption. |
| Write authority and agent ownership stay scoped | The lease fences transcript mutations, Managed verifies activation and commit facts, and separate chat/registry/transport views preserve subagent and workspace ownership across asynchronous boundaries. |

The useful abstraction is the model/tool **phase boundary**. Round events can be provisional, yet a tool batch normally launches after a model round has settled. A tool result can produce progress while it executes, yet provider injection and recording need a stable completed order. Keeping those boundaries distinct permits transport retry, native and MCP tool execution, and transcript reconstruction to share the same normalized types. The code also has separate rollback mechanisms for partly delivered provider output and partially persisted conversation state. ## 5. Weaknesses and evidence status

### F1. Chat send ownership admits simultaneous waiters and can be stranded before iteration

**Reproduced defect in the exported Core chat interface. High priority for history integrity.** `LlmChat.sendMessageStream` documents waiting for the previous message, but each caller awaits the current promise before assigning a fresh resolver. Two callers waiting on A take the same predecessor. When A settles, B and C both proceed, taking turns replacing the shared pending slot. The route's mutable token-count adoption is also before this wait. Both user entries can reach history before either response, and B's release cannot stand in for C's completion or vice versa. The same method acquires before returning the async generator, while its normal release runs inside that generator's `finally`. A return before the first `next()` bypasses the body and leaves the chat waiting on its old slot. Cancellation of a waiting caller also does not race that promise. [Serialization contract](repos/QwenLM__qwen-code/packages/core/src/core/llm-chat.ts:3513) · [Wait and replacement](repos/QwenLM__qwen-code/packages/core/src/core/llm-chat.ts:3608) · [Acquisition before generator creation](repos/QwenLM__qwen-code/packages/core/src/core/llm-chat.ts:4376) · [Generator release](repos/QwenLM__qwen-code/packages/core/src/core/llm-chat.ts:6092)

A real loopback SSE probe held A after its first chunk and queued B and C. After finishing A, it held B through C's request **and C's complete response**. C's wire payload included both B and C prompts, and contained no B response. Internal history ended with both user entries followed by C's model reply and then B's. ### Tradeoffs, source-supported risks and unresolved questions

- **C1 · Scope of cancellation. Source-supported risk.** Provider reads and closes are raced against abort, and the optional bus can detach the external run after a deadline. This protects host settlement. Tool-side effects and resource cleanup have their own lifetimes. A live invocation that has started may still finish on its backend. Native tool execution timeout is opt-in by default, and the procedural path awaits all owned work. The extension contract needs an explicit role for awaiting cleanup, uncertain side effects and disposal. F2 demonstrates the difference between host result settlement and tool completion. [Provider cancellation](repos/QwenLM__qwen-code/packages/core/src/core/llm-chat.ts:1728) · [Bus cancellation cap](repos/QwenLM__qwen-code/packages/core/src/event-bus/conversation.ts:72) · [Late tool-handler results](repos/QwenLM__qwen-code/packages/core/src/event-bus/tool.ts:45) · [Tool timeout configuration](repos/QwenLM__qwen-code/packages/core/src/core/coreToolScheduler.ts:6277)
- **C2 · Adapter-specific liveness and sizing. Design tradeoff with residual risk.** Leaving policy in wire adapters has reduced provider shape leakage into the loop. It also makes idle/lifetime policy uneven. OpenAI-compatible and Anthropic use shared stream guards, Responses has its own guard, and the Gemini config contract explicitly calls out the lifetime gap. The shared guard's lifetime counts upstream wait, including drip feeds, and allows slow consumers without charging their processing time. Application-level cancellation is still common. Context admission is approximate when prior authoritative counts are unavailable, particularly with system/tools and large media. The clamp is on the estimate, and reactive overflow remains necessary. - **C3 · Ordering versus throughput. Design tradeoff.** The scheduler settles approvals ahead of execution, preserves barriers between mutating batches and treats unknown tools conservatively. An earlier prompt/permission can hold unrelated safe work, and per-batch caps allow several concurrent agents to multiply aggregate concurrency. `agent` is considered concurrency-safe by name, while explicit worktree/container isolation is a separate execution decision. Several child agents can therefore share a workspace under their tool policies. Per-model/background claims constrain one form of resource use. Cross-agent file ordering is a lifecycle/coordination property, not a consequence of the scheduler cap. - **C4 · Replay has a layer-specific meaning. Design tradeoff.** Provider fingerprint replay suppression makes model retries safer, while the local legacy transcript cannot reliably prove effects in every process-loss window. MCP deliberately reconnects after ambiguous effects without replaying the call, and re-verifies whether a rediscovered tool remains safe before replay.
